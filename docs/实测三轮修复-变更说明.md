## 0. 为什么上一轮修复「无效」

两个问题的共同教训:**修在了错误的抽象层**。

- 赛马娘卡上一轮(八项第 7 项)修的是 jQuery 事件委托、数据 RPC 扩展、剪贴板宿主桥、
  楼层 depth——该卡三类交互**完全不用 jQuery/TavernHelper**,走的是「内联事件属性 +
  脚本内 function 声明 + 裸 document.getElementById/navigator.clipboard/alert」。
  修复面与失效面零交集,自然「修复无效」。
- team 模式上一轮的「同主传递前序产出」只覆盖首轮;而版本冲突高发的**打回补做轮**
  因 `goal_filter` 跳过未点名子目标,`prior` 收集为空 —— 修复在关键路径上失效。

本轮先用「卡内真实脚本 / plan 终态」在本地复刻出失败,确认红,再修,再确认绿
(赛马娘卡沙箱用例已验证:关掉修复即 2/3 失败)。

## 2. 行为变更与兼容性

- **team 终态判定口径变化(对外可观测)**:失败子目标经打回补做成功后任务可判 `done`
  (旧实现恒 `partial`)。这是修正假阴性;真正仍失败或审计/终审未通过才 `partial`。
- **`tasks.error` 语义扩展**:partial 终态写入可解释原因(此前恒空);重跑成功(Done)写空串
  清掉上一轮残留。旧库无需迁移(表结构不变)。
- **`TaskOutcome` 新增 `error` 字段**(内部类型,非 API 契约);六模式构造点同步补齐。
- **审计输入新增子目标编号**(「子目标 N「名」」)——纯提示词输入形态,不进对外契约。
- **沙箱能力扩展**:`document.getElementById` 门面 + select 状态镜像 + boot 控件快照。
  安全边界不退步:门面读走只读镜像,写仍经既有 DOM 白名单 batch 通道回写宿主元素;
  目标元素限定在已上屏的卡容器内;沙箱仍 `sandbox="allow-scripts allow-modals"`
  (无 allow-same-origin),拿不到宿主 DOM/localStorage/token。
- 其余为纯修复,不改变对外契约。

## 4. 残留与未做

- **单主内的自造版本**:规划器把「整合/校对」类子目标派给某个主 agent 时,该主仍可能
  自行另写一版(本轮实测复现)。现有防线=审计拦截 + 终态转 partial + error 说明;
  未加代码级校验(需判定产出语义是否为「整合」,超出本轮范围)。若要根治,方向是
  在规划提示词层禁止把「整合/汇总」派给主 agent,或对「整合」类子目标强制只读输入。
- **WebView2 下 `alert` 弹窗**:沙箱属性含 `allow-modals`,WebView2 默认对未处理
  `ScriptDialogOpening` 弹原生框;本轮未在桌面端做物理弹窗实证(与上方点击通道限制同因)。
  若实测弹窗不出现,再在沙箱 shim `alert` → 宿主 RPC 展示(列为兜底,不默认做)。
- **「禁止汇总另起一版」仍是提示词级约束**,无代码校验;本轮未加硬校验。
- 未改动 legacy/solo/multi/plan/custom 其余模式行为;未重构沙箱安全边界。
