- 4b 删除字符串回退的依据:`classify_engine_error` 全仓**只有 1 个调用点**
  (`agents/engine/mod.rs` 的 SSE Error 终态生产处);连接器 `generate`/`generate_stream`

  已在各处以 `.message()` 或注释显式落回 String。**没有保留任何字符串猜测回退路径**。

  改为只读上游**结构化** `error.type`/`error.code`,不再扫 `message` 自由文案。影响面已核实:

  改为 `upstream_error`(可重试),**不构成重试风暴回归**。

## 3. 已知兼容性变更登记

> 按仓库惯例,凡影响既有用户行为的改动须在此登记。当前只有一项。

### 3.1 批次 3:库版本高于应用时**拒绝启动**(有意)

**变更内容**(计划 §批次 3):`Db::open` 在建表前读 `PRAGMA user_version`;
若 `db_version > SCHEMA_VERSION`,返回 `Err` 并在文案中给出两个版本号与处置建议,
不再静默继续。

**这是有意的兼容性变更,不是缺陷**:

- 原行为是「库比代码新时静默打开」,风险后移且无任何提示;新行为把问题**提前暴露在启动点**,
  失败原因直接可读(两个版本号),符合仓库「绝不静默放过」的纪律。
- **副作用**:测试版 / 便携版共用同一个库、且其中一端为旧 exe 时,**旧端将无法打开该库**。
  这属于**期望的更早暴露**——旧端继续运行才是不该发生的状态。
- **回滚安全**:本批次不删列、不重命名,仅新增版本号与事务包裹;库文件对新旧 exe 均无破坏性改动。

**已兑现的验收断言**(见 §2.3):伪造 `user_version = SCHEMA_VERSION + 1` → `Db::open` 返回
`Err`,文案含「库 v{db}」与「应用支持的 v{app}」两个版本号,且**在建表批之前**返回
(库内未新增任何表,版本未被改写)——测试
`newer_database_version_is_rejected_with_both_versions`。
