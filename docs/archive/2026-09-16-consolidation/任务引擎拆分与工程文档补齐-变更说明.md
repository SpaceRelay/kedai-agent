## 一、4.2 `TaskBackend` 拆窄接口(纯结构重构,行为不变)

**背景**:`services/task_core/backend.rs` 是 20 方法的上帝接口,把「读任务/写库/追踪/提示词/
流程/事件/终态/生成重试」全混在一起;`record_self_heals` 直接引用 `agents::engine::executor::SelfHealRecord`
(倒置不彻底);`plan_task_retry` 等把重试/解析**算法**当宿主能力;`agent_flow()` 返回
`Arc<Mutex<AgentFlowService>>`,把锁纪律泄漏给 `task_engine`。

**改动**:

1. **按 ISP 拆 8 个窄接口**:`TaskStore`(任务/子任务读写)、`TaskTrace`(usage 与调用追踪)、
   `TaskSettings`、`TaskPromptKit`(提示词组装)、`TaskFlowAccess`、`TaskEvents`、
   `TaskTerminalSink`、`TaskGenerator`(7 个单次生成原语)。`TaskBackend` **保留为聚合别名**
   (supertrait + blanket impl),既有 `Arc<dyn TaskBackend>` 构造点零改动;新代码应依赖窄接口。
2. **算法上移回 task_engine**:新增 `task_engine/retry.rs`(`retry_if_empty_output`/
   `generate_step_retry`/`plan_task_retry`/`plan_revise_retry`/`summarize_task_retry` + 4 常量,
   签名由 `&TaskService` 改为 `&dyn TaskBackend`)与 `task_engine/parse.rs`(`parse_plan` +
   `salvage_step_objects`,8 例测试随迁);删除 `task_service/parse.rs`。接口只保留「发一次调用」的原语。
3. **锁纪律回收**:删 `agent_flow()`,改 `TaskFlowAccess::current_flow()`——宿主在能力内部完成
   「加锁 → 取启用流程 → 启用校验 → 工具集校验」,只交 `AgentFlowConfig` 快照。`task_engine` 内
   现已无任何 `agent_flow` / `Mutex<AgentFlowService>` 引用(已 grep 确认)。
4. **中性 DTO**:新增 `task_core::TruncationHeal`(与 `SelfHealRecord` 一一对应),
   `record_self_heals` 入参不再跨层引用 agents 类型;转换落在已依赖 agents 的引擎边界
   (`task_engine::executor::to_self_heals`),`solo.rs`/`custom.rs` 共用。

**验证**:`cargo test --workspace` **1004 passed / 0 failed**;`tests/tasks.rs`(50)与
`tests/task_events.rs`(9)未减;`cargo clippy -D warnings` 0 告警;`check-arch` 全绿(规则 C
仍锁 `task_engine ↛ task_service`,未绕过);新增 DTO 转换护栏 2 例。

**未做(如实登记)**:①`team.rs` 的自有重试/解析未合并(其 `parse_team_topology` 与
`plan_task_retry` 的解析目标不同:拓扑 vs 计划),属行为敏感改动,留待另立批次;
②`generate_text` 仍在宿主侧(承担连接器调用与 `task_llm_calls` 落库,非纯算法)。

## 二、6.5 EJS 冻结门禁(威胁模型 D5,`tools/check-arch.mjs` 规则 H)

**背景**:`parsing/assistant/ejs/` 是自研迷你 JS 引擎,纪律为「只接受安全修复,不再扩展新能力」,
但此前只有文字纪律(威胁模型 D5)。

**改动**:新增规则 H——统计 `ejs/env.rs` 的 `builtin_global` 表条数,与脚本内基线
`BASELINE_EJS_BUILTINS = 64` 比较,**超过即 FAIL**;去注释后计数,match 分支别名各计一条、
内联对象成员名各计一条;解析失败(文件缺失/`fn builtin_global` 或 `match name` 或 `_ => None`
结构未识别/计出 0 条/出现无法分类字面量)一律**显式 FAIL**,绝不静默返回空。
注释写明「**调低是唯一合法方向**」。

**验证(变异测试)**:基线档 64 条 = 基线 → OK;临时插入假 builtin 后 → 65 > 64,FAIL 并给出
「只接受安全修复,新模板能力请走 `scripts/runtime.rs` 的 rquickjs 沙箱」文案;还原后复查 OK。

## 三、3.2 构建指纹链评估(D2,只出评估文档)

**结论(评估后登记为设计边界,不修)**:两套指纹(`Write-BuildStamp.ps1` 的 SHA256 sidecar vs
`build.rs` 的 FNV-1a 内嵌)**输入都是 `web/dist`,都不覆盖 exe 自身字节**;现有比对只在两个
sidecar 之间,`/api/health.build_id` 无消费者 = 链断裂点。两案收益均仅为把「两端一致」升级为
「单端 包↔sidecar 一致」,而被检值由被检 exe 自报、无签名/信任根,同时替换 exe+sidecar 即绕过,
成本却落在最敏感的发行链路(Android `.so` 内嵌值全变、新增 build-dep、锁同步连带面)。

**推荐**:维持现状 + 补文档;**不选方案①**(build.rs 改 SHA256);若日后必须落地,优先文档 §六
的 `exe_sha256` 校验路径(几乎零风险、不动内嵌指纹/Android/build-dep),次选方案②(sidecar 增 FNV,
用 `Add-Type` 内联 C# 的 `unchecked` 规避 64 位溢出),不选方案①。附验收断言 B1–B5
(核心 B2:替换成另一次构建的 exe 后,启动器必须拒绝启动)。详见
[构建指纹链评估-2026-09-13.md](构建指纹链评估-2026-09-13.md)。

## 四、6.2 数据库版本与降级行为(文档部分;代码待办)

**现状**:`user_version` 恒为 0、无迁移台账(`backfill_meta` 只存 FTS/消息回填游标);升级靠
启动时 `CREATE TABLE IF NOT EXISTS` + 9 个幂等 `ensure_*` 补列/补表/补索引
(`server-rs/src/models/db/mod.rs:62-91`),schema 至今**只增不减**;任一步失败即 `Db::open` 失败
(命令行 `exit(1)`、桌面弹错),升级链**非单事务**,失败可停在中间态、靠幂等续补收敛。
因只增不减,旧版 exe 打开新版库**不报错、静默运行**(降级「大概率能跑」属未实测推断);
无 down 迁移、升级前也不自动备份。

**已交付**:行为矩阵(旧库→新版 / 新版库→旧版 / 桌面+Android / 测试版与便携版共用库 /
项目库与 `%APPDATA%` 分叉 / 双库合并)+ 引入 `PRAGMA user_version` 的最小方案与 7 条验收断言;
风险与不支持项单列。见 [数据库版本与降级行为.md](数据库版本与降级行为.md)。已登记
[known-limitations.md](known-limitations.md) L18。

## 五、6.3 代码签名与 SmartScreen(文档)

**实测**:根 `Kedai.exe`、`dist\kedai-server.exe`、`dist\Kedai-portable\Kedai.exe` 及 NSIS 安装包
均 `Get-AuthenticodeSignature` → **NotSigned**;Android APK 则经 `keystore.properties` 签名
(v2 scheme),证书 SHA-256 实测 `19d79a89…062f`,`CN=Kedai`。**为什么不签**:证书属付费产品决策
(未购买),自签证书对 SmartScreen 无效。

**已交付**:SmartScreen「Windows 已保护你的电脑」→「更多信息」→「仍要运行」步骤(含整包被拦时
「解除 ZIP 锁定再解压」的替代路径,明确反对全局关闭 Defender);产物来路自查(`.build.json` 的
`dist_hash`/`version`/`build_time` 只覆盖前端资源、**不是 exe 二进制哈希**,另用 `Get-FileHash`
核 exe 本体;APK 覆盖安装的同密钥约束);转正式签名的选型与构建改动要点(OV/EV + 硬件令牌或云
HSM + `signtool` 时间戳)。见 [代码签名与SmartScreen说明.md](代码签名与SmartScreen说明.md),
已登记 [known-limitations.md](known-limitations.md) L17 与 README 安装段。
