## 0. 经验总结(先读,决定后面怎么改)

### 0.1 这批 bug 的共同形态:状态被「静默改写」

五处缺陷表面各异,内核是同一个错误——**平台在传递语义时丢掉了定性信息,或悄悄替换了调用方的意图**:

| 现象 | 平台做了什么 | 调用方以为 | 实际情况 |
|---|---|---|---|
| 子任务被喂 `max_tokens=64` | `clamp(64, 4096)` 静默抬升 | 按 512 默认值执行 | 按 64 执行,推理烧光必然截断 |
| `agentend` 拼错 id | 恒返回 `ok: true` | 已清理 | 根本没这个任务 |
| `read` 未命中 | 返回与正常结果同构的 `content` | 读到了结果 | 其实是候选清单(15 条) |
| 聊天被截断 | `SseEvent::Finish` 不带 `finish_reason` | 正常完成 | 正文腰斩 |
| `ended` 状态 | 同时表示「完成后被召回」与「中途中断」 | 可据 status 判有无结果 | 两种情况不可分 |

**判据**:凡是「调用方无法从返回体/事件自证真实语义」的地方,就是下一个 bug 的温床。
修法不是加文档说明,而是**让返回结构自证**(显式字段/显式失败),或在日志里留下可诊断线索。

### 0.2 推理模型的预算语义是「推理与正文共享同一池」

本机实测(`deepseek-flash`)三条硬数据:

- `max_tokens=64` → 推理烧掉全部 64,正文为空,自愈到 128 依然如此;
- `max_tokens=10000` → `reasoning_tokens=9894`,正文只剩 178 字符即 `finish_reason=length`;
- 单次子任务仅推理就能吃掉近万 token。

**结论**:任何「小预算」档位对思考模型都等于「必然截断」。所以下限必须按推理消耗量级设(16384),
而不是按交付物长度设;且**自愈的封顶必须高于下限**,否则「翻倍」会被封顶压回原值,自愈被静默放弃
(本次 `TRUNCATION_HEAL_MAX_TOKENS_CAP` 8192 < 新下限 16384 正是这个陷阱,属连带必修项)。

### 0.3 「四处同源」的常量必须一起改

截断自愈的预算决策收敛在 `utils/retry.rs`(2026-09-13 批次 4.1 四路合一),但**封顶常量仍分散在四处**。
本次改校验上限时,四处的封顶与相关注释都要同步,否则会出现「设置页允许 131072、重试封顶仍 65536」
这类自相矛盾——`doubled_heal_budget` 会因 `min(current*2, cap) <= current` 恒判「无增长」。

**纪律**:改这类跨路径常量时,用 `grep` 把「同一语义的所有常量与注释」一次列全,逐个确认。

### 0.4 与并行写者共处:提交前必须先看工作区是不是自己的

本轮实施期间有**另一个会话在同一分支并行写同一批文件**(R5 测试基建)。教训:

- 动手前 `git status` 是 clean,不代表中途还是 clean;提交前必须重新核对;
- 交织文件(同一文件的 hunk 分属两个批次)无法用 `git add <path>` 干净剥离,只能按「文件归属一个主题」合并提交;
- **依赖倒挂**:我的新测试用了并行批次的 `dummy_for_test()` 新签名,导致「单独提交我的文件」会编译不过——
  提交粒度受**编译依赖**约束,不只是文件边界。

### 0.5 顺带修掉的既有缺陷要写进提交信息

R5 批次把两个权限测试改用 `TempDataDir` 后,把守卫自动创建的目录当文件写,机制被破坏
(`Os error 5 拒绝访问`)。我改成在其内一层放「文件」以保留原机制。这类「修别人的在制品」必须
在提交信息里说清,否则后续排查会把作者记错。

> ② `end` 由 `bool` 改为显式枚举 `SubtaskEndOutcome`(`Missing`/`Interrupted`/`AlreadyFinished`),

> [子任务终态语义与退出确认弹窗-变更说明.md](子任务终态语义与退出确认弹窗-变更说明.md)。

### 2.1 要解决的问题

记录第(3)条原文:

> `dup_name` 完成后被 `agentend`,最终 `status=ended`,但 `result` 仍保留;而中途召回的
> `team_lifecycle_probe` 同样是 `ended`,`result` 为空、`error` 也为空。用 `status==="done"` 过滤会丢掉
> 「已完成但被结束」的交付物,用 `ended ⇒ 空结果` 又会误判。

即 `ended` 一词同时承担两种语义。**根因**:`AgentSubtaskService::end` 无条件 `set_status(id, "ended")`,
把已完成(`done`)的记录也覆盖成 `ended`。

### 2.2 改动点

| # | 改动 | 位置 | 说明 |
|---|---|---|---|
| 4.1 | `end` 对终态幂等:已是 `done`/`error` 的记录不覆盖 status,仅记 `finished_at`,并返回「未中断」 | `services/agent_subtask_service.rs`(`end` / `set_status`) | 让「完成后召回」保持 `done`(result 保留),只有真正中途召回才是 `ended` |

| 4.3 | 迁移两处接线 | `models/db/mod.rs`(`Db::open` 升级链内)、`migration/merge.rs`(两侧各一次) | 漏一处会在跨库合并时报「基线缺少列」 |

**`task_subtasks` 表也需加列**:它是 legacy 路径的等价表,契约映射(`check-contract.mjs` 的
「任务子任务」组)比对的是 `TaskSubtaskRecord` ↔ `TaskSubtask`,两表必须同形状。

### 2.3 验收断言

- `end` 幂等:对 `done` 记录调 `end` 后 `status` 仍为 `done`、`result` 保留、`finished_at` 非空、返回「未中断」。
- 迁移:`ensure_agent_subtasks_finished_at_column` 对全新库与旧库各跑一次,幂等(`adds_and_is_idempotent`)。
- 迁移元测试:老库升级后与全新库逐表比对 `PRAGMA table_info` 一致(既有 `schema_migration_meta` 自动覆盖)。

- 契约门禁 `node tools/check-contract.mjs` 通过。

### 2.4 风险与回滚

**风险(语义收窄,须登记)**:`ended` 的覆盖面变小——此前「用 `status === 'ended'` 判断被取消」的
调用方,现在对「已完成再召回」的任务会看到 `done`。这正是记录第(3)条的诉求,但属**行为变更**,
须在变更说明中登记为兼容性变更,并检查仓内既有消费点(`web/src/components/AgentPanel.vue` 的
`subtaskDot`/`subtaskCardClass`、任务详情渲染)是否依赖旧口径。

**回滚**:本批次是 `ALTER TABLE ADD COLUMN`(只增不改)+ 纯幂等语义修正;回滚只需还原代码,
新增列留在库中无害(旧代码不读该列)。

**回滚**:5.1–5.3 是纯替换,还原 `lib.rs` 即可回到原生对话框;前端新增文件删除、注册表两处回退。
