# Kedai 三结合梯队架构（老中青三结合）

> 借鉴我国干部队伍/领导班子建设中长期沿用的「老中青三结合」组织原则，将其四条精神
> （优势互补 / 传帮带 / 梯队衔接 / 动态循环）映射为代码治理模型，作为 kedai 演进的总纲。
> 本文件是架构决策依据：**任何结构性改动先对照本文件判断落点与代际影响**。

## 1. 「老中青三结合」的含义与内容

「老中青三结合」是干部队伍与领导班子配备的指导原则：以**老（经验者）**把关定向、
**中（骨干）**承上启下、**青（后备）**注入活力，三部分按合理梯次组合，保证事业平稳
交接、后继有人、不断层、不僵化。

| 组成部分 | 特点与作用 |
|---|---|
| 老（经验者） | 经验丰富、把关定向、原则性强；「传帮带」的主要承担者，防风险的压舱石 |
| 中（骨干） | 年富力强、业务成熟，处于干事创业黄金期；承上启下、攻坚执行的中坚 |
| 青（后备） | 朝气蓬勃、学习力强、可塑性强；队伍的活水与未来，敢闯敢试 |

**四条精神内核**：
1. **优势互补**：经验 + 成熟 + 活力互补，避免「全老则僵化保守、全新则轻率失稳」的单结构缺陷；
2. **传帮带**：老带中青、经验传承，在实践中培养，防止能力断层；
3. **梯队衔接**：合理梯次、后继有人，保证事业平稳交接、不断层；
4. **动态循环**：青年成长为骨干、骨干沉淀为经验者，队伍新陈代谢、永续发展。

## 2. 分层模型：四代际（3 层 + 组合根）

**澄清（2026-09-14）**：本模型是 **3 层 + 1 个组合根 = 4 个桶**，不是「四层」。
`entry` 不是第四层，而是组合根（Composition Root），其判据与纪律与前三个代际不同。

### 2.1 判据（把比喻降维成可裁决的标准）

| 代际 | 精确判据（一句话） | 对应的机器门禁 |
|---|---|---|
| **L1 老层 · 稳**（Anchored Core / 基石层） | 承载**兼容契约**：形状一变即破坏既有用户数据或外部生态（SillyTavern 角色卡/世界书/正则脚本/酒馆助手协议），且**自身不依赖任何上层** | 规则 D + I + J |
| **L2 中层 · 干**（Orchestration / 骨干层） | 依赖 L1 完成**业务流程**，自身不被 L1 感知；承担**协议翻译**（V2/V3、新旧字段、注入合成） | 规则 C + J |
| **L3 青层 · 活**（Frontier / 探索层） | **失败必须被隔离**（沙箱 / 设置开关 / 注册表三者至少有一），不反向定义上层语义 | 规则 H + J |
| **entry 入口 · 装配**（Composition Root） | 只做**拼装与配置解析**，不承载业务语义（业务逻辑沉淀于此则无法被测试与复用） | 规则 I（并按约定豁免方向校验） |

### 2.2 代际判定程序（新增：用于裁决争议，按顺序适用，先命中先定）

旧叙述最大的缺口是**没有可操作步骤**，导致 `tools/` 这类模块长期卡在「名义 L3 / 实测 L2」。
判定任何模块时依次过筛：

- **P1 契约性**：改动是否会破坏外部生态兼容或既有用户数据？**是 → L1**。
- **P2 依赖方向**：是否存在指向 L2 或 L3 的出边？**是 → 不可能是 L1**。
- **P3 隔离性**：失败是否被沙箱 / 开关 / 注册表三者之一隔离？**否 → 不可能是 L3**。
- **P4 装配性**：是否只做拼装与配置解析、不承载业务语义？**是 → entry**。
- **P5 复用度**：被 ≥2 个调用点复用的业务逻辑 → **L2**；仅直接服务用户交互 → **L3**。

### 2.3 名义代际 vs 实测代际（核心纪律）

> **名义代际**由设计意图决定，**实测代际**由依赖图决定。两者不一致时，**以实测为准**，
> 并把差异登记为债务（`arch-layers.json` 的 `registeredEdges`）。
> **不允许**用「名义上是 L3」为越代依赖辩护。

规则 J 已把这套裁决机器化；本节只保证人和机器用同一把尺子。
**典型案例**：`tools/` 名义 L3，但存在 `→services`（违反 P2、不满足 P3），故实测为 L2——
修法见 `docs/架构分析-2026-09-14.md §5`。

### 2.4 单值代际纪律（新增）

**代际是单值**。一个模块若内部存在两种纪律，**按子目录拆分**，不得给模块贴双标签
（此前 `web/src/mvu/` 被标为「L1+L3」，无法按单一纪律评审，已修正为 L1）。

### 2.5 前后端的方向模型不同（务必区分）

同一套 L1/L2/L3 词汇，在两端的**依赖位置不同**，因此允许方向也不同
（配置见 `arch-layers.json` 的 `dependencyRules.backendAllowed` / `frontendAllowed`）：

- **后端 = 隔离模型**：L3（工具/沙箱）与 L2（编排）**双向互斥**。青层反向依赖骨干层会使
  「隔离」名存实亡，故 `L2→L3` 与 `L3→L2` 都禁止。
- **前端 = 层次模型**：`L3（展示）→ L2（状态编排）→ L1（纯契约）` 是**严格向下的正常依赖**。
  组件读 store、store 调 composable 是该架构的常态，故前端**额外允许 `L3→L2`**；
  真正禁止的是 `L2→L3`（编排依赖 UI/沙箱）与 `L1→L2/L3`（纯逻辑依赖状态）。
- **前端 `entry` 的双重身份**：`store.ts`（7 个 store 的门面）与 `modals.ts`（弹窗注册表）是
  **被广泛引用的公共装配面**，故组件/composable 引用它们是**豁免**的——门面存在的意义就是
  让组件不必直接引 7 个 store。这与后端 `entry` 只作依赖发起方不同。

kedai 三层落点：
- **L1**：`parsing/`（角色卡 V2/V3、世界书、mvu 协议兼容解析、EJS 渲染契约）、`models/`（SQLite 表结构、types 契约）、
  `contracts/`（万花筒契约 DSL）、`migration/`（迁移幂等，决定老层经验能否跨版本延续）、`utils/`（基础纯函数）、
  **既有测试套件**（数量见 `MAINTENANCE.md`，是「传帮带」的第一载体）、SillyTavern 生态兼容承诺。
- **L2**：`agents/`（engine 编排、状态机、planner/reflector）、`services/`（角色/会话/世界书/注入/任务引擎/undo）、
  `api/`（路由/鉴权/SSE）、`connectors/`（LLM 后端适配）、`slash/`（命令系统）。
- **L3**：`scripts/`（rquickjs 沙箱，新模板能力的唯一合法落点）、`mcp/`（默认关）、
  `plugins/`（受控指令脚本，白名单求值器）、`services/exec/`（命令执行，默认关）、
  前端 `components/` 与 `sandbox/`。
- **`tools/` 的归属修正（2026-09-14，L3 → L2）**：`tools/` 曾按设计意图标为 L3，但按 §2.2 判据实测为 **L2**：
  ① P3 隔离性**不满足**——目录内无沙箱、无设置开关、无实验隔离，仅有 `ToolRegistry` 注册表，
  而注册表是 L2 骨干设施、不是 L3 的失败隔离手段；② P5 复用度**命中**——被 `agents`/`services`/`api`
  共 32 处复用，是**核心必需设施**（它失败则整个应用不可用），与 L3「失败必须被隔离」的语义相反。
  故原先登记的 5 条 tools 相关越代「债务」实为**归属画错**，已随本次修正全部消除。
  真正的 L3 隔离能力在其相邻模块：`scripts/`（rquickjs 沙箱）、`mcp/`（默认关）、`plugins/`（受控求值器）、
  `services/exec/`（默认关）。**教训**：不要用「名义上是 L3」为越代依赖辩护，见 §2.3。

### 2.6 L3 的冻结项：EJS 自研解释器（`parsing/assistant/ejs/`）

**只接受安全修复，新模板能力一律在 `scripts/runtime.rs` 的 rquickjs 沙箱侧实现**（rquickjs 自带
内存/中断/栈上限）。该解释器已加固「循环步数 + 墙钟预算 + 解析深度守卫」，但不再扩展——自研引擎缺
引擎级沙箱限额，继续加功能会扩大不可信输入的攻击面。能力面由规则 H 的**字面量条数 ratchet** 钉死
（只降不升）。详见 `MAINTENANCE.md §0`。

## 3. 每代际的允许/禁止出边与违例后果

| 代际 | 允许出边 | 禁止出边 | 违例后果 |
|---|---|---|---|
| L1 | `→L1` | `→L2` `→L3` `→entry` | 规则 D + J **硬 FAIL**，无登记豁免 |
| L2 | `→L1` `→L2` | `→L3` `→entry` | 规则 J FAIL；确无法消除须登记 `class: debt` |
| L3 | `→L1` `→L3` | `→L2` `→entry` | 规则 J FAIL；装配类可登记为 `class: wiring` |
| entry | 任意 | 无 | 不参与方向校验，但**必须登记**（规则 I） |

**`debt` 与 `wiring` 的区别**（登记时必须二选一）：
- `wiring` = 组合根/兼容桥的**正常接线，设计上接受**（如 `api→tools` 的工具注册表装配）；
- `debt` = **应还的债**，必须写明 `remediation`（收口路径）。
两者都**只减不增**：还清一条删一条，禁止为过检查而加条目。

## 4. 三种「结合」机制

### 4.1 传帮带 · 晋升通道（动态循环）
青层创新成熟 → 过晋升门槛 → 升入中层打磨 → 沉淀为老层契约。
**晋升门槛（三关）**：① 通过既有测试套件（经验库）；② 不破坏兼容协议；③ 经评审确认边界。
- 新能力一律先进 L3 验证（GENERATE/@INJECT/EJS API 即走此路）；
- 反例（禁止）：新代码直接改写 L1 契约而不带测试 → 破坏经验传承。

### 4.2 优势互补 · 边界
- **老层**：不可变契约，防青层误伤、防中层漂移；
- **中层**：翻译适配（V2/V3、新旧字段、协议转义），是「经验 → 实现」的桥梁；
- **青层**：隔离试探（沙箱/功能开关），防架构僵化。
三层缺一不可：全老 = 僵化不可演进；全新 = 失稳无锚点。

### 4.3 防断层 · 兼容承诺
- 兼容协议是「老层经验」的载体：演进可迁移、不破坏（数据迁移幂等、v3fix 重刷、SQLite 迁移）；
- 数据结构演进必须带迁移路径（如旧字段兼容解析、`serde(default)` 缺省）；
- 跨端协议（前后端 mvu）以协议文档锁定双端一致，防「代际交替」时行为漂移（见 `docs/mvu-protocol.md`）。

## 6. 代际流动规则与评审纪律

1. **改 L1**：先写失败测试 → 最小实现 → 声明兼容影响（`MAINTENANCE.md` 架构治理节）→ 评审；
2. **改 L2**：不得绕过 L1 契约直接改数据层语义；协议翻译集中在中层；
3. **进 L3**：新能力自由，但必须默认隔离（沙箱/开关/注册表），且纳入晋升跟踪；
4. **晋升**：L3 → L2：能力被 2 个以上调用点复用且测试覆盖；L2 → L1：协议稳定、外部依赖成型；
5. **Mutex/并发纪律**：禁止持 `std::sync::Mutex` guard 跨 `.await`（Clippy `await_holding_lock` 防护）；
   锁中毒一律恢复（`unwrap_or_else(|e| e.into_inner())`），不 panic；
6. **文档先行**：结构性改动先更新本文件或对应协议文档，再动代码（传帮带：先稳基座再动骨干）；
7. **代际变更须同步 SSOT**：新增/改名/删除顶层模块时，先更新 `arch-layers.json` 再动代码，
   否则规则 I 直接 FAIL（不静默放过）。

「传帮带」的门槛此前只有文字描述、无记录。登记每次代际晋升：

| 日期 | 能力/模块 | 代际变化 | 复用调用点 | 测试 | 评审要点 |
