## 2. 逐项要点

### P-1 + P-3 · SQLite 写路径

- 写连接补 `synchronous=NORMAL`、`temp_store=MEMORY`、`cache_size=-16000`。
- 只读池 `with_init` 补 `temp_store`/`cache_size`;池 `connection_timeout` 收到 5s。
- 启动收尾执行一次 `PRAGMA optimize`(失败仅留痕,不阻断启动)。

**取舍已显式记录在代码注释里**:WAL 下 `synchronous=NORMAL` 意味着掉电可能丢最近若干次
提交(最坏丢最后一条消息/状态),**但不损坏数据库**;本机单用户应用接受该权衡。
若需最强持久性,改回 `FULL` 是单行变更、无连带。

### P-2 · 静态资源缓存

`cache_control_for(target)` 分三档:`index.html` 恒 `no-store`(它是版本指针,语义不变);
`assets/*`(Vite content hash 命名)改 `public, max-age=31536000, immutable`;
其余固定名资源改 `max-age=3600`。

immutable 的安全性依据不是「内容不变」,而是「同一 URL 必对应同一内容」——hash 命名保证这点,
且 index.html 恒不缓存使新 hash 必然被引用。测试含一条**遍历内嵌 `web/dist` 取真实产物名**
的对拍,避免硬编码 hash 自说自话。

### P-4 · 运行时提示词读缓存

按 `(mtime, 长度)` 指纹缓存。三个正确性要点(均有对应用例):

1. 指纹含 mtime **与**长度,外部修改与删文件都会失效;
2. 本进程写入**主动**清缓存——Windows 时间戳约 15.6ms 粒度,同长度改写可能同 tick,
   只靠 mtime 会返回旧值(用例刻意不 sleep);
3. **旧文件指纹也进缓存键**——否则「首次读时新旧文件都不存在 → 缓存内置默认 → 用户之后
   放进旧文件但主文件指纹未变」会一直命中缓存,导致一次性迁移永不触发、提示词静默不生效。

### P-5 · Embedding 复用与批量

- reqwest Client 提为进程级 `OnceLock` 共享(构造点遍布热路径,`/api/memory` 甚至在循环内逐条新建)。
- 新增 `MemoryService::get_many`(一条 `IN (...)`、**保持入参顺序**、跳过缺项、空输入短路)。
- 蒸馏补向量:`逐条 get + 逐条 embed + 逐条 upsert` → `一次 get_many + 一次 embed(内部 32 分片)
  + 一次 upsert_vectors(单事务)`。
- `embed_one_entry` 不再接收调用方传入的 content,改按 id 读库,消除两个真值源。

**护栏判别力已实测**:临时退化为逐条嵌入后,`memory_embedding.rs` 断言失败并报
「实际 3 次,批大小 [1,1,1]」;恢复后通过。

### P-6 · 任务引擎落库让出 worker

- 新增 `utils/blocking.rs::park_worker`:**按 runtime flavor 分派**。multi-thread 的 worker
  走 `block_in_place`(交还调度核心);current_thread、spawn_blocking 线程、无 runtime 三种
  场景直接执行。
- `TaskService` 的 11 个写方法统一加 `Self::blocking(|| {...})` 包装;
  `record_self_heals` 不包(委托给已包装方法,包了只是多余嵌套)。

**为何不用 `spawn_blocking`**:落库调用散布在 6 个执行器 40+ 处且部分在同步辅助函数内,
改 async 会牵连调用点与顺序;`block_in_place` 让调用点保持同步签名而效果等价。

**为何必须探测 flavor**:`block_in_place` 在 current_thread runtime 下会 panic
(「can call blocking only when running on the multi-threaded runtime」),而本仓大量单测默认
就是 current_thread。这条由单测显式锁定。

### P-7 · `finalize_messages` 同步 IO

四处同步 IO 各包 `park_worker`:`save_session_vars`(写锁)、`runtime_prompt.read_optional()`
(文件读)、`memory.list` + `memory.get_vectors`(合并为一次让出);原先通道 2 内单独的
`get_vectors` 块随之删除(已并入同批,避免同批向量读两次)。

最终采用「让出」而非「数据前移」:本函数对顺序有硬要求(变量须在本轮消息构建之后、下发之前
落库),前移要改 `CollectedCtx`/`RunContext` 数据流与 `{{setvar}}` 展开时序,收益相同而风险更高。

## 4. 未做与已知缺口

- **未做 p95 前后对比**:`tools/perf-baseline.mjs` 需要服务在运行(`-Perf` opt-in),
  本次未启动服务,故**没有**端到端延迟数据。P-1/P-5/P-6 的收益方向明确,但幅度未经实测;
  建议在真实数据量下补测(尤其 P-1 的写入吞吐与 P-6 的并发读 p95)。
- **P-6/P-7 的集成用例不是判别性证明**:multi-thread 用例的价值是**防生产路径回归**
  (让出链路不破坏功能/事件完整性);在只读池不争写锁的场景下,即使不让出也可能通过。
  真正证明「必须让出」的是 `utils::blocking` 的单测(已实测判别力)。
- **`TaskService` 仍有少量同步落库不在包装内**(如 `list_*` 读方法走只读池,未包装):
  只读池无写锁竞争,风险低,故按「最小必要」只包装写方法。
- 前端项(P-8 首屏 chunk 反向耦合、P-9 虚拟滚动渲染缓存等)与 schema 变更(P-11)
  按用户范围决定**本轮不做**。
