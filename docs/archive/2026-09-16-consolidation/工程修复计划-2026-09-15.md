## 1. 执行纪律(本计划全程适用)

1. **每批次独立可交付、独立可回滚**;不跨批次顺手改别的东西(`AGENTS.md` 禁用项)。
2. **先写失败测试**(`AGENTS.md` 约定);新测试须经**变异测试**确认能捕获目标缺陷,
   避免「永远通过」的装饰性断言(方法学见报告 §3.4)。
3. **ratchet 只降不升**:改动 `tools/check-arch.mjs` 基线必须同步下调并记录前后值。
4. **数字同步**:测试数量以 `MAINTENANCE.md` 为唯一真值源,每次新增测试后跑
   `node tools/count-tests.mjs --check` 确认不漂移。
5. **`-j 2` 是必需参数**:默认并行度下 rustc 可能崩溃(`STATUS_STACK_BUFFER_OVERRUN`),
   报错伪装成「依赖 rlib 缺失」(报告 §6.1)。
6. **Git 提交按 `AGENTS.md`「Git 提交纪律」执行**(2026-09-15 修订:完成并验证后按体例提交,一逻辑批次一提交);
   需 exe 版时另跑 `.\build.ps1`(debug 通过 ≠ exe 已更新)。
7. **不可动的冻结点**:
   - `models/db/schema.rs` 的 `CREATE_TABLES` 静态文本(须与 `ddl.rs` 在 `normalize_sql` 后一致);
   - `SseEvent` / `TaskEventKind` 线格式值(`check-contract.mjs` 守卫);
   - EJS 能力面(规则 H 冻结,只降不升);
   - `/api/health` 的 `ok` 语义(桌面壳单实例判定依赖它,见批次 2.5);
   - SSE 重连算法(只加可观测信号,不改策略)。

**原因说明(为何遵守第 1 条)**:本仓已有「批次化 + 变更说明 + 核对表」的成熟体例,
照此执行可让每批次留下可追溯的对外契约。混批会让回滚粒度失效。

### 1.2 状态码正确性审计(A 揭示的问题类)

**A 暴露的不是孤例,而是一类**:错误体配 200 状态码,使前端按成功处理。

**做法**:检索全部 `Json(json!({ "error"` / `err_json` 出口,确认每个都显式设定了
非 2xx 状态;凡「返回错误体但状态为 200」的一律修正。

> **⚠️ 实测修正(2026-09-15,实施时核实)**:全仓扫描 `api/` 的 128 处错误体出口后,
> **除下述两处外全部已带非 2xx 状态码**，「错误体 + 200」并非普遍现象。
> - 真正的「错误体 + 200」只有 `api/static_files.rs:34,48`(目录穿越拒绝 / 头像不存在);
> - `api/resource.rs:108/116/140` **不是** 200——该文件各错误分支已配 `.with_status(400/500/502)`,
>   其真实问题是「第三种形状 `{ok:false,error}` 且无 `code`」;
> - 同族的 `api/settings.rs:766` 与 `api/plugins.rs:82` 亦属「第三种形状」,各自状态码为 200 / 400。

**已知同类形态(需一并判定)**:`api/resource.rs` 用的是
**`{ok: false, "error": ...}`**——与全局 `{error, code}` 约定是第三种形状。
处置:**已采纳方案 ②**(统一到 `{error, code}` + 真实状态码,`resource` 原状态码保留),
并同步改了前端消费点 `web/src/composables/useResourceFrames.ts`(改为按 HTTP 状态判成败)
与测试。`settings.rs:766`(embedding 测试)与 `plugins.rs:82`(插件加载)因 `ok:false`
承载**正常业务上报**语义,改为**保留原字段并补 `code`**,不改状态码——理由见变更说明 §2.1。

### 1.3 提取器与中间件拒绝统一为 JSON(P1)

**现状实测**:畸形 JSON → `400 text/plain`;40MB body → `413 text/plain`;
`DELETE /api/health` → `405` 空 body;未知 `/api/*` → `404 {"error":"Not Found"}`(JSON 但无 code)。

**做法**:

1. 在 `api/` 内新增薄包装 `JsonBody<T>`(实现 `FromRequest`,把 `Rejection` 映射为
   `{error, code: VALIDATION}` + 400)。**不新增第三方依赖**——`check-lock-sync.mjs` 对
   依赖变动敏感,且 axum 的 rejection 处理无需新 crate。
2. 按仓库既有「增量接入」节奏,优先接热门 handler(`chat` / `tasks` / `settings` /
   `characters`),并用 ratchet 防新增未接入点。
3. `Router::method_not_allowed_fallback`:405 返回 JSON + code。
4. 未知 `/api/*` 路径补 `code`(当前已是 JSON,只缺 code)。
5. **413(`DefaultBodyLimit`)属 axum 内建 rejection**,拦截成本较高——
   **本轮登记为已知例外并记录原因**,不强行改造。

### 1.4 前端形状闸门推广

**做法**:把 A 中 `web/src/api/diagnostics.ts` 的 `assertDiagnostics` 模式
(见报告 §3.3)推广到其它「`request<T>()` 返回值被直接解构」的 API 封装。

**理由**:可选链只能挡 `null`/`undefined`,挡不住「形状不对的真值对象」——
A 的 TypeError 正是这样产生的。形状闸门把「载荷不对」变成可捕获的 `Error`。

### 1.5 门禁基线下调

`tools/check-arch.mjs` 的 `BASELINE_BARE_ERROR` 从 **117** 下调至批次完成后的实际值,
并在变更说明记录「前 → 后」。**只降不升**。

**层序是关键(已复核 `api/mod.rs:109/113/116`)**:axum 的 `.layer()` 是**后加者在外层**,
故 request_id 必须注册在 `security::guard`(109)与 CORS(116)**之后**,
否则 401/403 等早退响应拿不到 requestId。

### 2.2 span 字段穿透 `PinoFormat`

`utils/logging.rs` 的 `PinoFormat` 目前**显式不输出 span**(源码注释:
「span 在本仓未使用」)。改为合并当前 span 作用域字段:

- 新增一个薄 `Layer` 实现 `on_new_span`,把 `request_id` 存为 **span extension**;
- `PinoFormat` 经 `FmtContext::event_scope()` 读 extension 合并进 JSON 行。

> **为何需要 `on_new_span` 而非单改格式化器**:`FormattedFields` 给的是**格式化后的字符串**,
> 不是结构化值;要拿到结构化 `requestId` 必须存 extension。这一点在 A 的
> 「原样透出 error 文案」需求上已有先例——形状保真需要显式设计。

**收益**:中间件把 `requestId` 挂到 span 后,请求生命周期内**所有日志(含 service 层)
自动携带**,无需逐处传参。这把「手工传 sessionId」升级为真传播。

**若该实现意外复杂**:退一步先只让**访问日志行与错误响应**携带 requestId,
把全链路 span 传播登记为后续项——**分阶段优于硬上**。

### 2.3 访问日志(当前完全缺失)

同一中间件内,请求结束打 1 行 INFO:`method / path / status / duration_ms / requestId`。

### 2.4 spawn 边界补 span

span 不跨 `tokio::spawn` 自动继承,需用 `.instrument(span)` 显式闭合两处:
`agents/engine` 的 run 入口、`services/task_service` 的执行器 spawn。
两处已手工传 `sessionId` / `task_id`,改为挂 span。

> **⚠️ 实测修正(2026-09-15,实施时核实)**:第二处的**物理位置**与本文措辞不符——
> `services/task_service/` 目录内**没有 `tokio::spawn`**,真实 spawn 在
> `services/task_engine/mod.rs`(由 `task_service/executor.rs` 的 `run_mode` 间接调用)。
> 落地时已在 `api/chat.rs`(引擎 run 入口)与 `services/task_engine/mod.rs` 两处各加
> `.instrument(run_span)`。

### 2.5 health 依赖探测(遵守契约)

**约束来源(已复核)**:`src-tauri/src/lib.rs:415-434` 的 `health_ok()` 以
`body.ok == true` 判定「已有实例在运行」,用于单实例复用与端口竞态处理。

> **⚠️ 实测修正(2026-09-15,实施时核实)**:`api/health.rs` **该文件不存在**——
> health handler 是 `api/mod.rs` 的 `build_router` 里**内联闭包**返回

## 批次 3 · 数据库版本与升级事务化

**目标**:兑现 `docs/known-limitations.md` 的 **L18**(无 `user_version`)与 **L21**(升级链无事务)。
方案出自 `docs/数据库版本与降级行为.md §四`,本批次落地其实测报告 §4.4 已再次实证的缺口。

### 改动

1. `models/db/schema.rs` 新增 `pub const SCHEMA_VERSION: i32 = 1;`
   (`0` 留给「从未写过版本」的旧库,与 SQLite 默认值天然区分)。
   **不动** `CREATE_TABLES` 静态文本(保持与 `ddl.rs` 的 `normalize_sql` 一致)。
2. `models/db/mod.rs:49-91` 的 `Db::open` 重构:
   - 建表批**之前**读 `PRAGMA user_version`;
   - `db_version > SCHEMA_VERSION` → 返回 `Err`,文案含两个版本号与处置建议
     (采纳文档 §4.2 推荐策略 1「拒绝启动 + 明确文案」);
   - 用 `BEGIN IMMEDIATE … COMMIT` 包住**建表批 + 9 个 `ensure_*`**,任一步失败整体回滚
     (SQLite 的 DDL 是事务性的);
   - `ensure_memory_entries_fts_backfill`(全表重建,大库代价高)与
     `backfill_scope_variables` **保持在提交之后**——二者由 `backfill_meta` 保证幂等,
     不进 DDL 事务可避免长写事务膨胀 WAL;
   - 全部成功后**最后**写 `user_version`(提前写会导致失败时误判「已最新」而跳过补迁)。
3. `migration/merge.rs`:两侧预补 DDL 后,把工作库与合并产物的 `user_version`
   置为 `SCHEMA_VERSION`;不满足时按既有风格保守停止。
4. `migration/ddl.rs`:**不改任何 DDL 文本**。

### 验收(文档 §四 7 条 + 本轮新增)

`server-rs/tests/schema_migration_meta.rs` 扩测:

1. 全新库 → `user_version == SCHEMA_VERSION`;
2. 冻结基线老库升级后 → 版本值正确且结构指纹与全新库一致(保留现有断言);
3. 伪造 `user_version = SCHEMA_VERSION + 1` → `Db::open` 返回 `Err`,文案含两个版本号;
4. 连续两次 `Db::open` 幂等,第二次不改版本、结构指纹不变;
5. 构造令某 `ensure_*` 失败的库 → `Err`,且库内 `user_version` **仍是旧值**、
   **schema 未被改动**(事务回滚断言,同时锁住 L21);
6. 合并产物 `user_version` 对齐;
7. 静态一致性:`schema.rs` 与 `ddl.rs` 文本 normalize 后仍一致。

### 风险与回滚

- 「库比代码新时拒绝启动」是**有意的兼容性变更**,须按仓库惯例在变更说明中登记。
  副作用:测试版/便携版共用库且一端为旧 exe 时,旧端直接打不开——**这是期望的更早暴露**。
- 无其它破坏性动作(不删列、不重命名),旧版 exe 仍可静默打开新库,回滚安全。

## 批次 6 · 日志容量与运行时调级

**前置**:依赖批次 2(同改 `utils/logging.rs`,须在 `PinoFormat` 定型后再动)。

### 6.1 容量上限

### 6.2 运行时调级

**做法**:增加运行时调整入口(端点或信号),并纳入安全白名单决策

**关键可执行断言(本计划新增)**

1. 畸形 JSON / 未知 API 路径 / 405 → 均为 `{error, code}` JSON(当前 400/413 是 `text/plain`);
2. 内部错误响应体**不含** `SQLite` / `no such column` / 盘符路径(泄露守卫);
3. 响应含 `X-Request-Id`(**含 401/403**),客户端传入 ID 被沿用;
4. 每个请求产生 1 行访问日志,请求内日志行含 `requestId`(当前 30+ 请求仅 2 行日志);
5. 全新库 `PRAGMA user_version == 1`;伪造更高版本 → 启动返回 `Err` 且文案含两版本号;
6. 某 `ensure_*` 失败 → 返回 `Err` 且用户库 `user_version` 未变、schema 未改(事务回滚);
7. `/api/health` 返回 `dependencies.db` 且 `ok` 语义未变;
8. 任务终态落库失败时产生 error 日志(不再静默停在 Running)。

## 环境侧备忘(摘自报告 §6)

| 现象 | 真实原因 | 处置 |
|---|---|---|
| `required to be available in rlib format` / `can't find crate for kedai_server` | 默认并行度下 **rustc 进程崩溃**(`0xc0000409 STATUS_STACK_BUFFER_OVERRUN`) | 降并发 `-j 2` 复跑,**不要改依赖** |
| `deps/` 里只有 `.rmeta` 无 `.rlib` | check/clippy 模式残留(实测 183 个) | 清理孤立 `.rmeta` 与对应 `.fingerprint/*-<hash>` |
| 集成测试目标报「找不到 rlib」 | 同上两者叠加 | 先清理残留,再 `-j 2` 复跑 |
