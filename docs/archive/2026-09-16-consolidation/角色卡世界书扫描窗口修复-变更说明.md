> 依据:用户 2026-09-14 反馈「吸血鬼角色卡修复之后**仍然**掉格式」。
> 前序记录:[0.3.0-A-beta-变更说明.md](0.3.0-A-beta-变更说明.md) §三(2026-09-13 首次修复)。
>
> 结论:**0.3.0-A-beta 的修复方向正确但不完整**。那次修的是「世界书未注入由
> character_id 缺失导致」与「输出被 max_tokens 截断」两条路径;本次实测证明
> 还存在**第三条**:世界书条目**解析出来了、character_id 也传对了**,但被
> **错误的扫描窗口**挡在门外,同样注入 0 条格式规范。

## 一、现场证据(本机真实数据)

`%APPDATA%\com.kedai.app\logs\kedai-2026-09-14.log` 的 generate-raw 调用记录:

```json
{"messages":3,"total_chars":20884,"msg":"generate_raw_call"}
{"character_id":"00b005fb-…","entries":54,"injected":17,"msg":"generate_raw_worldbook_inject"}
```

三个关键读数:

| 读数 | 含义 |
|---|---|
| `entries=54` | 角色卡内嵌世界书解析正常(干物吸血鬼少女卡,板板鸭 v2.1) |
| `character_id` 非空 | 角色 id 送达正常,注入流程**已进入** |
| `injected=17` | 注入 17 条——**恰好等于该卡的常驻(constant)条目总数** |

第 3 条是决定性的:带 `keys:["system log"]` 的**响应格式规范条目一条都没进**。
且本次调用**没有任何** `generate_raw_truncated_retry` / `still_truncated` 日志,
说明输出没被截断——**排除**了 09-13 修复覆盖的「未注入」与「被截断」两种情况。

## 二、根因:`depth` 与 `scanDepth` 语义混用

该卡权威数据(数据库实读,`characters.data_raw.character_book.entries`):

| 条目 | keys | `extensions.depth` | `extensions.scan_depth` | 内容长度 |
|---|---|---|---|---|
| `[INS]🔗响应格式🔗[FORMAT]` | `system log` | **1** | 缺省(无) | 6837 |
| `🔗故事编写🔗` | `system log` | **1** | 缺省(无) | 1095 |
| `[TMP]🔗响应格式🔗[FORMAT]` | `system log` | 1 | 缺省(无) | 6288(该条 `enabled=false`,本就应跳过) |

对照 SillyTavern 原版语义(`public/scripts/world-info.js`):

- `entry.depth` ↔ `originalData.extensions.depth`——是**插入深度**(`position=atDepth`
  即 `position=4` 时决定"插到倒数第几条"),**不是关键词扫描窗口**;
- 扫描窗口是**另一个字段** `entry.scanDepth` ↔ `extensions.scan_depth`
  (`get(entry)` 用 `entry.scanDepth ?? 全局扫描深度`,从不读 `depth`)。

**失误链条**:

1. 2026-09-12 的 F1 修复([实测四轮修复-变更说明.md](实测四轮修复-变更说明.md))
   为修赛马娘卡「关键词在窗口外仍命中」,给 `depth` 补了 `extensions` 回退,
   并把它**当作扫描窗口**用(`scan_depth_window = e.depth`)。对赛马娘卡是对的
   (那张卡的 `extensions.depth` 恰与作者预期窗口一致),但**语义张冠李戴**。
2. 吸血鬼卡格式条目 `extensions.depth=1` 因此被当成「只扫最近 1 条消息」。
3. 作者页(`v2.1.html` 的 `Bk`/`ph` 函数)把整段 `<chat_history>` **压成一条
   user 消息**发出,而触发词 `system log` 只出现在该消息**开头的注释行**
   `/* system log(IGNORE the line): … */`——它落在窗口第 1 条,而窗口只剩最后
   1 条(尾部的 `<user_input>` 那条)→ **永不命中**。
4. 格式规范不注入 → 模型自由发挥 → 卡片 `$y.extract()` 多重回退全失败
   → 弹「布豪!丢格式了!😭」。

## 三、修复

### 3.1 `scan_depth` 独立成字段(语义归位)

| 文件 | 改动 |
|---|---|
| `parsing/world_book.rs` | `WorldEntry` 新增 `scan_depth: Option<i64>`(预留 None = 未声明);解析兼容 `scan_depth` / `scanDepth` / `extensions.scan_depth`;**不再**用 `depth` 顶替 |
| `parsing/world_book.rs` | `depth` 的文档注释更正为「插入深度(position=atDepth 用),不是扫描窗口」 |
| `parsing/world_book.rs` | 新增共享纯函数 `scan_window_len(e, texts_len, fallback)`:scan_depth 优先、未声明用调用方兜底、`<=0` 表示全部、按可用条数封顶 |

### 3.2 两条路径各自取正确口径(收敛到共享函数)

| 路径 | 窗口取值 | 理由 |
|---|---|---|
| `api/chat.rs::inject_worldbook_for_raw`(卡片生成) | `scan_window_len(e, len, **0**)` = 未声明则**扫全部** | 作者页自组的是**扁平完整上下文**,不存在"最近聊天"概念;触发词可能出现在被压平的历史里 |
| `agents/engine/worldbook.rs`(角色扮演主引擎) | `scan_window_len(e, len, e.depth)` = 未声明则**沿用 depth 兜底** | 保持赛马娘卡等存量卡行为**逐字节不变**(引擎扫的是真实聊天历史,depth 兜底是既有约定) |

两个调用点收敛到同一个 `scan_window_len`,避免再次各自抄一份、口径漂移。

### 3.3 顺带修复:编辑保存会抹掉 `extensions`(让本修复不白做)

`view_to_value` 的注释写着「未改动的 extensions 保留」,但
`merge_entries_into` 实际是**整体替换条目对象**——而 `extensions` 里的
`depth` / `scan_depth` / `role` 都**不在**前端 `WorldBookEntry` 视图里,
于是任何一次条目编辑保存都会静默抹掉它们,退化成缺省值,世界书触发行为随之改变
(编辑一次 → 本修复失效)。

| 改动 | 内容 |
|---|---|
| `merge_entries_into` | 改为**字段叠加**(`overlay_view`):视图字段覆盖到原始条目对象上,未承载的键(`extensions`、作者自定义键)原样保留;数组形态同样按 uid 叠加 |
| `view_to_value` | `regex` / `role` 在视图为空时写显式 `null`(叠加语义下,不写就会让用户清空后的旧值"复活");`keysecondary` 与 `secondary_keys` 两侧同写,避免原始键残留成"影子值"被优先读到 |

> 注:前端视图本次**未**新增 `scan_depth` 编辑项(超出「修掉格式」范围)。
> 叠加语义保证该字段在编辑后不丢;UI 暴露列入后续候选。

## 五、兼容性

- **不改 API 线格式**:`generate-raw` 请求/响应不变;`WorldBookEntryView` 未加字段。
- **不改 DB schema**。
- **引擎侧行为不变**:真实卡片(`scan_depth` 均为缺省)→ 窗口仍为 depth 兜底,
  赛马娘卡等存量卡触发行为与修复前完全一致。
- **卡片生成侧行为变更(有意)**:未声明 `scanDepth` 的条目由「按 depth 收窄」
  改为「扫全部」。对作者页自组上下文这是唯一正确口径;若某卡确实想要窄窗口,
  应在 ST 里用 `scanDepth` 显式声明(本实现已支持)。
- **编辑保存语义更保守**:不再抹掉 `extensions`。此前保存过世界书的卡,
  若其 `extensions` 已被抹掉,需要重新导入卡片恢复(本机该卡数据实测完好)。

## 六、诊断口径更新

卡片再报「丢格式」时,按以下顺序看 `%APPDATA%\com.kedai.app\logs\kedai-*.log`
(或前端 `kedai.tavern-call-log`):

| 现象 | 读数 | 含义 |
|---|---|---|
| 未进入注入流程 | 无 `generate_raw_worldbook_inject` | 桥没调到后端 / 请求被拒 |
| 注入 0 条 | `injected=0` + `entries=N` | 触发词未命中(本次修复的场景)或条目全 disabled |
| 缺角色 id | `generate_raw_without_character_id` | 前端未传 `character_id` |
| 输出被截断 | `generate_raw_truncated_retry` / `still_truncated` | 预算不足,见 09-13 修复 |

**本次修复后**,本机该卡的正常读数应为 `entries=54, injected=19`。
