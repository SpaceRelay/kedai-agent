## 3. 修复项(A):`/api/diagnostics/cache` 三缺陷叠加

### 3.1 缺陷与复现

修复前的实测响应(隔离实例,无 `session_id`):

```http
GET /api/diagnostics/cache?window=20 HTTP/1.1
→ 200 OK
{"error":"读取缓存统计失败: Wrong number of parameters passed to query. Got 1, needed 2"}
```

三个缺陷叠加成一条完整的用户可见故障链:

| # | 缺陷 | 位置 | 后果 |
|---|---|---|---|
| 1 | SQL 参数序号错位:无会话分支的 SQL 写 `LIMIT ?2`,但只绑定 1 个参数 | `api/diagnostics.rs`(旧 32-40 行 + 旧 69 行) | 该分支**恒定失败** |
| 2 | 失败却返回 **200 OK**,并携带原始 SQLite 文案 | 同上(旧 55/65/78/29 行) | 前端按成功处理;内部细节直达用户 |
| 3 | 前端 `data.value?.totals.hit_rate` 的可选链只保护了 `data.value` | `components/CacheHealthPanel.vue:44` | `{error}` 是真值对象 → 取 `.totals` 得 `undefined` → `.hit_rate` 抛 TypeError |

**用户可见路径**:`components/OptimizeModal.vue:233` 使用的是 `<CacheHealthPanel />`,
**不传 `sessionId`**——即缺陷 1 的分支正是前端默认路径。换句话说,优化面板的缓存健康区
在当时是**必然打不开的**。

### 3.2 为何全绿测试没有拦住

这是本报告最值得记录的部分。三个环节各自「看起来没问题」:

1. **后端集成测试**永远带 `session_id`(`tests/api_integration.rs` 的两处调用
   `?session_id={sid}` / `?session_id={sid}&window=1`),无参分支**从未被执行**。
2. **前端单测**用 `status: 500` 模拟失败路径,而后端该路径**实际返回 200**——
   mock 与实现不一致,恰好绕开了缺陷。
3. **前端组件测试**注入的是格式正确的样例数据,不经过真实响应形状。

结论:**「测试全绿」在这次给出的信号是假的**。根因不是某个测试写错,
而是缺少「mock 契约与后端实现对齐」这一层护栏(见 §7)。

### 3.3 修复处置

| 文件 | 改动 |
|---|---|
| `server-rs/src/api/diagnostics.rs` | 两条 SQL 提为常量 `SQL_ALL_SESSIONS` / `SQL_BY_SESSION`,各自注释参数序号;无会话分支改用 `LIMIT ?1`;两个分支合并为单一 `rusqlite::Result` 出口;失败改走 `err_with_code(ErrorCode::Db, "读取缓存统计失败", 500)`,原始错误经 `tracing::error!(error = %e)` 只进日志 |
| `server-rs/tests/api_integration.rs:2150` | 新增 `diagnostics_cache_without_session_id_returns_all_sessions`:锁定「200 + `totals`/`entries`/`watermark` 结构完整 + 无 `error` 字段」 |
| `web/src/api/diagnostics.ts:69` | 新增 `assertDiagnostics` 形状闸门:载荷缺 `totals`/`entries`/`watermark` 即抛错,并透出后端 `error` 原文 |
| `web/src/api/diagnostics.test.ts:78` | 新增两例:200 携带 `{error}`、200 但结构缺失——均要求抛错而非透传 |

**修复后实测**(同一隔离实例,插入 2 条真实 `llm_requests` 后):

```http
GET /api/diagnostics/cache?window=20     → 200 {"cost":0.011351, "totals":{...}, "entries":[2 条], ...}
GET /api/diagnostics/cache?session_id=s-demo → 200 count:2 hit_rate:0.65 cost:0.011351
GET /api/diagnostics/cache?session_id=ghost  → 200 count:0(空统计,非报错)
```

### 3.4 变异测试:确认新测试有效

为避免「新测试只是装饰」,临时把 `SQL_ALL_SESSIONS` 改回 `LIMIT ?2` 复现原缺陷:

```
diagnostics_cache_without_session_id_returns_all_sessions ... FAILED
  assertion failed: 无 session_id 应正常返回: {"code":"DB","error":"读取缓存统计失败"}
  left: 500  right: 200

diagnostics_cache_reports_hit_rate_and_pricing ... ok   ← 既有测试依然通过
```

两侧信息都有价值:新测试**捕获**了缺陷,既有测试**依然通过**——正好印证 §3.2 的
「既有测试存在覆盖盲区」判断。同时错误体已变为 `{"code":"DB","error":"读取缓存统计失败"}`,
不再泄露 SQL 细节。验证后已还原。

### 4.1 错误响应普遍缺 `code`(P1)

对 15 个 GET 端点做错误形状普查,**全部无 `code` 字段**,含典型 404:

```
/api/tasks/ghost-id     → {"error":"任务不存在"}          ← 无 code
/api/memory             → {"error":"缺少 character_id"}    ← 无 code
/api/undo/ghost-session → {"error":"Not Found"}            ← 无 code
/api/characters         → {"error":"Not Found"}            ← 无 code
```

`check-arch.mjs` 规则 G 实测裸 `{error}` **112 处**(基线 117;本次修复降至 112)。
影响是双向的:前端 `client.ts` 的遮蔽只对**带 code** 的错误生效,
于是「不该透传的一侧透传了」(见 4.2)。

### 4.2 提取器与中间件拒绝未统一为 JSON(P1)

```http
POST /api/chat/sessions  畸形 JSON  → 400 + text/plain
     "Failed to parse the request body as JSON: key must be a string at line 1 column 2"
POST /api/chat/sessions  40MB body  → 413 + text/plain
DELETE /api/health                  → 405 + 空 body
Origin 不受信任                      → 403 + {"error":"Origin 不受信任"}(无 code)
缺少 bearer token                    → 401 + {"error":...,"code":"UNAUTHORIZED"}(合规)
未知 /api/* 路径                     → 404 + {"error":"Not Found"}(JSON,但无 code)
```

即:鉴权出口合规,但**提取器拒绝(400/413/405)返回 `text/plain`**,
与「统一 JSON 错误体」的承诺不符。根因是全仓无 `JsonRejection` / `QueryRejection` /
`handle_error` / `method_not_allowed_fallback`。

### 4.3 可观测性:零访问日志、零关联 ID(P1)

以隔离实例发出 30+ 请求(含多个错误请求)后,日志文件**全文如下**(共 2 行):

```json
{"msg":"Kedai server starting", ...}
{"msg":"Kedai 已启动", ...}
```

```
含 requestId/traceId 行数  : 0
含 GET/POST 访问记录行数    : 0
```

静态检索同样确认三项结构性缺失:

| 检索项 | 命中 |
|---|---|
| `request_id\|requestId\|X-Request-Id`(仓内全量) | **0** |
| `instrument\|span!`(server-rs/src) | **0** |
| HTTP 访问日志中间件(`TraceLayer`;`tower-http` 未启 `trace` feature) | **无** |

**约束(实测确认,防止后续改动踩坑)**:`src-tauri/src/lib.rs` 的 `health_ok()`
以 `body.ok == true` 判定「已有实例在运行」,用于单实例复用与端口竞态处理。
故 `/api/health` 的 `ok` **必须保持 liveness 语义**;补依赖探测应新增字段
(如 `dependencies.db`)而非改变 `ok` 含义。

### 4.4 数据库无 schema 版本号(P2,L18 实证)

系统 `sqlite3` 直读探针实例的库文件:

```
user_version = 0          ← 与 SQLite 默认值相同,无法区分「从未标记」与「版本 0」
journal_mode = wal
table 数量   = 37
迁移台账表    = (无,查 sqlite_master 中 LIKE '%migration%' / '%schema%' 为空)
```

`user_version` 全仓静态检索 **0 命中**,与 `known-limitations.md` L18 一致。
补充实证了 L18 的两条推论:① 无法判断「库被哪个版本写过」;
② 既有幂等 `ensure_*` 是唯一升级手段(无版本可比对)。

## 5. 实测确认的既有设计(正面结论)

以下几条经实测**确认成立**,不是缺陷,记录以免后续被误改:

1. **鉴权出口形状合规**:缺 token 返回 `401 + {"error":..., "code":"UNAUTHORIZED"}`。

5. **迁移链幂等**:探针实例首次启动即建成 37 张表,`ensure_*` 全部通过。

## 6. 环境侧发现(与产品代码无关,但会误导排查)

### 6.1 默认并行度下 rustc 自身崩溃

首次 `cargo test`(默认并行)失败,输出为一组**看起来像代码问题**的错误:

```
error: crate `aho_corasick` required to be available in rlib format, but was not found in this form
error[E0463]: can't find crate for `kedai_server`
error: could not compile `kedai-server` (test "assistant") due to 1 previous error
```

真实根因在日志末尾:

```
rustc.exe ... (exit code: 0xc0000409, STATUS_STACK_BUFFER_OVERRUN)
```

**是编译器进程被终止**,不是代码错误。改用 `-j 2` 后一次通过、0 编译错误。
项目 `tools/check-all.ps1` 的 `cargo test --workspace -j 2` 已带此参数,
其注释记录了同类现象(「本机并行链接曾撞页面文件不足,限并发换稳定」),
但**该规避只覆盖 `check-all.ps1` 内部**;直接调用裸 `cargo test` 仍会撞上。

> **建议**:`AGENTS.md`「验证命令」节的 `cargo test` 补 `-j 2`,
> 并在 `MAINTENANCE.md` 记录「默认并行度下 rustc 可能崩溃,表现为依赖 rlib 缺失;
> 见到 `required to be available in rlib format` 先降并发,别改依赖」。

### 6.2 `deps/` 残留 183 个孤立 `.rmeta`

`server-rs\target\debug\deps` 中存在**只有 `.rmeta`、没有同名 `.rlib`** 的产物
(实测 183 个),属于 check/clippy 模式留下的完整一套。它们是 §6.1 报错中
「找不到 rlib」的直接来源。清理孤立 `.rmeta` 及其 `.fingerprint/*-<hash>` 后,
编译恢复正常。

> 处置:已清理。此类残留会随 `cargo check` / `cargo clippy` 与 `cargo test`
> 交替执行而累积,建议纳入「构建异常排查」清单。

## 7. 测试体系盲区(建议新增护栏)

**核心问题**:前端单测 mock 的 HTTP 状态码可以与后端实现**不一致**,
而没有任何机制发现它。§3.2 的 P0 据此存活。

**具体案例**:`web/src/api/diagnostics.test.ts` 原用 `status: 500` 模拟
「后端统计失败」,但后端该路径当时实际返回 **200**。

**建议护栏**(三选一或组合,归入后续批次评估):

1. **契约化 mock**:前端 mock 的状态码/错误体形状从单一位置声明,
   并在注释中标注对应的后端源码位置(轻量、无新增依赖)。
2. **新增后端负路径测试**:凡 handler 有错误分支,集成测试必须至少覆盖一次
   并断言真实状态码(本例即缺此覆盖)。
3. **前端形状闸门**:凡 `request<T>()` 的返回被直接解构的 API 封装,
   加运行时形状校验(§3.3 的 `assertDiagnostics` 即此模式的首例)。

> 其中 **2** 收益最大且不需新机制:它把「后端错误分支是否被真实执行过」
> 变成可检查的事实,而当前 112 处裸 `{error}` 中大部分从未被测试触达。
