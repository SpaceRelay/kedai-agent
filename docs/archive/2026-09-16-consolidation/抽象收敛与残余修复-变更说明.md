## 一、4.1 四份截断重试合一(纯重构,行为不变)

**背景**:「截断(`finish_reason=length`)→ 预算翻倍 + 封顶」的同一算法此前有四份实现,封顶与触发条件各异,任一路径调口径不会同步。

| 路径 | 位置 | 封顶 | 触发条件 |
|---|---|---|---|
| 卡片生成 generate-raw | `api/chat.rs::generate_raw_heal_budget` | 32768 | `length` 且 `rounds < 2` |
| 引擎单轮自愈 | `agents/engine/executor.rs::doubled_heal_budget` | 8192 | 外层 `truncation_heal_cause` 已判定(空正文/半截 tool_call) |
| team 审计/终审/汇总 | `services/task_engine/team.rs::trunc_heal_budget` | 65536 | `length`,单次 |
| 步骤/汇总空输出重试 | `services/task_service/executor.rs::retry_if_empty_output` | 65536 | 空输出;`length` 走翻倍分支,其余走 temperature=0.7,封顶后仍同预算重试 |

**改动**:新增 `server-rs/src/utils/retry.rs`(挂 `utils/mod.rs`),两个纯函数:

- `doubled_heal_budget(current, cap) -> Option<u32>`:翻倍并封顶(`saturating_mul` 防溢出);结果未超过 current(已达/超上限、current=0)返回 `None`,表示重发无意义。
- `truncation_heal_budget(reason, used, rounds, cap, max_rounds) -> Option<u32>`:仅 `reason == Some("length")` 且 `rounds < max_rounds` 时委托前者。

四路径改为**薄封装**调用共享函数,各自保留封顶常量、轮次与场景依据注释,原单测继续断言薄封装(封顶值仍被测试锁定):

- `chat.rs`:cap=32768、max_rounds=2(旧 `used < CAP` 条件由「未增长即 None」等价覆盖);
- `executor.rs`:cap=8192(触发语义仍由 `truncation_heal_cause` 判定,未动);
- `team.rs`:cap=65536、max_rounds=1;
- `task_service/executor.rs`:新增薄封装 `truncated_retry_budget`,cap 命中时回退原预算(`unwrap_or`),保住「封顶后同预算仍重试一次」的兜底语义。

**等价性证据**:四处原单测全绿 + `utils::retry` 新增 7 例 + `task_service` 新增 1 例;`tests/generate_raw.rs` 的 mock 钩子链路(`[[trunc_text:]]`/`[[trunc_fail:]]`)仍绿。两处已知且**不可达**的差异已写进调用点注释:

1. `used == 0`:旧实现返回 `Some(0)`,新实现 `None`——实际预算经 `generate_raw_budget` 恒 ≥1、引擎/team 预算恒 ≥1;
2. `task_service` 的 `default_max_tokens > 65536`:旧实现缩小到 65536,新实现保持原值——设置 API 校验区间 `1..=65536` 挡死(单测显式锁定该分支)。

## 二、3.7 用量统计事务化(`agents/engine/run_finish.rs`)

- `record_usage_sync` 的 `session_usage` upsert 与 `global_usage` update 包进**同一事务**:开事务/两条 SQL/commit 任一步失败即回滚并 `tracing::warn!`。此前两条独立提交且 `let _ =` 吞错,第二条失败会留下「会话已加、全局未加」的永久偏差且无日志。
- `record_usage` 的 `spawn_blocking` JoinError 由 `let _ =` 改为 warn 留痕(线程池关闭/任务 panic 不再静默丢用量)。
- 新增 2 例测试:`record_usage_sync_rolls_back_when_global_update_fails`(DROP `global_usage` 后调用,断言 `session_usage` 零新增 = 真回滚;已先用旧实现验证该用例 FAIL)、`record_usage_sync_keeps_session_and_global_in_step`(两次落库后两侧 delta 相等)。

## 三、3.1 消息删除的 message 作用域变量孤儿清理(`services/session_service.rs`)

- `scope_variables` 的 message 行(`scope='message'`、`scope_id`=消息 id 文本)无 FK 级联,消息删除后成孤儿(此前只有**会话删除**路径清理)。新增私有助手 `cleanup_message_scope_variables`,在**删 messages 之前**按同一子查询口径清理。
- 三处删除路径接入:`delete_message`(API `DELETE /api/chat/messages/{id}`;`undo_service` 回退亦复用)、`truncate_messages_after`(编辑用户消息后重发截断)、`clear_messages`(清空;`import_chat` 复用,导入后消息 id 重分配,旧变量按旧 id 存续即为永久孤儿)。
- 边界:只清 `scope='message'`(chat 等其它作用域不受影响);不牵连 `undo_snapshots`/`kaleido_changelog`(属会话删除,见 `cleanup_dependent_rows_before_delete`);失败只 warn 不阻断消息删除,方法签名与返回语义不变。
- 新增 3 例测试:单条删除只清自身(同会话其它消息与 chat 作用域保留)、截断清 anchor 之后(anchor 自身保留)、清空仅限本会话(其它会话保留)。
