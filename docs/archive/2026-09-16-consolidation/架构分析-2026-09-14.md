## 1. 架构全景

### 1.1 系统形态

三层物理结构，通过 HTTP + SSE 连接：

| 层 | 技术 | 位置 | 规模 | 职责 |
|---|---|---|---|---|
| 桌面壳 | Tauri 2 | `src-tauri/` | 5 个 `.rs` | 窗口、侧车进程管理、便携版组装 |
| 后端 | Rust / axum | `server-rs/` | 218 文件 / 72,839 行 | 数据、解析、编排、Agent 与任务引擎、LLM 连接器 |
| 前端 | Vue 3 / TS | `web/` | 223 文件 / 26,824 行(非测试) | UI、状态编排、角色卡脚本沙箱 |

运行时数据目录解析顺序：`DATA_DIR` 环境变量 > `%APPDATA%\com.kedai.app\data\` > 项目根 `data\`
（`server-rs/src/config.rs`）。**产品运行时提示词与开发提示词严格分离**：开发 agent 读仓库根
`AGENTS.md`，产品运行时主 Agent 提示词在 `DATA_DIR/AGENTS_RUNTIME.md`（见 `AGENTS.md` 开篇），
这是一条被明确写死的隔离，避免把开发指令注入聊天模型。

### 1.2 四代际（3 + 1）

三结合是**三层 + 一个组合根**，共 4 个桶。这一点在旧叙事里不够醒目，本次明确：

| 代际 | 别名 | 判据（一句话） | 对应的护栏规则 |
|---|---|---|---|
| **L1 老层 · 稳** | Anchored Core / 基石层 | 承载**兼容契约**：形状一变即破坏既有用户数据或外部生态，且自身不依赖任何上层 | I / J（+ D 专项） |
| **L2 中层 · 干** | Orchestration / 骨干层 | 依赖 L1 完成**业务流程**，自身不被 L1 感知 | J（+ C 专项） |
| **L3 青层 · 活** | Frontier / 探索层 | **失败被隔离**（沙箱/开关/注册表），不反向定义上层语义 | J（+ H 专项） |
| **entry 入口 · 装配** | Composition Root | 只做**拼装与配置解析**，不承载业务语义 | I（并按约定豁免方向校验） |

`entry` 不是「第四层」，而是组合根：它**被允许依赖一切**（`tools/check-arch.mjs:588` 的
`if (from === 'entry') continue` 与 `:654` 的前端同名豁免）。这条豁免常被误读成「根文件无需归属」，
实际规则 I 要求根文件**必须登记**、只是不参与 J 的方向校验——**登记与豁免是两件事**。

## 2. 「三结合」含义的彻底明确化

现有 `docs/ARCHITECTURE-3H.md` 的叙述是**比喻性**的（「老带中青」「压舱石」「活水」），
可读但不足以裁决实际争议。本节把比喻**降维成判据**，同时保留原有术语（不改名、不弃用）。

### 2.1 精确含义（保留原术语，补精确释义）

| 原术语 | 精确释义 |
|---|---|
| 老层 · 稳 / Anchored Core | **兼容契约的持有者**。判据不是「老」而是「契约性」：其形状被外部生态（SillyTavern 角色卡/世界书/正则脚本/酒馆助手协议）或既有用户数据依赖。 |
| 中层 · 干 / Orchestration | **协议翻译与业务流程的承担者**。它的存在理由是把 L1 的稳定形状翻译成当前业务需要的形状（V2/V3、新旧字段、注入合成）。 |
| 青层 · 活 / Frontier | **失败必须被隔离的探索区**。判据不是「新」而是「隔离性」：沙箱、设置开关、注册表三者至少有一。 |
| 传帮带 | **测试套件即经验库**。晋升（L3→L2→L1）的门槛是「过既有测试 + 不破坏兼容协议 + 评审确认边界」。 |
| 优势互补 · 边界 | 三层缺一不可：全 L1 = 僵化不可演进；全 L3 = 失稳无锚点。**边界就是对 `use` 方向的约束**。 |
| 防断层 · 兼容承诺 | 数据结构演进必须带迁移路径（SQLite 迁移幂等、`serde(default)` 缺省、旧字段兼容解析）。 |
| 动态循环 · 晋升 | L3 能力被 ≥2 个调用点复用且测试覆盖 → 升 L2；协议稳定、外部依赖成型 → 升 L1。 |

### 2.2 代际判定程序（新增，用于裁决争议）

旧叙事最大的缺口是**没有可操作的判定步骤**，导致 `tools/` 这类模块长期卡在「名义 L3 / 实测 L2」。
本次补入 5 条判据，按顺序适用，先命中先定：

- **P1 契约性**：改动是否会破坏外部生态兼容或既有用户数据？是 → **L1**。
- **P2 依赖方向**：是否存在指向 L2 或 L3 的出边？是 → **不可能是 L1**。
- **P3 隔离性**：失败是否被沙箱 / 设置开关 / 注册表三者之一隔离？否 → **不可能是 L3**。
- **P4 装配性**：是否只做拼装与配置解析、不承载业务语义？是 → **entry**。
- **P5 复用度**：被 ≥2 个调用点复用的业务逻辑 → **L2**；仅直接服务用户交互 → **L3**。

**名义代际 vs 实测代际的裁决规则**（本次新增的核心纪律）：

> 名义代际由设计意图决定，实测代际由依赖图决定。两者不一致时，**以实测为准，并把差异登记为债务**
> （`arch-layers.json` 的 `registeredEdges`）。**不允许**用「名义上是 L3」为越代依赖辩护。
> 规则 J 已经把这套裁决机器化，本判据只是让人和机器用同一把尺子。

按此程序裁决 `tools/`：它同时存在 `→services`（P2 违反、P3 不满足），因此**实测代际为 L2**；
拆分为 L2 设施与 L3 沙箱两条路径的完整方案见 **§5**。

### 2.3 每代的纪律与违例后果（收紧为可判定表述）

| 代际 | 允许的出边 | 禁止的出边 | 违例后果 |
|---|---|---|---|
| L1 | `→L1` | `→L2` `→L3` `→entry` | 规则 D + J **硬 FAIL**，无登记豁免 |
| L2 | `→L1` `→L2` | `→L3` `→entry` | 规则 J FAIL；确无法消除须登记 `class: debt` |
| L3 | `→L1` `→L3` | `→L2` `→entry` | 规则 J FAIL；装配类可登记为 `class: wiring` |
| entry | 任意 | 无 | 不参与方向校验，但**必须登记**（规则 I） |

`debt` 与 `wiring` 的区分是明确化的重要一环：`wiring` 表示「组合根/兼容桥的正常接线，设计上接受」，
`debt` 表示「应还的债」。当前 **10 条后端登记边 = 6 条 `debt` + 4 条 `wiring`**；前端 1 条 `debt`。
其中 **5 条 `debt` 与 `tools` 相关**（唯一例外是 `mcp → services`），这正是 §4.5 判定「tools 归属画错」的量化依据。

### 2.4 需要修正的三处术语冲突（明确化的代价）

1. **单一代际 vs 混合标签**：`ARCHITECTURE-3H.md:105` 把 `web/src/mvu/` 标为「L1+L3」，
   而 `arch-layers.json:130` 只允许单一 `L1`，规则 I/J 也按单值判定。
   → **明确化结论**：代际是**单值**；模块内若有两种纪律，**按子目录拆分**（如 `mvu/protocol/` 与
   `mvu/host/`），而不是给模块贴双标签。
2. **「legacy 仍驻 task_service」**（`ARCHITECTURE-3H.md:99`）与代码事实相反：

## 5. `tools/` 层归属修正与依赖倒置（本节已执行，2026-09-14）

> **本节结论已落地**。原本这里规划的「三步走拆分」在执行中被一个更根本的发现取代：
> **`tools/` 的代际画错了，不是代码写错了**。下面记录最终采取的处置与理由。

### 5.0 最终结论：名义 L3 → 实测 L2（归属修正，非结构拆分）

按 §2.2 的判定程序逐条过筛 `tools/`：

| 判据 | 检查 | 结果 |
|---|---|---|
| P3 隔离性 | 目录内是否有沙箱 / 设置开关 / 实验隔离？ | **不满足**：无沙箱、无开关；仅有 `ToolRegistry` 注册表，而注册表是 L2 骨干设施，不是「失败隔离」手段 |
| P5 复用度 | 被多少调用点复用？ | **命中 L2**：被 `agents`/`services`/`api` 共 **32 处**复用；它失败则整个应用不可用——与 L3「失败必须被隔离」语义**相反** |

**判定**：`tools/` 实测为 **L2**。原先登记的 5 条「tools 相关越代债务」（`agents→tools`、`services→tools`、
`tools→services`、`tools→agents`、`tools→connectors`）实为**归属画错产生的伪债务**——
`tools` 作为 L2 设施被 L2/L3 合理依赖，这些边**天然合法**，已随归属修正全部消除（不是靠豁免掩盖）。

**真正的 L3 隔离能力**在相邻模块，各自都有隔离手段（不需要动）：

| 模块 | 隔离手段 |
|---|---|
| `scripts/` | rquickjs 独立 Runtime + 64MB 内存上限 + 1s 中断 + 5s 墙钟 + 单轮 32 脚本上限 |
| `mcp/` | `mcp_enabled` 默认关 + 仅启动装配 + 工具名前缀 + 未知工具默认 Dangerous |
| `plugins/` | 白名单递归下降求值器（不使用 eval）+ 文件名净化 + 工具级授权裁决 |
| `services/exec/` | `exec_enabled` 默认关 + 四道闸 + 命令级硬门 + 审计 |

### 5.1 同时完成的两项词汇/契约下沉（L3 依赖倒置的配套）

归属修正之外，为让 `plugins/` 与 `mcp/` **不再依赖 L2**（它们确是 L3），做了这些下沉：

| 内容 | 从 | 到 | 消除的边 |
|---|---|---|---|
| `AuthorizationMode` / `ToolRisk` / `CommandRisk` | `tools/permissions.rs`、`tools/command_risk.rs` | `models/tool_policy.rs`（L1） | `services→tools`（settings/audit 两处） |
| `ToolOrigin` | `tools/action_class.rs` | `models/tool_policy.rs`（L1） | 供 `plugins`/`mcp` 标注来源 |
| `McpServerConfig` | `services/settings_service/params.rs` | `models/tool_policy.rs`（L1） | **`mcp→services`**（完全消除） |
| `ToolExecutor` 类型别名 | `tools/registry.rs` | `models/types.rs`（L1） | 供 `plugins`/`mcp` 构造执行器 |
| `ToolRegistrar` 窄接口（**新增**） | — | `models/types.rs`（L1） | 供 `mcp` 经注入注册工具，替代直接持有 `ToolRegistry` |

**`plugins/` 的依赖倒置**：`ToolPluginLoader` 从「解析 + 注册」改为**纯解析**（`parse_all`/`parse_file`
返回 `LoadedToolPlugin`），注册动作移到组合根（`api/plugins.rs::register_plugins` + `app_state.rs`），
并为 `mcp` 提供 `plugin_executor()` 工厂。L3 加载器不再 `use crate::tools::`。

### 5.2 效果（门禁实测）

- 后端越代边：**10 条 → 3 条**（且这 3 条全为 `wiring` 装配点/兼容桥）；
- 后端 `debt` 类债务：**6 条 → 0 条**；
- 全仓越代债务（含前端）：**13 条 → 5 条**；
- `tools` 目录内 `use crate::services` 的 16 处与 `use crate::agents` 的 3 处**不再计为违规**
  （因其为 L2 设施读业务数据，方向合法）；`plugins`/`mcp` 对 L2 的依赖**真实消除**。
- 后端测试：**1022 通过 / 0 失败**（新增 `ToolRegistrar` 契约与词汇线格式冻结测试）。

> 目标：把 `tools/` 从「名义 L3、实测 L2」的模糊态，变成归属清晰、方向合规的结构。

### 5.3 历史记录：原「三步走拆分」方案（已被上面的归属修正取代）

> 以下为**执行前的规划原文**，保留作决策溯源。它假设 `tools` 名义 L3 正确、需拆结构；
> 实际执行中发现真正的问题是**归属画错**（见 §5.0），故「设施转 L2 + 宿主注入」这些
> 结构手术**不必要**——把 `tools` 正确标为 L2 后，那些边本就合法。
> 唯一采纳的是其中的「词汇/契约下沉」（即上面 §5.1 的实际完成项）。

原方案要点（存档）：

- **反面约束（仍然成立且被采纳）**：不能只把 `tools` 改成 L2 就完事——`plugins(L3) → tools`
