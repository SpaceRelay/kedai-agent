## 一、现状

> **2026-09-15 已变更**:本节的 1.1 / 1.3 / 1.4 描述的是**引入版本号之前**的现状。
> 新增的现实:`models/db/schema.rs` 现有 `pub const SCHEMA_VERSION: i32 = 1`(0 留给
> 「从未标记」的旧库);`Db::open` 在建表批**之前**读 `PRAGMA user_version`,库版本高于
> 应用即 `Err`;建表批 + 9 个 `ensure_*` 已用 `BEGIN IMMEDIATE … COMMIT` 包裹,
> 失败统一 `ROLLBACK`(`ensure_memory_entries_fts_backfill` 与 `backfill_scope_variables`
> 仍留在提交之后);全部成功后才**最后**写 `user_version`。
> 故 1.1 的「代码零引用 `user_version`」与 1.4 的「升级链不是单一事务」**均已不成立**。

### 1.1 没有 schema 版本号,也没有迁移台账(**2026-09-15 起前半句已不成立**)

- **2026-09-15 前**:全仓搜索 `user_version` 只命中残余计划 6.2 一处,**代码零引用**:数据库文件的
  `PRAGMA user_version` 始终是 SQLite 默认值 `0`。
  **2026-09-15 起**:已引入 `SCHEMA_VERSION`(见本节开头标注),`user_version` 由 `Db::open` 读写。
- 没有版本记录表(如 `schema_migrations` / `migration_history`)。`backfill_meta`
  (`server-rs/src/models/db/schema.rs:366`)不是迁移台账:它只存两件事——FTS 回填标记
  `memory_fts_rebuilt` 与 message 作用域回填游标 `message_scope_last_id`
  (`server-rs/src/migration/ddl.rs:314`、`server-rs/src/models/db/backfill.rs:19-24`)。
  **这一点至今未变**(本轮只加了单值的 `user_version`,未建台账表)。
- **2026-09-15 前**:因此**无法在启动时判断「这个库是哪个版本建的/被哪个版本写过」**,也无法判断
  「库比当前代码新还是旧」。
  **2026-09-15 起**:以单值 `user_version` 与 `SCHEMA_VERSION` 比较即可判「库比代码新」并拒绝启动。

### 1.2 升级靠幂等 DDL(schema 只增不改)

升级不靠版本比较,而靠「缺什么补什么」的幂等 DDL,分两层:

1. **全量建表**:`Db::open` 每轮启动都执行 `CREATE TABLE IF NOT EXISTS` 建表批
   (`server-rs/src/models/db/mod.rs:62`,SQL 常量在 `schema.rs` 的 `CREATE_TABLES`,
   共 30 张表 + FTS 虚拟表 + 索引)。已存在的表原样跳过,不比对、不改写。
2. **增量 `ensure_*`**:对无法用 `CREATE TABLE IF NOT EXISTS` 触达的「已有表补列 / 补表 /
   补索引」,逐个函数探测后补齐(`server-rs/src/migration/ddl.rs`):
   - 补列:`PRAGMA table_info(<表>)` 读现存列名 → 缺失才 `ALTER TABLE ... ADD COLUMN`
     (`ensure_llm_requests_usage_columns:69`、`ensure_skills_progressive_columns:107`、
     `ensure_tasks_task_mode_column:135`、`ensure_task_llm_calls_finish_reason_column:171`、
     `ensure_memory_entries_pinned_column:286`)。列一律追加在**表尾**,且带常量默认值
     (如 `task_mode TEXT NOT NULL DEFAULT 'legacy'`),旧行零迁移成本。
   - 补表:`PRAGMA table_info` 探测不到列(表不存在返回零行)才建
     (`ensure_task_messages_table:358`、`ensure_exec_audit_table:406`,DDL 全 `IF NOT EXISTS`)。
   - 补索引:`CREATE INDEX IF NOT EXISTS`(`ensure_perf_indexes:425`)。
   - 一次性回填:`ensure_memory_entries_fts_backfill:313` 用 `backfill_meta` 标记保证
     `rebuild` 只跑一次(全表重建代价高,不进热启动路径)。

   **不变式(跨库合并依赖)**:这些补列/补表/补索引的文本必须与 `schema.rs` 的
   `CREATE_TABLES` 在 `normalize_sql` 后逐字节一致,否则跨库合并的 schema 比对会判冲突
   (`server-rs/src/migration/merge.rs:264`)。新增/改动索引时 `ddl.rs` 与 `schema.rs`
   两处都要改。

### 1.3 执行时机与顺序

全部发生在 `Db::open` 内部(`server-rs/src/models/db/mod.rs:49`),即**进程装配期、监听端口之前**:

| 步骤 | 内容 | 位置 |
|---|---|---|
| 1 | 注册 sqlite-vec 扩展、建数据目录、打开写连接 | `mod.rs:51-55` |
| 2 | `journal_mode=WAL`、`foreign_keys=ON`、`busy_timeout=5s` | `mod.rs:56-61` |
| 3 | `CREATE TABLE IF NOT EXISTS` 全量建表批 | `mod.rs:62` |
| 4 | 8 个 `ensure_*` 按固定顺序补列/补表/补索引 | `mod.rs:65-87` |
| 5 | FTS 一次性回填 + scope_variables 幂等回填 | `mod.rs:89-91` |
| 6 | 建只读连接池 | `mod.rs:93-109` |

顺序为:`llm_requests usage 列 → skills 渐进披露列 → tasks.task_mode →
task_llm_calls.finish_reason → task_messages 表 → memory_entries.pinned →
exec_audit 表 → 性能索引 → FTS 回填 → scope_variables 回填`。

### 1.4 失败处理:启动失败即退出,不留半可用状态

- 任何一步返回 `Err`,`Db::open` 即返回 `Err`;`AppState::new` 用 `?` 上抛
  (`server-rs/src/api/app_state.rs:113-116`);`run_server` 再包成
  `初始化失败: <细节>`(`server-rs/src/lib.rs:99-102`)。
- 命令行版:打印 `[错误] ...` 后 `std::process::exit(1)`(`server-rs/src/main.rs:19-22`)。
- 桌面版:启动阶段收到后端 Err 后弹错误并退出,错误文本会落到
  `%APPDATA%\com.kedai.app\logs\tauri-start-error.log`(`src-tauri/src/lib.rs:339-380`、
  `:739-740` 的错误提示文案)。
- **升级链不是单一事务(2026-09-15 起已不成立)**:原 `Db::open` 没有用事务把整条链包起来,
  建表批与各 `ensure_*` 的 DDL 各自提交。**2026-09-15 起**:建表批 + 9 个 `ensure_*` 已用
  `BEGIN IMMEDIATE … COMMIT` 包裹,任一步失败统一 `ROLLBACK`,**不会**留下「部分升级」的
  中间态;`ensure_memory_entries_fts_backfill` 与 `backfill_scope_variables` 仍留在提交之后
  (二者靠 `backfill_meta` 幂等,不进长事务以避免膨胀 WAL)。
  回滚断言见 `tests/schema_migration_meta.rs` 的
  `failed_ensure_rolls_back_whole_upgrade_chain_and_keeps_version`。

### 1.5 元测试与冻结基线的护栏作用

- `server-rs/tests/schema_migration_meta.rs` 的做法:用冻结基线
  `tests/fixtures/schema_baseline_v0_3_0_beta.sql` 建一个「老库」→ 跑 `Db::open`
  (真实启动路径,执行全部 `ensure_*`)→ 另建全新库 → **逐表比对结构指纹**
  (`PRAGMA table_info` 的列名/类型/NOT NULL/默认值/主键 + `PRAGMA index_list` 的索引清单),
  两侧必须完全一致(`schema_migration_meta.rs:78-125`)。
- 作用:防「`schema.rs` 加了列/表/索引却忘了写 `ensure_*`」——这种 bug 只在老用户机器上
  以 `no such column` 炸,新装机与其它全量测试都发现不了(踩坑记录见
  `MAINTENANCE.md:458-461`)。
- **纪律:不要更新基线文件**。它是 0.3.0-beta 发布时的 `CREATE_TABLES` 历史快照
  (`schema_baseline_v0_3_0_beta.sql:1-4`),更新它等于关掉守卫。
- **覆盖边界(重要,别高估)**:基线快照已经包含当前绝大部分表/列(实测:基线 30 张表
  与当前一致,仅差 `idx_sessions_character`/`idx_tasks_character`/`idx_tasks_status`
  三个性能索引)。因此**从基线建出的「老库」升级后能与新库一致,主要靠 `ensure_perf_indexes`**;
  其余 `ensure_*` 对应的列/表在基线里已存在,该测试**当前并没有实际锻炼到它们**——
  它们的价值是拦住**基线之后新增**的结构。此外基线只有 0.3.0-beta 一个版本,
  **早于 0.3.0-beta 的库没有 fixture 覆盖**,只能靠代码上的 `ensure_*` 兜底。

### 1.6 「三处迁移逻辑」里只有一处是 schema 迁移

残余计划 §五登记的「三处迁移并存」指的是下面三种,职责不同:**只有第 3 种动 schema**。

| # | 位置 | 做什么 | 是否动 schema |
|---|---|---|---|
| 1 | `launcher/src/main.rs:251`(启动器,`main:708` 调用) | 命令行版 `<root>\data` → 桌面版 `%APPDATA%\com.kedai.app\data` 的**整目录搬迁**;交互确认、目标非空则不动、覆盖前备份、先清陈旧 `-wal`/`-shm`;头像绝对路径借系统 `sqlite3` 改写(无 `sqlite3` 则如实报告不修) | 否(只搬运文件) |
| 2 | `src-tauri/src/lib.rs:474`(桌面壳,`#[cfg(desktop)]`) | 项目 `data` → `%APPDATA%` 的**首启搬迁**,仅在目标 pristine 时执行;用 SQLite Online Backup API 生成一致性快照(`snapshot_database`,`server-rs/src/migration/backup.rs:7`),写 `.migration-v1` 标记,源目录保留 | 否(整库快照) |
| 3 | `server-rs/src/migration/`(`ddl.rs`/`merge.rs`/`backup.rs`/`conflict.rs`) | **schema 幂等升级**(§1.2)、跨库合并(§2.5)、快照备份 | 是 |

- 三者**不会互相冲突**:1/2 各自有「目标非空则跳过」的门槛(启动器 `looks_pristine`,
  `launcher/src/main.rs:368-370`;桌面壳 `target_is_pristine`,`src-tauri/src/lib.rs:510-527`),
  且搬迁的是整库快照/文件,不解析也不改写表结构。收敛方向见残余计划 §五(收敛为 server-rs
  单一实现,注意 launcher 零依赖约束)。
- 副作用:1/2 留下的是**两份数据**(源目录不删 + 目标目录新拷贝),这正是 §三「双库分叉」
  的成因。

## 二、行为矩阵

先给结论速查,再逐场景展开。

| 场景 | 会发生什么 | 用户/开发者该怎么办 |
|---|---|---|
| 旧库 → 新版(升) | 启动时幂等补齐;当前全部为「只增」变更,预期无痛 | 直接升级;升级前手动备份 `kedai.db` |
| 新版库 → 旧版(降) | 无版本门禁,旧版**静默打开**;多余表/列被忽略,预期能跑 | 无官方回滚路径;要回退必须先备份 |
| 桌面 + Android 双端 | 两个**物理隔离**的库,互不可见 | 用导入/导出或 `kedai-data-merge` 手工合并 |
| 测试版 + 便携版 | 同一 `%APPDATA%` 库 + 同一端口 | 勿同时运行;二者抢库会互相阻塞 |
| 项目 `data\` + `%APPDATA%` | 可能长期并存两份库(双库分叉) | 用合并工具;别再手动各写一边 |
| 双库合并 | CLI 工具;schema 冲突/缺表时**停止并保留两份原数据** | 先让两端都升到同版本再合 |

### 2.1 旧库 → 新版(升级)

- **会发生什么**:`Db::open` 跑建表批 + `ensure_*`,缺的列/表/索引补齐(§1.2);
  schema 变化至今全部是**追加**(新增表、表尾加列、加索引),没有重命名或删除列。
  补列带常量默认值,旧数据行的新列取默认值(如 `tasks.task_mode='legacy'`、
  `task_llm_calls.finish_reason=''`、`memory_entries.pinned=0`)。
- **失败时**:应用启动即失败退出(§1.4),不会带着半残 schema 继续服务。
- **该怎么办**:
  1. 升级前**手动复制一份 `kedai.db`(连同 `-wal`/`-shm`,或先关应用使其 checkpoint)**
     ——当前没有「升级前自动备份」这一步,**这是目前唯一的回滚手段**。
  2. 升级失败看启动错误文本与 `tauri-start-error.log`;修掉原因后重启即可续补(幂等)。
- **推断**:`scope_variables` 回填是增量的、FTS `rebuild` 只跑一次,大库升级耗时主要在
  首次 FTS rebuild;重复启动不会重复付这个代价。

### 2.2 新版库 → 旧版(降级)

- **会发生什么**:因无 `user_version` 门禁,旧版 exe **不会察觉库更新,直接打开**。
  - 多余的表:`CREATE TABLE IF NOT EXISTS` 原样跳过,旧代码不引用即无影响。
  - 多余的列:旧代码的查询多按显式列名取列,不认识的列不参与;旧代码 `INSERT` 不写这些列时
    走常量默认值。**推断**:因此能正常读写。
  - 缺列:当前 schema 只增不减,**旧代码需要的列在新库都存在**,不存在「缺列」问题;
    真正会断的是未来引入「重命名列/删除列/改类型或约束」之后——那时旧版会在运行时
    报 `no such column` 或读到语义错位的数据。
  - 新增 trigger(如 `memory_entries_*` FTS 触发器):SQLite 自动执行,旧代码不感知,
    但若**旧版本对相关表的结构假设与新 trigger 不兼容**,属未验证区(推断:现阶段无不兼容)。
- **该怎么办**:项目**没有官方降级/回滚路径**。要回退到旧版,只能:
  1. 关闭应用;
  2. 用升级前的手工备份覆盖 `kedai.db`;
  3. 再启动旧版。
  若已用新版写入过数据,这些数据在回退后丢失。**不要假设「装回旧版 exe 就能无损降级」。**
- **风险管理**:§四的 `user_version` 检查就是为了让这条「静默打开」变成**显式提示**。

### 2.3 桌面端 + Android 端

- **会发生什么**:两个**物理隔离、各自独立**的库,不存在共享:
  - Windows 桌面(便携版/`Kedai.exe` 桌面壳,以及被其复用数据目录的测试版):
    `app_data_dir()` = `%APPDATA%\com.kedai.app`,再 `.join("data")`
    (`src-tauri/src/lib.rs:176`;identifier `com.kedai.app` 见 `src-tauri/tauri.conf.json:5`),
    即 `%APPDATA%\com.kedai.app\data\kedai.db`。桌面壳启动时把该路径注入
    `DATA_DIR`(`src-tauri/src/lib.rs:188`)。
  - Android:`app_data_dir()` 映射到应用私有目录 `/data/data/<pkg>/files`
    (`src-tauri/src/lib.rs:170-171`,注释明示),无 `%APPDATA%`,解析失败直接报错退出
    (`:74-80`)。
- **该怎么办**:两端数据不自动同步。需要在两端之间搬运时,走应用的会话/数据导入导出,
  或把一端的 `kedai.db` 取回后用 `kedai-data-merge` 合并(§2.5)。
- **注意**:Android 端 `Db::open` 的升级路径与桌面完全相同(同一 `kedai_server` crate),
  所以「旧库→新版」的 §2.1 结论在 Android 上同样成立,只是失败日志位置不同。

### 2.4 测试版与便携版共用同一库

- **会发生什么**:`start.ps1` 默认启动测试版(`dist\kedai-server.exe`,浏览器模式),
  便携版是 `dist\Kedai-portable\Kedai.exe`(Tauri 桌面壳)。两者**共用端口 3001 与同一数据
  目录**(`MAINTENANCE.md:220`,原文「两版共用端口 3001 与同一数据目录,勿同时运行」)。
- **数据目录解析(测试版为何也会落到 `%APPDATA%`)**:`AppConfig::from_env`
  的顺序是 `DATA_DIR` 环境变量 > 用户级统一目录 > 项目根 `data\`
  (`server-rs/src/config.rs:138-144`)。其中用户级目录
  `%APPDATA%\com.kedai.app\data` **仅在该目录已含用户数据时才被采用**
  (`canonical_user_data_dir`,`config.rs:73-83`;判据 `dir_has_user_data:85-105`:
  存在 `settings.json`,或库里有非内置角色/任何会话)。桌面版则**无条件**指向
  `%APPDATA%`(§2.3)。
- **后果**:桌面版用过的机器上,测试版随后启动会命中「已有用户数据」→ 也切到 `%APPDATA%`,
  两版即共用同一库,**同一时刻只能跑一个**(第二个实例要么被健康检查判定为「已在运行」
  而复用,要么抢端口/抢写锁)。
- **该怎么办**:开发迭代时明确「同时只跑一端」;切换版本前先关掉另一端的进程。

### 2.5 项目 `data\` 与 `%APPDATA%` 双库分叉与合并

- **会发生什么(双库分叉)**:在桌面版从未用过的机器上先跑测试版,它会用项目根 `data\`
  建库;之后跑桌面版会把项目数据**拷贝**(非移动)到 `%APPDATA%`,源目录保留
  (§1.6)。于是磁盘上出现两份库。此后测试版若再启动,会因 `%APPDATA%` 已有用户数据而切过去,
  但项目 `data\` 里那份旧库仍在,可能与新库内容分叉。
- **手工合并工具**:`server-rs/src/bin/kedai-data-merge.rs`,用法
  `kedai-data-merge <基线数据目录> <源数据目录> <工作目录>`(`:9-12`),
  入口是 `migration::merge_data_dirs`(`server-rs/src/migration/merge.rs:54`)。
  注意这是**离线 CLI**,需要显式传三个目录,**不删源数据**、产出写在工作目录。
- **合并时的 schema 行为**:合并前会对基线库与源快照**各补一遍 `ensure_*` + 新增表 DDL**
  (`merge.rs:177-251`),把两侧拉到同款 schema 再比对,因此「旧库 vs 新库」合并通常不会
  因新增表/列失败。若仍出现:
  - `表 <T> 的 schema 冲突,已停止合并并保留两份原数据`(`merge.rs:264-267`);
  - `基线缺少源表 <T>,已停止合并并保留两份原数据`(`merge.rs:269-270`)。

  都是**保守停止**,不会写坏任何一侧;解决方式是把两端都升级到**同一版本**再合。
- **该怎么办**:合并前对两份库各做一次备份;合并失败时按报错表名定位是「哪端版本旧」。

## 三、已知风险与不支持项

> **2026-09-15 已变更**:第 1 / 4 / 6 条已由批次 3 处理,下方逐条标注现状;
> 第 2 / 3 / 5 / 7 / 8 条**仍然成立**。

1. **无官方降级/回滚路径**(**部分已变更**):仍没有 down 迁移(不 `DROP COLUMN`、不重建表),
   降级仍依赖用户自己的备份(已登记为 [known-limitations.md](known-limitations.md) L25「有意不做」)。
   **但「无『库版本 > 代码版本』检测」已不成立**:批次 3 起 `Db::open` 会在建表批前读取
   `user_version`,库比代码新时**拒绝启动**并给出两个版本号(把静默继续改为启动点显式失败)。
2. **升级前不自动备份**:`Db::open` 的升级链没有任何前置快照。唯一自动快照
   (`snapshot_database`)只服务于**跨目录搬迁**(§1.6 第 2 种)与**合并**,
   **不服务于 schema 升级**。(**仍未变**;本轮把「库比代码新」变显式,但未加自动备份。)
3. **降级正确性未被测试锁定**:§2.2 的「旧代码能跑」是推断,没有「新库 + 旧 exe」的
   回归测试(也不现实,旧 exe 不在仓库)。一旦引入重命名/删除列,降级会静默损坏。
4. **`user_version` 缺失导致无法诊断**(**已变更**):原指排查「用户库怎么长这样」时无库内标记可读,
   只能靠结构指纹反推。**批次 3 起 `user_version` 已是可读标记**,`= SCHEMA_VERSION` 时
   即可判定「库由本代或更新的代码写过」。
5. **元测试只覆盖 0.3.0-beta 之后的漂移**(§1.5):早于该版本的库无 fixture;
   且基线已含当前绝大多数结构,当前真正被该测试锻炼的是新增的三个性能索引。
6. **升级链非原子**(**已修复**):原「失败可停在部分升级的中间态」已由 `BEGIN IMMEDIATE …
   COMMIT` 事务包裹消除;失败即整体回滚,`user_version` 保持旧值(否则下次启动会误判「已最新」)。
7. **双库/多库并存无自动检测**:§2.4、§2.5 的分叉只有一个**手动** CLI 合并工具,
   没有启动期「检测到另一套库」的提示(桌面壳只在「复用运行中实例」时校验数据目录,
   见 `src-tauri/src/lib.rs:359`,不覆盖多份库并存的情况)。
8. **schema 是事实上的版本契约,却只写在代码里**:每个 `ensure_*` 的默认值语义
   (如 `task_mode='legacy'` 的含义)散在注释中,没有集中清单。

## 四、已兑现方案(历史索引):引入 `PRAGMA user_version` 的最小方案

> **状态(2026-09-15)**:本节原为**设计稿**,现已在批次 3 **完整落地**,保留作为
> 「为什么这样设计」的历史索引。落地实况与验收证据见
> [工程韧性修复-变更说明.md](工程韧性修复-变更说明.md) §2.3。
> 与下方原文的差异只有一处:实际包进事务的是「建表批 + 9 个 `ensure_*`」,
> 而 `ensure_memory_entries_fts_backfill` 与 `backfill_scope_variables` **有意留在提交之后**
> (避免长写事务膨胀 WAL;二者靠 `backfill_meta` 幂等)。


### 4.1 最小实现

1. **定义单一版本常量**:在 `server-rs/src/models/db/schema.rs`(或 `mod.rs`)加
   `pub const SCHEMA_VERSION: i32 = 1;`,并导出;`0` 保留给「未标记的旧库/未知」
   (与 SQLite 默认值一致,天然区分「从未写过版本」)。
2. **启动时读取并分流**(`Db::open`,在建表批之前):
   - `db_version > SCHEMA_VERSION` → 库比代码新,进入 §4.2 的策略分支;
   - 否则(含 `0`)→ 照常跑建表批 + 全部 `ensure_*` + 回填(**保持每轮幂等执行**,
     不因版本相等而跳过;这样可自愈「部分升级」的中间态,见 §1.4);
   - 全部成功后再写 `PRAGMA user_version = SCHEMA_VERSION`。
3. **写入时机**:必须在所有 `ensure_*` 与回填**成功之后**写;否则失败时版本被提前抬高,
   下次启动会误判为「已最新」而跳过补迁。
4. **合并路径对齐**:`merge_databases` 的两侧预补 DDL 之后,把工作库(及合并产物)的
   `user_version` 设为 `SCHEMA_VERSION`;不满足时按合并既有风格保守停止。
5. **不改 `CREATE_TABLES` 的静态文本**:`user_version` 是连接级 `PRAGMA`,不进建表 SQL,
   对 `normalize_sql` 比对与元测试零影响。

### 4.2 「库版本 > 代码版本」时的显式提示策略(需主智能体决策)

三选一,推荐第 1 种(与现有「升级失败即退出、宁可明确报错」的纪律一致):

1. **拒绝启动 + 明确文案(推荐)**:`Db::open` 返回 `Err`,
   文案含「数据库由更新版本的 Kedai 写入(库 vX > 应用支持 vY);请升级应用,
   或从升级前备份恢复」。桌面版会弹错误并写 `tauri-start-error.log`;
   命令行版 `exit(1)`。优点:杜绝旧代码写坏新库;代价:同机降级会直接打不开。
2. **警告但继续**:仅 `tracing::warn!` + 控制台提示,照常启动。优点:不阻断;
   代价:旧代码仍可能写坏新库数据。
3. **拒绝启动 + 引导用合并/备份恢复**:在文案里再给出 `kedai-data-merge` 与备份路径提示。

> 推荐策略下要同步评估:测试版与便携版**共用库**场景,若一端是新版、另一端是旧版 exe,
> 旧端会直接打不开(比现在的静默打开更早暴露问题,符合预期)。

### 4.3 验收断言建议

在 `server-rs/tests/schema_migration_meta.rs` 扩测,至少覆盖:

1. **全新库**:`Db::open` 后 `PRAGMA user_version == SCHEMA_VERSION`。
2. **旧库(冻结基线,`user_version=0`)**:`Db::open` 后 `user_version == SCHEMA_VERSION`,
   且结构指纹与全新库一致(现有断言保留)。
3. **伪造「更新的库」**:在临时库上 `PRAGMA user_version = SCHEMA_VERSION + 1` 后调
   `Db::open`,断言返回 `Err` 且错误文案含两个版本号(按 §4.2 选定策略调整);
   若选策略 2 则断言「成功打开且输出了警告」(需可观测点,如返回的告警字段或日志钩子)。
4. **幂等**:连续两次 `Db::open`,第二次不改动 `user_version`、结构指纹不变。
5. **失败不抬版本**:构造一个会让某个 `ensure_*` 失败的库(如手工建一张同名列型不兼容的表),
   断言 `Db::open` 失败后文件的 `user_version` 仍是旧值(证明 §4.1 第 3 条)。
6. **合并后对齐**:合并产物的 `user_version == SCHEMA_VERSION`。
7. **静态一致性**:沿用现有「`schema.rs` 与 `ddl.rs` 文本 normalize 后一致」的护栏,
   新增表/列时仍必须同步 `ensure_*`(`MAINTENANCE.md:458-461` 纪律不放松)。
