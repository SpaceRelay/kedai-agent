## 二、任务模式加入命令执行(bash)能力

**问题**:`bash` 在权限矩阵里风险恒为 `Dangerous`(`tools/permissions.rs::default_risk`),
任务模式默认策略 `deny_dangerous` 按风险级一刀切过滤,导致 bash **整个工具**不下发——
任务模式连 `ls`/`echo` 都用不了。用户要求任务模式具备 bash 能力。

**改动**(按工具名开例外,不放宽风险级):

| 文件 | 改动 |
|---|---|
| `server-rs/src/services/task_engine/tool_policy.rs` | `compile()` 的 `deny_dangerous` 分支放行 `bash`;新增 `deny_dangerous_bash_exception_does_not_leak_to_other_dangerous` 测试,原测试补 bash 断言 |
| `server-rs/src/tools/bash.rs` | 安全模型注释与工具描述同步(「任务模式此类命令不可用」→「高危命令不可用,普通命令可用」) |
| `web/src/components/settings/AndroidExecSection.vue` | 面板文案同步 |
| `docs/授权模式.md` | 三·五节工具级说明 + 任务模式策略表加 bash 例外 |
| `docs/任务引擎六模式.md` | 工具可用性矩阵前言 |
| `docs/命令执行层与Android三档执行器-变更说明.md` | 修正「不进任务模式默认集合」的旧表述 |
| `web/src/api/types.ts` | `task_tool_policy` 注释同步 |

**安全边界(关键)**:「下发工具」≠「放行危险命令」。`permissions::check` 的**命令级硬门
排在任何自动放行之前**(`tools/permissions.rs` 有专项注释与 2026-09-13 冒烟实测记录):

- `destructive` / `admin` 命令(删除、格式化、提权、包管理…)在任务模式下**直接拒绝**
  ——无 UI 确认通道,不「假装问过」;
- `safe` / `sensitive` 命令经任务白名单授权(`custom_authorized`)放行;
- 仍受 `exec_enabled` 总开关(默认 **false**)约束,关闭时一律拒绝并留审计。

即:任务模式的 bash 只能执行普通命令,高危命令的硬门未动。

## 三、Android 真机吸血鬼卡「掉格式」(掉格式 = 生成 JSON 被截断)

**截图现象**:卡片自检弹出「布豪!丢格式了!😭」,叙事原文被当纯文本逐段显示。

### 根因(实测证据链)

1. 该卡(`干物吸血鬼少女与夜间工作` v3 卡,PNG 内嵌 54 条世界书)要求模型
   「**整个回复有且仅有一个 JSON**」——该规范是**世界书触发条目**
   `[INS]🔗响应格式🔗[FORMAT]`(6837 字符,`keys:["system log"]`),由
   `generate-raw` 的世界书匹配注入交给模型。
2. 卡片自带解析器(`v2.1.html` 内 `$y.extract()`):多重回退(`tryParse` →
   `extractFromCodeBlocks` → `robustParse` → `fieldBoundaryCapture` →
   `precisionCapture`)全失败时返回 `{parseFailed: true}`,界面即报「丢格式」。
   **被 `max_tokens` 截断的 JSON 必然走到此分支**——这不是 WebView/CSS 渲染问题。
3. **Android 首装默认 `default_max_tokens = 1024`**(出处:`server-rs/src/config.rs:142-145`
   读环境 `DEFAULT_MAX_TOKENS`、缺省兜底 1024,经 `services/settings_service/params.rs:383-390`
   的 `from_config` 传递;桌面用户数据里是 10000)。该卡完整响应需 `thinking` + `self_check` + `context`
   (`rii_story` 正文)+ `character_state` 等字段,常达数千 token,1024 必然腰斩。
   模拟器实测截图(`kedai-android/artifacts/ui-fix-03-genparams.jpg`)确认「最大生成长度
   = 1024」。
4. 前端桥接始终不传 `max_tokens`(`useResourceFrames.ts`),故必然落到该默认值。

### 修复(三层)

| 层 | 落点 | 行为 |
|---|---|---|
| 预算下限 | `chat.rs::generate_raw_budget` | 未显式指定时取「用户设置 vs `GENERATE_RAW_MIN_TOKENS=8192`」的较大者;作者页显式指定则尊重之(不擅自抬高) |
| 截断自愈 | `chat.rs::generate_raw_heal_budget` | `finish_reason=length` 时预算翻倍重发,封顶 32768,最多 2 次;重发失败则回退上一次的半截产出(不把可读的半截变成整体报错) |
| 诊断可见 | `chat.rs` 日志 + `useResourceFrames.ts` | 注入 0 条、缺 `character_id`、截断重试、自愈用尽、重发失败回退均留日志;前端把后端 `injected` / 产出长度写入 `kedai.tavern-call-log` |

**为何不直接改全局默认 1024**:普通聊天的 `default_max_tokens` 是用户可见设置,语义是
「用户想要的回复长度」;卡片生成是「必须完整的结构化对象」,截断即等于失败,二者诉求不同。
故只给 `generate-raw` 路径专属下限,不动用户设置语义。

**诊断指引**(卡片再报丢格式时):查 `kedai.tavern-call-log` 或日志
`generate_raw_*` 字段——`injected=0` 表示世界书未注入(角色 id 未送达/条目未命中),
`chars` 偏小表示被截断;两种情况日志已可区分。
