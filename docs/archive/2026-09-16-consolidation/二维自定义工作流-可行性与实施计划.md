# 二维自定义工作流:可行性与实施计划

> 状态:分析稿(未开工)。范围:把现有「一维自定义 Agent 流程」升级为类 ComfyUI 的
> 二维节点图,并补齐节点级配置、严格/宽松节点、强制/对比选择机制、多套 API 与多套流程的
> 存储与导出。
> 代码锚点以 `file:line` 给出,行号基于 2026-09-15 的 `main`。

## 一、结论速览

方向**合理**,与既有架构演进方向一致(`ModeExecutor` / `TaskBackend` 就是为此类扩展留的缝);
但需求清单的难度**不是均匀的**,其中三项远超「加个功能」的量级。

| 需求 | 可行性 | 难度 | 关键判断 |
|---|---|---|---|
| 1. 一维 → 二维画布 | 可行 | **高** | 数据模型改动小(扩 `PlanStep` 即可),真正的成本在**图执行器**(拓扑调度/并行/节点状态)与**前端画布**(需新引入图库) |
| 2. 节点级配置 | 大部分可行 | 中 → **高** | token/工具/温度**现已就绪**;`max_context`/`max_tool_rounds` 是白捡;**节点级模型是硬骨头**,依赖需求 5 的多套 API |
| 3. 严格/宽松节点 | 可行 | **高** | 「嵌入」与需求 4 的「类工具化」**是同一套机制**,可合并实现;但需改引擎工具分派内核 |
| 4. 强制/对比选择 | 可行 | 中 | 强制模式成本低(任务绑定流程 id);对比模式复用需求 3 的动态工具通道 |
| 5. 多套 API + 多套流程存储导出 | 可行 | **高**(API)/低(流程) | 多流程库**已存在**;多套 API 是全新子系统,且触及**凭据加密**,安全敏感 |

三个必须提前知道的判断:

1. **需求 2 的「节点级模型」是全局架构瓶颈**。当前引擎只持有一个全局连接器实例
   (`agents/engine/mod.rs:78,131`),聊天与任务共用(`api/app_state.rs:341-351`)。
   要支持「这个节点用 A 家的模型、那个节点用 B 家」,必须先做需求 5 的多套 API,
   并把连接器选择从「进程级单例」下推到「请求/节点级」。这条链不通,需求 2 只能做一半。
2. **需求 3 的「严格节点嵌入宽松节点」和需求 4 的「流程类工具化调用」应该合并设计**。
   两者本质都是「把一个已定义的执行单元暴露给模型当工具调」。合成一套机制后,
   实现量约为分别实现的一半。
3. **这不是一个批次能落地的事**。按现有仓库的批次粒度(每个 `批次 X.Y` 都是一个 commit),
   完整落地约 7 个批次,其中 2 个是架构级重构、1 个是安全敏感改动。

## 三、逐条需求分析

### 3.1 需求 1:一维 → 二维化

#### 数据模型:推荐「扩 `PlanStep`」而非新建平行结构

两个方案:

- **A1(推荐):在 `PlanStep` 上加 `x` / `y` / `inputs: Vec<String>`(上游节点 id)**
  - `inputs` 缺省为空 → 语义回退为「按数组顺序串联」,**存量流程 JSON 逐字节兼容**,
    旧客户端导出的流程仍可导入。
  - 单一事实源,不存在 `steps` 与 `edges` 两份数据漂移。
  - 聊天 custom 路径把图**按拓扑序线性化**即可继续工作(分支被忽略,需在文档声明)。
- **A2:新增 `graph: {nodes, edges}` 与 `steps` 并存** — 否决。两份事实源必然漂移,
  且所有既有消费者(校验/planner/前端/导出)都要写双分支。

配套必须同时确定的三个语义(不定就会在实现期反复):

1. **多父节点如何合并输入**。线性时代是「上一步产出进下一步 user 消息」
   (`custom.rs:272-281`)。图里一个节点可有多个父节点,建议:user 消息 =
   任务目标 + **按父节点在数组中下标升序**逐段拼接「父节点名 + 产出」。
   顺序必须确定,否则同一流程两次运行结果不可复现。
2. **最终成果取哪个节点**。建议新增 `is_output: bool`(缺省 = 无后继的汇点),
   存量线性流程的最后一个生成步骤天然是汇点,**语义与现在一致**。
3. **环检测**。校验期(`validate_flow` 扩展)与运行期双重拦截;自环/不可达节点同样拒绝。

#### 执行器:这是本需求真正的工作量

现有 custom 执行器是一个 130 行的线性 for 循环(`custom.rs:262-359`)。图化后需要:

- **拓扑调度**(Kahn 算法 + 就绪队列),而非数组遍历;
- **并行分支**(可选但建议有,否则二维图相对一维的唯一收益只是「能画」);
- **节点运行时状态**:`TaskStep` 现在只有 `name/goal/status/result` 四个字段
  (`models/types.rs:927-942`),而六模式文档把它列为「不动(兼容承诺)」。
  建议**新增 `node_id: Option<String>`(serde default)** 做画布映射——这是**加性改动**,
  旧客户端反序列化不受影响,但确实触及该结构,**需同步修订文档中的兼容承诺表述**。

**已识别的真实缺陷风险(必须在设计期解决,否则并行必炸)**:
`set_plan` 是「整列 JSON 覆写」。多个节点并发完成时,各自持有 `plan` 的旧快照做
读-改-写,会**丢失更新**(节点 A 的 Done 被节点 B 的写入覆盖)。解法二选一:
(a) 在服务层对 plan 写入做串行化(成本最低,plan 体积小);
(b) 新建 `task_nodes` 表做行级更新(成本高,但为将来节点级并发查询留路)。
**v1 建议 (a)**,并补一条并发回归测试。

#### 前端画布:需引入依赖

- 已验证 npm registry 可达,`@vue-flow/core` 最新 `1.48.2`(MIT,Vue 3 原生)。
  它直接提供拖拽、连线、端口(handle)、缩放/平移、minimap——自研等价物是数周工作量。
  建议引入 `@vue-flow/core` + `background` + `controls` + `minimap` 四个包。
- 代价:仓库当前依赖极精简且有审计门禁(`docs/前端工具链与审计升级-变更说明.md`),
  新依赖需过一次 lint/audit/CI;**画布在 jsdom 下渲染受限**,前端测试应断言
  **数据层与交互逻辑**(节点增删/连线合法性/配置面板),而非画布像素。
- 工作量集中在:节点检查器(Inspector)面板、连线合法性校验、
  「一维流程 → 图」的自动布局(存量流程升级时用得上)。

| **最大工具轮次** | 缺节点级;`GenerationParams.max_tool_rounds` 已是参数(`types.rs:383`),`custom.rs:119` 恒用全局值 | **通道已备(低成本)** |

#### 关于「使用的模式」的歧义(需要决策)

这句话有三种可能读法,实现量差别很大:

- **(甲)执行档位**:该节点是「单轮生成」还是「多轮工具循环」——
  **这正是需求 3 的严格/宽松**。若取此读法,需求 2 与需求 3 合并,最省。
- **(乙)任务模式**:该节点内部按 solo/multi/plan/team/custom 之一运行(即节点可自编排)。
  这会引入「节点内套模式」的语义,与需求 3 的「严格嵌入宽松」部分重叠,但更重。
- **(丙)顶层模式**:roleplay / task 二选一。当前双模式由设置层 `for_mode` 与类型级
  隔离承载(`docs/模式提示词边界.md`),把模式下推到节点会**破坏既有的隔离不变量**,
  不建议。

**推荐 (甲)**:需求 2 的「模式」= 需求 3 的严格/宽松档位。理由:实现量最小、
语义自洽、且与用户后文「严格节点可以嵌入宽松节点内」的表述衔接自然。
若你的本意是 (乙),请在开工前说明——那会把批次 2/4 的范围显著放大。

#### 节点级模型的依赖链

要让「节点 A 用 deepseek、节点 B 用本地 qwen」成立,需要依次打通:

1. **多套 API 配置**(需求 5):`RuntimeSettings` 现在只有单份
   `openai_base_url / openai_api_key / model`(`settings_service/mod.rs:72-75`);
2. **连接器注册与缓存**:`Connector` 是 `Clone` 的实例枚举
   (`connectors/mod.rs:27-30`),`build_connector` 是纯工厂(`:114-122`),**天然支持多实例**;
   但引擎只有一个 `Arc<RwLock<Connector>>`,需改为「按 profile id 缓存 + 按节点解析」;
3. **请求级路由**:`GenerationParams`(`types.rs:374-389`)或 `run_tool_loop` 需携带
   连接选择;注意 `GenerationParams` **未实现 Serialize**,可直接加字段而不动线格式;
4. **可观测性**:调用追踪的 `model` 列现在恒取当前全局模型
   (`custom.rs:163`),须改为逐节点真实模型,否则调用面板会显示错误模型名。

### 3.3 需求 3:严格 / 宽松节点与嵌入

#### 语义定义(建议固化进文档)

- **严格节点**:单次模型调用即完成,**不进入工具自循环**。定位是确定性、低成本的
  原子步骤(如「压缩到 200 字」「抽取 JSON」)。
- **宽松节点**:允许多轮完成——即现有 `run_tool_loop` 语义,工具轮次上限取
  `max_tool_rounds`(`engine/executor.rs:475-476`)。可自循环直到收敛。
- **嵌入**:宽松节点内含严格节点组成的子图。

现有代码的映射很直接:严格 = `generate_text` 分支(`custom.rs:289-307`),
宽松 = `run_tool_loop` 分支(`custom.rs:311-317`)。所以这个需求**不是新执行范式**,
而是把现有两个分支提升为**节点的一等属性**(`kind: Strict | Loose`)并加一个嵌套层。

#### 关键判断:嵌入与需求 4 的「类工具化」是同一套机制,应合并

两种「嵌入」通道,本质都是「调用一个已定义的执行单元」:

- **静态子图**:宽松节点定义里挂一个 `subgraph`(或 `sub_flow_id`),执行时先跑子图,
  产出作为该节点的输入/前置结果。**结构在流程内,无需工具注册表。**
- **动态调用**:模型在工具循环里主动调用某个节点/流程(需求 4 对比模式)。

**推荐 v1 只做「静态子图」**,理由是它不触碰引擎工具分派内核,风险小、可独立验证;
动态调用留给批次 5(需求 4),届时两者共用同一套「子执行 + 深度守卫 + 记账」原语。

#### 动态调用的技术方案(批次 5,务必按此实现)

**不要**在运行期往全局工具注册表里注册/注销流程对应的工具。理由:
`ToolRegistry` 是全局单例,`register_external` 会失效 `definitions_cache`
(`tools/registry.rs:123-130`);并发任务各自注册会造成缓存抖动与竞态,
且任务结束时的注销时机会与仍在跑的并发任务冲突。

**正确做法:注册一个稳定的内置工具 `run_flow`(启动时注册一次)**,
参数携带目标流程名/节点名。运行期通过 `params.tools` 是否包含它来控制「可见性」——
而 `GenerationParams.tools` 是**逐次调用传入的定义列表**
(`types.rs:378`,消费点 `custom.rs:91-99`),天然支持按任务差异化下发,
完全不碰全局注册表。

工具实现取上下文的路径已有先例:`ToolContext { session_id, character_id, agent_depth }`
(`types.rs:560-568`),而 `agentgo` / `run_subtask` 已是同类实现
(`tools/agent_tools_agent.rs`,依赖经 `ToolDeps` 的 `OnceLock<Weak<...>>` 后注入,
见 `docs/任务引擎六模式.md` §七)。`run_flow` 可照抄该模式,
从 `session_id`(格式 `task:{id}:step:{n}`,见 `custom.rs:123`)反解任务 id,
再查该任务的流程名单。

**必须同时加的三道闸(否则是烧钱/死循环事故)**:

1. **深度守卫**:子流程调用 `agent_depth + 1`,沿用现有 `subagent_max_depth` 口径;
2. **流程级环检测**:A 调 B、B 调 A 必须在**调用链**上拦截(图内环检测挡不住跨流程环);
3. **每任务调用预算**:总节点调用次数上限,防「模型反复调同一个流程」——
   引擎已有先例:普通工具循环的重复调用熔断(`engine/executor.rs:478-481` 注释记载
   实测 7 分钟烧 150 万 token 未收敛),`run_flow` 必须纳入同一熔断或更严的预算。

**记账口径需先决策**:`record_llm_call` / `record_usage` 的定位参数是
`phase: &str` + `step_index: Option<usize>`(`task_core/backend.rs:76-100`)。
嵌套调用需要表达「节点 2 的子节点 3」这种路径。两个选项:
(a) 编码进 `phase` 字符串(如 `step:2/sub:3`,零 schema 改动);
(b) `task_llm_calls` 新增 `node_path` 列(需 `ensure_*` 迁移)。
**建议 (a)**,与既有 `phase=agent/subagent/audit` 的命名习惯一致。
但注意 §八 的既有不变量:「`/calls` 各行 token 求和 == 详情 `usage_total`」,
嵌套记账若漏行会直接破坏该不变量,**必须补集成测试**。

### 3.4 需求 4:强制 / 对比选择机制

#### 强制模式(成本低,建议先做)

用户选一套流程执行任务。**当前恰好缺这个能力**:`POST /api/tasks` 只有
`title/character_id/task_mode`(`api/tasks.rs:16-25`),custom 执行时现读全局
`current_flow_id`(`custom.rs:236`),所以「不同任务用不同流程」现在做不到。

改动清单:

1. `CreateTaskBody` 增加可选 `flow_id`(可选 = 旧客户端行为不变,回退全局当前流程);
2. `tasks` 表加 `flow_id` 列(走既有 `ensure_*` 幂等迁移范式,
   `migration/ddl.rs` + `models/db/mod.rs:81-108` 注册调用点);
3. `TaskFlowAccess::current_flow`(`task_core/backend.rs:153-156`)扩为
   「先按任务绑定,回退全局」;
4. **流程快照**:建议在任务创建时把流程定义快照落库(或至少落 `flow_id` + 版本),
   否则用户执行中途改流程会导致任务行为漂移——这是现有 chatt custom 路径
   已经做过的事(`AgentRunRequest.flow` 就是快照,`engine/types.rs:38`);
5. 前端:任务创建处加流程选择器。

#### 对比模式(复用 3.3 的 `run_flow`)

「一至多套流程释放给模型,模型在任务工作中类工具化调用」完全落在 3.3 的动态调用方案上。
额外需要:

- **名单来源**:任务级(或设置级)的流程 id 列表,建议随任务落库(`flow_ids` JSON 列),
  与强制模式的 `flow_id` 同批迁移;
- **释放形式**:两处都要——① 工具定义(`run_flow` 的 description 里列出可用流程名与用途,
  或每流程生成一个工具定义并按 `params.tools` 下发,后者对模型更友好、也更省 token
  抉择成本);② system 提示词里说明该能力。建议走「①每流程一个工具定义」,
  因为 OpenAI 兼容协议下模型对「多个平铺工具」的选择准确率高于「一个带枚举参数的工具」;
- **权限边界**:被调流程内部的工具集仍必须经 `task_tool_policy` 编译后再收窄
  (参照 `custom.rs:85-99` 现有口径),**不得**因为「是子流程」而放宽;
- **前端**:任务创建处选择「强制 / 对比」+ 名单多选。

### 3.5 需求 5:多套 API + 多套流程的存储与导出

#### 多套流程:已基本具备

`AgentFlowLibrary { current_flow_id, flows }` 已是多流程库
(`agent_flow_service.rs:96-121`),支持新建/复制/选择/删除
(`:52-80`)、导入导出(`useAgentFlow.ts:129-184`)。**本需求只需扩到二维字段**,
外加「批量导出全部流程」与「导入时合并策略」(现有导入恒分配新 id,见
`useAgentFlow.ts:154`,合并导入需保留)。

#### 多套 API:全新子系统,且是安全敏感改动

现状:`RuntimeSettings` 只有一份 `openai_base_url / openai_api_key / model`
(`settings_service/mod.rs:72-75`),且 `docs/模式提示词边界.md` 明确
「连接信息始终全局共享,不入覆盖层」(§一)。要多套必须改动这条设计承诺。

**建议数据形态**:

```
connections: Vec<ConnectionProfile>   // 新增
active_connection_id: Option<String>  // 新增(默认连接)
// 保留扁平 openai_base_url/api_key/model 作为兼容字段(旧配置/旧客户端)
```

`ConnectionProfile { id, name, connector_type, base_url, api_key, model, enabled }`。
`connector_type` 复用现有 `available_connector_types()`(`connectors/mod.rs:133-137`)。
底层 `Connector` 是 `Clone` 实例枚举、`build_connector` 是纯工厂
(`connectors/mod.rs:27-30,114-122`),**多实例天然支持**,不需要改连接器层。

**凭据加密是最大的技术风险点**。现有加密逻辑是**按字段名硬编码**的:
`secret.rs:183-186` 只处理 `openai_api_key` / `embedding_api_key`,
`read_preserved_ciphertexts` 的 `pick("openai_api_key")` 同样是固定键名
(`secret.rs:203-238`)。改为数组后必须泛化,且**必须继承既有的两条不变量**
(已有测试锁死在 `secret.rs:266-280`):

1. **解密失败/空值时必须保留磁盘原密文**,绝不能把密钥擦成空串——
   否则用户重装/换机器唤醒 DPAPI 失败时会**静默丢失所有 API Key**;
2. **落盘不得出现明文**(迁移旧明文配置的路径见 `secret.rs:146-162`)。

必须新增的测试(先写失败测试):
- 保存后读原始 JSON,断言无任何 profile 的 key 以明文出现;
- 读入时 key 为空的 profile,其磁盘密文保持不变(不擦除);
- 旧单份配置 → 首次读入时自动播种为 `connections[0]` 且**幂等**(重复读不重复播种);
- `embedding_api_key` 行为不变(回归)。

**导出策略是安全决策,需明确**。流程导出无敏感性,API 配置导出**含凭据**。
建议:
- **默认导出的 API 配置不含密钥**(仅 name/base_url/model/type),
  并在 UI 明示「密钥需重新填写」;
- 需要含密钥的导出走**显式二次确认**的独立选项,文件名加 `-含密钥` 标识;
- 无论如何**不得**写入日志或错误消息(现有 `不泄露聊天正文、API Key` 是 AGENTS.md 硬约束)。

#### 关于「节点级模型」的落地顺序

需求 2 的节点级模型**必须排在多套 API 之后**(见 §3.2 依赖链)。
且需注意连接器解析层的落点:引擎当前只有一个
`Arc<RwLock<Connector>>`(`agents/engine/mod.rs:78,131`),建议新增一个
**连接器解析器**(按 profile id → `Arc<Connector>`,带缓存),注入
`AgentEngine` 与 `TaskService`;`GenerationParams` 加 `connection_id: Option<String>`
(该结构未实现 Serialize,加字段不动线格式)。**不要**在 `TaskService` 里
另建一份连接器缓存,否则聊天/任务两套缓存会出现数据源分裂。

### 4.2 技术与产品风险

**高风险(会在实现期变成坑,已在方案中给了解法)**

1. **并发节点丢更新**:`set_plan` 整列覆写 + 多节点并发 = 丢失更新(§3.1)。
2. **多套 API 的凭据静默丢失**:现有加密按字段名硬编码,泛化时若丢掉
   「空值保留原密文」不变量,用户换机器后会**静默丢光所有 Key**(§3.5)。
3. **嵌套调用烧钱/死循环**:跨流程环 + 模型反复调同一流程,
   已有实测先例(7 分钟 150 万 token,`engine/executor.rs:478-481`)。
4. **`PlanStep` 双路径退化**:改共享契约可能悄悄破坏聊天 `agent_mode=custom`
   (`api/chat.rs:178-206`)。每批都必须跑聊天侧回归。
5. **兼容承诺表述需修订**:`docs/任务引擎六模式.md` §二 把「TaskStep 四字段」
   列为「不动(兼容承诺)」。加 `node_id` 是加性改动(serde default),
   旧客户端不受影响,但**文档必须同步修订**,否则后续评审会按旧承诺判定违规。

**中风险**

6. **前置入口缺陷**:`SettingsHub.vue:125` 把 `'flow'` 列为 `ROLEPLAY_ONLY`,
   任务模式下用户看不到流程编辑区——而 custom 任务依赖它。**做画布前先修**。
7. **导出/导入幂等**:流程导入恒分配新 id(`useAgentFlow.ts:154`),
   「批量导出 → 导入合并」需明确是「新增副本」还是「按 id 覆盖」,否则用户会得到重复流程。
8. **新前端依赖过审计门禁**:仓库依赖极精简且有 lint/audit/lock 门禁
   (`npm run check:arch` / `check:lock` / `check:lint`)。引入 vue-flow 需一次过闸。
9. **画布测试受限**:jsdom 下画布渲染不完整,测试须断言数据层与交互逻辑,
   不要断言像素/布局坐标。

**产品风险(建议写进 UI 文案)**

10. **二维画布对普通用户是负担**。ComfyUI 式画布的价值在表达能力,代价是门槛。
    建议**保留线性列表为默认视图**,画布作为「高级模式」切换;存量流程进入画布时
    自动布局为纵向链,视觉上仍是一维,不惊吓用户。
11. **并行 = 成本倍增**。并发节点数应默认保守(如 2),并在 UI 提示
    「并行节点会成倍消耗 token」。

## 五、批次执行计划

按仓库既有批次粒度(一批次一 commit,先写失败测试,文档同步)。**规模是量级估计,非承诺**。

| 批次 | 内容 | 规模 | 前置 | 关键验收 |
|---|---|---|---|---|
| **0** | 修 `SettingsHub` 的 `flow` 入口错位(任务模式可见) | S(<0.5 天) | — | 前端单测:任务模式下流程编辑区可见 |
| **1** | 图数据模型:`PlanStep` 加 `x/y/inputs/is_output/kind`;`validate_flow` 扩图校验(环/可达/汇点/kind);`agent_flows.json` v2 迁移;custom 执行器改**拓扑序串行**(行为与现在等价) | M(1~3 天) | 0 | 存量线性流程跑通且**结果逐字节不变**;环/孤立点被拒并给中文错误;旧 JSON 加载迁移幂等 |
| **2** | 图执行器**并行**:JoinSet 调度 + `max_parallel_nodes`;`TaskStep` 加 `node_id`;plan 写入串行化;**取消传播到并行分支**;并发回归测试 | L(3~10 天) | 1 | 并发 N 节点无丢更新(专测);取消时全部分支收口;usage 汇总正确 |
| **3** | 前端画布:引入 `@vue-flow/core` + background/controls/minimap;节点 Inspector(逐字段编辑);连线合法性校验;存量流程自动纵向布局;前端数据层/交互测试 | L(3~10 天) | 1 | `npm test -w web` 全绿;`check:lint`/`check:lock` 过闸;连线成环被前端拦截 |
| **4** | **多套 API**:`connections` 数组 + `active_connection_id`;加密逻辑泛化(键名硬编码 → 数组遍历)+ 迁移幂等播种;**导出默认不含密钥** | L(3~10 天) | — (独立) | 磁盘无明文;空值保留原密文;旧单份配置播种幂等;`embedding_api_key` 回归不变 |
| **5** | **节点级模型 + 强制模式**:连接器解析器(profile id → `Arc<Connector>`,带缓存);`GenerationParams.connection_id`;节点级 `max_context`/`max_tool_rounds`;调用追踪 `model` 列改逐节点真实值;`tasks` 加 `flow_id`/`flow_ids` 迁移;前端任务创建选择器 | XL(>10 天) | 4 | 同一任务内两个节点走不同 provider 且调用面板显示各自真实模型;任务绑定流程后改全局流程不影响该任务 |
| **6** | **严格/宽松 + 静态子图**:`kind: Strict\|Loose`(严格=单次调用,宽松=工具自循环);子图执行;深度守卫;嵌套记账(口径 D6) | M(1~3 天) | 2 | 严格节点不进入工具循环(断言只 1 次模型调用);子图产出正确注入;超深嵌套被拒 |
| **7** | **对比模式 + 导出整合**:`run_flow` 内置工具 + 按流程生成工具定义并释放名单;跨流程环检测;每任务调用预算;批量导出/导入合并策略 | L(3~10 天) | 5, 6 | 模型可自主调用名单内流程;名单外流程被拒;A↔B 互调被拦;超预算熔断;批量导出→导入不产生重复 id |

**批次为 3~4 个里程碑**:

- **里程碑一(批次 0~2)**:后端二维化完成。此时前端仍是线性编辑,但流程已可在
  JSON 层表达二维并被正确执行——可先用 JSON 导入验证。
- **里程碑二(批次 3)**:画布可用,一维 → 二维对用户可见。
- **里程碑三(批次 4~5)**:多套 API 与节点级模型——这是「一个节点用 A 家、另一个用 B 家」
  真正成立的节点。
- **里程碑四(批次 6~7)**:严格/宽松嵌入与对比模式,需求 3、4 收口。

**批次 1 与 4 可并行**(无交集:一个动流程文件与执行器,一个动设置与加密)。
**批次 3 必须等批次 1 的数据模型冻结**。

### 每批次必须跑的验证(仓库既有口径)

```powershell
cargo test --manifest-path server-rs/Cargo.toml -j 2   # 环境先加载 vcvars64
npm test -w web
npm run build -w web
node tools/check-arch.mjs
```

补充说明:
- `cargo test` **必须带 `-j 2`**(本机默认并行度下 rustc 会崩,见 AGENTS.md);
- 本计划新增文件都落在既有顶层目录(`services/`、`components/` 等),
  **不需要**改 `tools/arch-layers.json`(它登记的是顶层模块);若将来新增顶层目录,
  规则 I 会直接判 FAIL,须同步登记;
- 改完代码后 `dist\` 与 `Kedai.exe` **不会自动更新**,交付前跑 `.\build.ps1`;
- 批次 4 涉及凭据,必须额外人工检查:落盘 JSON 无明文、日志无 Key。

### 建议的第一个动作

不要从画布开始。先做**批次 1**,因为它是唯一能反过来证伪整个方案的一步:
如果 `PlanStep` 加 `inputs` 后无法让存量流程保持逐字节等价,或聊天 custom 路径退化,
那么二维化的数据模型假设就需要重做——这个结论越早知道越好,且批次 1 的成本很低。
