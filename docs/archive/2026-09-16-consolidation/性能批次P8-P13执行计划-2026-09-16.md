## 2. P-8 首屏拆 `modal-settings` 反向耦合

### 现状证据(已实测)

- `web/vite.config.ts:29` 的 `manualChunks` 把 `/components/SettingsHub` 与
  `/components/SettingsModal` 强制归入 `modal-settings`。
- `web/src/components/SettingsModal.vue:11-17` 静态 import 了 `../store`(useAppStore)、
  三个 composable(`useApiSettings`/`usePromptInject`/`useDataManager`)、两个 section 组件。
- `web/src/store.ts:21-27` 顶层实例化全部子 store。
- 结果:被入口与弹窗**共享**的模块落进 `modal-settings`,于是 `index.js` 不得不静态
  import 该 chunk → `index.html` 发出 `modulepreload` → **首屏多拉 188KB / 62KB gz**。
- vite.config 注释里「避免把首屏共享模块误划入异步 chunk 造成反向耦合」的护栏**没覆盖这条路径**。

### 目标

首屏不再加载 `modal-settings`;弹窗懒加载语义恢复。预期首屏少 188,565 B / 61,850 gz。

### 步骤

1. **量基线**:`npm run build -w web` 后记录 `dist/index.html` 的 modulepreload 列表与
   各 chunk 体积,追加进 `docs/perf-baseline.md`(作为 P-12 预算与回归对照)。
2. **主方案**:删除 `manualChunks` 中两条 app-code 归组(`SettingsHub`/`SettingsModal`),
   让 `modals.ts:40` 的动态 `import()` 自然产出异步 chunk。
   8 个 section 已由 `SettingsModal.vue:18-30` 的 `lazyModal` 各自成 chunk,不受影响。
3. **验证是否真的解开**:重新构建后断言 `dist/index.html` **不含** `modal-settings`,
   且 `index-*.js` 不再出现 `from"./modal-settings-…js"`。
4. **备选(仅当主方案产生反向耦合或碎片过多时)**:保留归组但对
   `/src/store.ts`、`/src/stores/`、`/src/composables/`、`/src/asyncModal.ts`
   返回固定 chunk 名(如 `'app-core'`),确保 `modal-settings` 内不再含被入口引用的模块。
5. 复核 `web/src/modals.ts` 注册表在本改动后仍与 `modals.test.ts` 的元测试一致。

### 验收

- `npm run build -w web` 通过;`dist/index.html` 无 `modal-settings` 预载;
- `npm test -w web` 全绿(注意 `modals.test.ts` 可能断言 chunk 归属);
- **手动**:打开综合设置,逐个 tab 切换,确认 8 个分区仍懒加载且功能正常;
- 记录新体积到 `docs/perf-baseline.md`。

### 风险与回滚

风险中:`manualChunks` 调整会改变 chunk 划分,可能出现循环 chunk 或某个 chunk 变大。
回滚 = `git revert` 单个 commit(vite.config.ts + 可能的 modals 调整)。
**注意**:`web/dist` 被 `include_dir!` 编入 server 二进制(`server-rs/build.rs`),
手动验证前必须重新 `npm run build -w web` 并重建 server,否则服务端仍发旧资源。

## 3. P-9 虚拟滚动与渲染缓存生命周期对齐

### 现状证据

- `useVirtualMessages.ts:147-154`:离开缓冲区即销毁组件(模板降级为占位 `div`)。
- `ChatMessageItem.vue:213-234` 的 `html` 是**组件内 computed**,组件卸载即失效;
  其内部 `renderScopedScripts`(`render.ts:377`)与 `renderMarkdown`(`markdown.ts:59`)
  都是无外部缓存的直接调用。
- 代价参照:`sanitize-html` 处理 16.8k 字符 ≈ 3.057ms(`docs/perf-baseline.md:118`),
  含 HTML 卡片的长会话来回滚动会反复付这份成本。

### 目标

滚动卸载/重挂后不重复计算 markdown/sanitize/脚本渲染;缓存有界不泄漏。

### 步骤

1. **先写失败测试**:加渲染计数(mock 或 spy 统计 `renderMarkdown`/`renderScopedScripts`
   调用次数),断言「同一消息内容二次渲染不重算」。
2. **缓存提到模块级**:新增 `web/src/renderCache.ts`(或并入现有渲染模块),
   提供有容量上限的 Map(建议容量 500,超出按 FIFO/LRU 淘汰)。
3. **缓存键沿用现有脚本缓存口径**(`ChatWindow.vue:61-91` 的
   `${scopeId}|${scriptHash}|${depth}|${text}` 形态),并加入 `renderHtml` 开关与
   `scripts` 版本(复用 `props.scriptHash`),保证:
   - 内容变更 → key 变更 → 必 miss(响应式正确);
   - `scripts` 引用或字段变化 → key 变更 → 必 miss(脚本热更新即时生效)。
4. `ChatMessageItem.vue` 的 `html` computed 改为「先查模块级缓存,未命中再算并写回」,
   命中路径不得触发 `sanitize`。
5. 顺带收敛 `overscanPx=1200` 固定像素对超高卡片覆盖不足的问题:改为按**条数窗口**
   (建议上下各 8 条)与像素窗口取较大者,减少挂载/卸载抖动。
6. **不要**把缓存做成全局无界(内存风险);淘汰策略写进注释与测试。

### 验收

- `npm test -w web` 全绿,**含新增的缓存命中用例**(证明二次渲染零重算);
- 长会话(>80 条、含 HTML 卡片)滚动时,Performance 面板无重复 `sanitize-html` 长任务;
- `npm run typecheck -w web` 与 `node tools/check-frontend-lint.mjs` 通过(类型逃逸只降不升)。

### 风险与回滚

风险中:key 设计错误会渲染**陈旧内容**(显示 bug)。缓解:key 必须包含内容本身
(或内容哈希),而非仅消息 id;测试覆盖「内容变更必重渲」。
回滚 = revert 单个 commit(缓存模块 + 组件调用点)。

## 4. P-12 前端体积预算门禁 + 性能门禁可见性

### 现状证据

- `tools/check-all.ps1:235` 有 `vite build`,但**无产物体积断言**。
- `tools/check-all.ps1:242-247`:性能门禁默认关闭(需 `-Perf` 且要求服务在跑),CI 不跑;
  跳过时**无任何提示**,属静默跳过。
- 仓库既有护栏体例为「纯 Node 零依赖 + ratchet 只降不升」(`tools/check-frontend-lint.mjs`)。

### 目标

首屏体积与 chunk 划分回归可被自动拦截;被跳过的门禁必须显式可见。

### 步骤

1. **新增 `tools/check-bundle.mjs`**(纯 Node 零依赖,风格对齐 `check-frontend-lint.mjs`):
   - 断言 `web/dist/index.html` 的 modulepreload **不含** `modal-*`(P-8 的固化护栏);
   - 断言首屏集合(index + 其预载的 vendor/vue-vendor/content-rendering/CSS)的
     gzip 总量不超过预算;
   - 断言各 chunk gzip 体积不超单项预算;
   - 预算取 P-8 实测值 + 10% 余量,写为脚本内 `BASELINE` 常量,**只降不升**;
   - `web/dist` 缺失时给出明确提示并失败(与仓库「门禁 fail-closed」纪律一致);
   - 支持 `--json` 与 `--verbose`(与既有脚本一致)。
2. **接入 `check-all.ps1`**:在 `web: vite build` 之后加
   `Invoke-Stage 'web: bundle budget' { node tools/check-bundle.mjs }`;
   `-Quick` 模式跳过它(与 vite build 同步跳)。
3. **性能门禁可见性**:`check-all.ps1` 收尾打印一行显式提示,
   说明「未运行性能门禁(需服务在运行,用 -Perf 开启)」,避免静默跳过被误读为通过。
   不改 `-Perf` 的默认关闭语义(该门禁依赖外部服务,不适合默认开)。
4. 更新 `MAINTENANCE.md` §11 或 §0 门禁清单,登记新增门禁项。

### 验收

- 正常状态 `node tools/check-bundle.mjs` exit 0;
- **负向验证**:手工把某 chunk 撑大 / 把 `modal-settings` 加回 `index.html` 预载,
  脚本必须 exit 1(证明门禁有效,不是空断言);
- `npm run check` 全绿。

### 风险与回滚

风险低。回滚 = revert(新增脚本 + check-all 两行 + 文档)。
若预算过紧导致正常功能增长即红,把余量调到实测值**再收紧**,不得直接删除门禁。

## 5. P-10 AgentPanel 增长治理

### 现状证据

- `web/src/sseReducer.ts:105,121,123,138,153,168,197`:`chain` 与
  `toolCalls` 每次事件**无条件 push,从不裁剪**。
- `web/src/components/AgentPanel.vue:392,408,426,456,488` 全量 `v-for`,**无虚拟化**,
  且 key 用 index(`:key="i"` / `:key="'r'+i"`)。
- `AgentPanel.vue:86` 的 `ioText` 在渲染路径上做 `JSON.stringify(v, null, 2)`
  (展示与复制共用)。
- `web/src/stores/chat.ts:123-144` 的 `restoreAgentTrace` 会把后端历史
  **全量**回填进 `agent.value`。

### 目标

长 agent 会话下 DOM 节点数与渲染耗时不再线性膨胀;裁剪行为**显式可见**,不静默丢信息。

### 步骤

1. **先写失败测试**:派发 N(建议 500)次 step/tool 事件后,断言
   `chain`/`toolCalls` 被裁剪到上限,且 AgentPanel 渲染的 DOM 节点数受限。
2. `sseReducer` 加有界裁剪:保留最近 N 条 + 在列表首部渲染「已省略 M 条」提示
   (**不静默丢弃**;`agent_sessions` 落库侧不受影响,面板只是展示层上限)。
3. **需确认**:裁剪上限取值(建议 `chain` 500 / `toolCalls` 200)。
   `restoreAgentTrace` 走同一上限,保证刷新前后口径一致。
4. `AgentPanel` 的工具卡列表接入 `useVirtualMessages` 或改为「仅抽屉打开时渲染」;
   key 改稳定 id(`toolCalls` 已有 `callId`,优先用它;`chain` 需补稳定 id)。
5. `ioText(v)` 结果改为 computed 预计算(按 tool call id 缓存),避免模板每次重渲染
   重复 stringify 大对象。
6. **先读清 `restoreAgentTrace` 与 `agent.value` 的整体替换语义**(`chat.ts:140`
   `agent.value = base`),确保裁剪不破坏「刷新后重建」与流式追加的共存。

### 验收

- `npm test -w web` 全绿 + 新增裁剪用例;
- 跑一轮 agent 模式(几十次工具调用)观察渲染耗时与 DOM 节点数**不再线性膨胀**;
- `npm run typecheck -w web`、`node tools/check-frontend-lint.mjs` 通过。

### 风险与回滚

风险中高:裁剪是**可见行为变更**(用户会看到「已省略 M 条」)。
缓解:上限取值保守 + 提示显式 + 变更写入 `docs/known-limitations.md`(若降级为已知限制)。
回滚 = revert(裁剪逻辑 + 面板改动)。

## 6. P-13 `-j 2` 并发限制解除实验(**允许失败,产出入档**)

### 现状证据

- `tools/check-all.ps1:108-109` 强制 `cargo test --workspace -j 2`。

  `libkedai_server-*.rlib`(带 debuginfo 约 665MB)触发 `os error 1455 页面文件太小`。

- **用户已明确:不通过削减 debuginfo 换并发**。故本批次只走「参数与栈」两条路。

### 目标

给出「本机能否放开 `-j 2`」的**实测结论**;无论成功或失败,把矩阵入档,避免下次重复试错。

### 步骤

1. **记录基线**:不带 `-j` 复跑一次,捕获退出码与崩溃文本(确认当前是否仍复现)。
2. **并发矩阵**:依次 `-j 4` / `-j 6` / `-j 8` 各跑一次 `cargo test --workspace`,
   记录成功/失败与失败形态(条目 17 的内存型 vs 条目 29 的栈型,处置不同)。
3. **栈假设验证**:若崩溃形态属条目 29,试 `RUST_MIN_STACK=33554432`(32MB)后
   再测默认并行度,验证是否与 rustc 线程栈相关。
4. **若仅高并发崩** → 取稳定上限 N 固化(`.cargo/config.toml` 的 `[build] jobs = N`,
   或改 `check-all.ps1` 与 `AGENTS.md` 的验证命令)。
5. **若全手段仍崩** → 结论「维持 -j 2」,把矩阵写入 `MAINTENANCE.md` 条目 29/30/31 附近。
6. **约束**:测试期间**不得**与 `build.ps1` 并发(`MAINTENANCE.md:434` 明确警告内存争用
   会让链接器崩 `0xc0000409`);每轮之间清一次孤立 `.rmeta`(条目 30)。

### 验收

- 实测矩阵(并发度 × 结果 × 失败形态)入档 `MAINTENANCE.md`;
- 若放开:门禁脚本与 `AGENTS.md` 同步更新,并复跑一次全量确认;
- 若未放开:结论与依据入档,`-j 2` 维持现状并注明「已实测,勿重复尝试」。

### 风险与回滚

风险低(纯实验,不改产品代码)。回滚 = 还原 `check-all.ps1`/`.cargo/config.toml`。
**唯一真实风险**:实验可能写坏 rlib(条目 17/29 的产物损坏),故每轮失败后按
条目 30 清孤立 `.rmeta` 与成对 `.fingerprint` 目录再继续。

## 7. P-11 角色卡列表解析与启动 N+1(**需单独确认,风险最高**)

### 现状证据

- `character_service.rs:95-113` 的 `list()`:注释称「列表不含 data_raw」,但 SQL **仍取
  `data_raw` 列**,且 `row_to_character`(`:39-54`,以 `with_data_raw=false` 调用)对它做
  完整 `serde_json::from_str`,只为取派生字段:`first_mes`、`alternate_greetings`、
  `regex_scripts`、`creator`、`character_version`、`creator_notes`。
- `character_service.rs:165-205` 的 `reflatten_v3_cards` 是 N+1:先 `SELECT id FROM characters`,
  再**逐个 id** `SELECT data_raw`;启动期由 `seed_default_character` 触发
  (`:127-131`,`app_state.rs:144` 调用)。
- `list()` 用 `prepare` 而非 `prepare_cached`。
- `SCHEMA_VERSION = 1`(`schema.rs:8`);最近一次加列(`finished_at`)的模式是
  `migration/ddl.rs:244` 的 `add_column_if_missing`,且**不动 SCHEMA_VERSION**。

### 目标

列表接口与启动路径的 JSON 解析次数不随「卡数量 × 卡体积」线性增长。

### 步骤

1. **先写失败测试**:造 50 张卡(其中含 1MB 级 `data_raw`),断言
   `list()` 的解析次数/耗时**不随卡体积线性增长**;断言 `reflatten_v3_cards`
   的查询次数为 **O(1)**(不是 O(卡数))。
2. **派生列方案**:为 `characters` 增加派生列(建议单列 `derived_json` 存一个 JSON 对象,
   避免 6 个散列),写入路径(upload/编辑/迁移)同步计算并落盘;
   列表与 `get` 直读列 → **零 JSON 解析**。
3. **迁移**:用既有 `add_column_if_missing` 模式加列(不动 `SCHEMA_VERSION`);
   新增幂等回填:对已有卡按需计算 `derived_json`(一次性,靠 backfill 标记幂等)。
4. `reflatten_v3_cards` 改**单次全表** `SELECT id, data_raw` 遍历,消除 N+1。
5. `list()` 的 `prepare` 改 `prepare_cached`。
6. **不改列表接口返回字段集合**(派生字段本来就在返回体里,只是改为读列而非现算)。

### 验收

- `cargo test --manifest-path server-rs/Cargo.toml -j 2` 全绿;
- **必须同步 `tests/schema_migration_meta.rs` 与 `tests/fixtures/schema_baseline_v0_3_0_beta.sql`**
  (该测试断言老库升级后结构一致性并冻结基线);
- 50 卡基准(列表耗时、启动耗时)记入 `docs/perf-baseline.md`;
- 手工:上传/编辑/删除角色卡后列表派生字段正确(封面、开场白、正则脚本均正常)。

### 风险与回滚(**最高**)

- schema 变更牵连迁移链、降级策略与冻结基线;`db/mod.rs:66-76` 的「库比代码新则拒绝启动」
  意味着**一旦抬高 `user_version` 后回滚,用户库需从备份恢复**。
- 故:**本批次执行前需单独确认**;执行前先备份 `data/`;建议先在副本库上验证迁移。
- 回滚 = revert 代码 + 从备份恢复库(不可仅靠 git revert)。

## 8. 全程纪律

- **一逻辑批次一 commit**:Conventional Commits 前缀 + 中文 scope/描述,正文写清
  「改了什么 / 为何这么改 / 验证证据(实际命令与结果)」。
- **每批次先写失败测试再最小实现**(`AGENTS.md` 核心约定)。
- **新增测试后必须同步计数门禁**:`node tools/count-tests.mjs` → 更新 `MAINTENANCE.md`
  (`--check` 是硬门禁;当前记录:后端 **1154** = 930 单测 + 224 集成(23 文件),前端 **834** / 87 文件)。
- 每批次收尾跑:
  `cargo test --manifest-path server-rs/Cargo.toml -j 2`、
  `npm test -w web`、`npm run typecheck -w web`、`node tools/check-frontend-lint.mjs`、
  `node tools/check-arch.mjs`、`node tools/check-contract.mjs`、
  `node tools/count-tests.mjs --check`;改前端另跑 `npm run build -w web`。
- **交付 exe 前**跑一次完整 `.\build.ps1`(`dist\` 与根 `Kedai.exe` 不会自动更新;
  改前端后必须重建,因为 `web/dist` 经 `include_dir!` 编入 server 二进制)。
- 本机 `cargo` 需先 `call vcvars64.bat`;`cargo test` 必须带 `-j 2`(直到 P-13 改变结论)。
- 文档回填:`docs/perf-baseline.md`(体积/延迟前后对比)、必要时
  `docs/known-limitations.md`(P-10 裁剪上限)与 `MAINTENANCE.md`(P-12 新门禁、P-13 矩阵)。

## 9. 明确不做

- **不改 API 契约**(不新增分页参数;列表返回字段集合保持不变)。
- **不削减 debuginfo**(用户已定;P-13 只走参数与栈两条路)。
- **不动「构建后清 target」策略**(用户已说明为省盘有意为之)。
- **不加 `release` 的 `panic="abort"`**(仓库依赖 unwind:锁中毒 ROLLBACK、
  `pending_runs` RAII drop)。
- 不做 SSR/预渲染、不引入 gzip/brotli 服务端压缩(loopback 场景收益极低)、
  不引入图表/虚拟滚动第三方库(`useVirtualMessages` 已是零依赖自研)。

## 10. 需在执行时确认的两个决策点

1. **P-10 的裁剪上限**(`chain` / `toolCalls` 保留条数)。默认建议 500 / 200;
   它是**可见行为变更**,确认后再落地。
2. **P-11 是否执行**(唯一有数据影响的批次)。若决定做,先备份 `data/` 并在副本库上验迁移。
