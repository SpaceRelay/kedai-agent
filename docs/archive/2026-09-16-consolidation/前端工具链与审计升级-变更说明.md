## 一、4.3 `AgentEngine` 依赖结构体分组

`agents/engine/mod.rs` 的 `AgentEngine::new` 原 **18 个参数**,按职责收敛为 4 个结构体:

| 结构体 | 含依赖 | 职责 |
|---|---|---|
| `EngineCore` | connector / settings / db / initial_model | 基础运行依赖 |
| `EngineStorage` | characters / sessions / agent_sessions / world_books / contract_registry / kaleido_state | 数据服务 |
| `EnginePrompt` | prompt_inject / quick_replies / runtime_prompt / memory / skills | 提示词与上下文注入 |
| `EngineExt` | tool_registry / user_scripts / slash | 工具与扩展 |

新签名 `new(core, storage, prompt, ext)`;`#[allow(clippy::too_many_arguments)]` 已删;
字段类型与语义逐一保持原样(未引入 trait 对象/包装类型)。构造点 `api/app_state.rs` 按 4 个
结构体组装;已核实 `agent_tools` 的 `OnceLock` 回填发生在 `new` 之后、与入参顺序无关。

## 二、4.4 状态机迁移非静默

`transition` **本就返回 `Result`**(非法迁移 `Err("非法状态迁移:from → to")`),问题在 8 处
调用点用 `let _ =` 静默吞掉。新增 `StateMachine::transition_best_effort(to, session_id) -> bool`:
内部调 `transition`,失败时 `tracing::warn!(session_id, from, to, error, ...)` 并返回 `false`。

8 处改用它:`engine/executor.rs:28/99/766/787`(工具循环回到 ToolCall/Executing)、
`engine/mod.rs:421/432/744/754`(中断/收尾/异常终态;末条为清单外同类第 8 处)。三处已用 `?`
传播的(`run_loop.rs:82/364`、`plan.rs:24`)保持不动。新增 3 例测试:合法迁移返回 true 且状态变更、
非法迁移返回 false 且状态不变、**非法迁移发出 warn 日志**(复用仓库既有 `tracing-subscriber`
的捕获 writer,未引入新依赖)。

## 四、6.1 审计门禁升级

- **cargo audit 补扫双锁**:原口径只扫 `server-rs/Cargo.lock`;现独立成审计段,双锁
  (`server-rs` + `src-tauri`)各自判定,**任一 FAIL 即整体失败**,且与 `-SkipRust/-SkipWeb` 解耦。
  新增 `-AuditOnly` 供快速核查;追加 `--no-yanked`(yank 非漏洞信号,冷索引下会大量超时刷屏)。
- **实测告警**:两锁**真漏洞均为 0**;`src-tauri` 锁有 7 条 allowed warning——6 条
  `unmaintained`(proc-macro-error + rust-unic 全系,均 `patched=[]` 上游无修复、来自 Tauri
  固定依赖链)与 1 条 `unsound`(glib 0.18.5,仅 Linux 目标、`patched>=0.20.0` 而 Tauri GTK 锁 0.18)。
- 新建 `.cargo/audit.toml` **只 ignore 6 条 unmaintained** 并逐条注释理由与复审时机
  (每次 Tauri/gtk-rs 升级后重跑,依赖消失即删条目);**未 ignore 任何真漏洞**。
- **npm audit 由警告档升为硬门禁**(实测 `--omit=dev` 零漏洞);`ci.yml` 同步口径
  (仍如实标注「仓库无远端、推送后生效」)。
- **门禁不成为不可通过的阻塞点**(踩坑 23⑤):未加 `-D warnings`,故 glib unsound 是 allowed
  warning、exit 0,与改动前行为一致。

## 五、只读审查后的收口(修上一批遗留)

对 `154eaf0` / `dc8eb03` / `9f30da1` 三个提交做独立只读审查,发现并修正:

1. **P1 修正:EJS 冻结门禁范围不足**。原规则 H 只锁 `env.rs::builtin_global`,而
   `get_prop`(字符串/数组属性方法表)**同样是模板可达的能力面**——往其中加一个
   `"padStart" => ...` 就是一次真实的能力扩展却完全不被拦;原 D5「已封堵」表述过乐观。
   现规则 H 覆盖**三个能力面**(`builtin_global` 64 / `get_prop` 26 / `set_prop` 0,任一处超基线即 FAIL),
   并按顶层 `fn` 切分函数体(比原先手工定位边界更稳)。**变异验证**:只给 `get_prop` 加一个
   方法名 → 27 > 26 FAIL;给 `builtin_global` 加条目 → 65 > 64 FAIL;还原后 OK。
2. **P2 修正:`readModalFlags` 静默少项**。原正则只认单引号且仅在「整表 0 条」时 FAIL,
   若有人用双引号写新条目会静默少算一项。现引号放宽到单/双引号,并加**交叉校验**
   (`modal(` 出现次数必须等于解析条数,不等即 FAIL)。**变异验证**:loader 写成非字面量 import 时
   报「`modal(` 出现 14 次但仅解析出 13 条」FAIL。
3. **P2 修正:`retry.rs` 注释前提不准**。原注释称 `default_max_tokens` 恒在 1..=65536
   (故某分支不可达);实测 `RuntimeSettings::load` 无该字段钳制,手改 settings.json 可超出。
   注释已改为如实描述(超出时保持原预算不缩小,由单测锁定)。
4. **P2 收口:3 处内联重复**。`task_engine/team.rs:418`、`task_engine/retry.rs`(plan 与
   revise 两处)的 `(x*2).min(CAP)` 内联改为统一走 `utils::retry::doubled_heal_budget`,
   消除 4.1 之后残留的同类重复;语义等价(达上限保持原值,由既有单测锁定)。
5. **P2 修正:`modals.test.ts` 恒真断言**。`expect(m.component).toBeTruthy()` 恒真,改为断言
   组件带 `__asyncLoader`(真·`defineAsyncComponent` 产物),能拦住「被误改成静态 import」。
