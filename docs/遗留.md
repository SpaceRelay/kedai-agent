# 遗留 —— 已确认的缺陷与知情接受的残缺

> 本文件归属：**遗留**类（现状行为 + 判定 + 归宿）；有方案的见 `计划.md`，有方向的见 `展望.md`，修复记录见 `功能-变更史.md`。
>
> 定位：把散落在多份文档里的「已确认存在的 bug、已知问题、知情接受的残缺」收拢到一处。目的有二——① 避免后续会话把**有意裁剪**误判为 bug 反复排查；② 避免**知情接受**的残缺因无人登记而被当成「遗漏」，或反过来被当成「已实现」。
>
> **本文件只登记问题，不登记方案。** 凡条目本身已是「有改动点 + 验收断言」的改动方案，一律归 `计划.md`，本文只在「归宿」里指向它。

## 条目模板

```
### <ID> <标题>
- **现状行为**（`文件:行号` 或实测证据）：
- **判定**：缺陷 / 有意裁剪 / 知情接受 / 待验证
- **影响面**：
- **归宿**：转计划（`计划.md` <ID>） / 转展望（`展望.md` <ID>） / 接受（不修）
- **来源**：archive/2026-09-16-consolidation/<原文件名> §X
```

ID **沿用源文档编号**（L1~L27、T1~T5、D1~D5、批次 7.3、项 10~14、B.4b 等），**不重新编号**，以便与原日志、提交信息、代码注释里的引用一一对上。

## IF 判定规则（按顺序适用，先命中先定）

| 序 | IF（现状行为满足） | THEN 判定 | 归宿 |
|---|---|---|---|
| R1 | 行为与文档/契约的承诺不符，且无「有意保留」的书面理由 | **缺陷** | 转计划（`计划.md`） |
| R2 | 行为是有意的兼容子集 / 安全取舍，且**没有**补齐方向 | **有意裁剪** | 接受（不修） |
| R3 | 行为是有意的兼容子集 / 安全取舍，且**有**方向与触发条件 | **有意裁剪** | 接受（不修）+ 方向见 `展望.md` |
| R4 | 已知残缺，判定为「现在不修」并有明确书面理由 | **知情接受** | 接受（不修） |
| R5 | 现象已记录但根因/边界未定，或结论来自推断而非实测 | **待验证** | 转计划（`计划.md`）或标注【待核实】 |
| R6 | 缺陷已被修复并有验收证据 | **不登记为遗留** | 只进 §九「已封堵项索引」，指向 `功能-变更史.md` |

补充口径：

- 「计划」与「遗留」的分界是**条目性质**，不是严重度：条目本身是**问题**（有能力缺口、有可观测的坏行为）→ 本文；条目本身是**改动方案**（有改动点 + 验收断言）→ `计划.md`。
- 「有意裁剪」若无方向 → 本文「接受（不修）」；若有方向与触发条件 → 本文登记**现状行为** + `展望.md` 登记**方向**（本文「归宿」写「方向见 `展望.md` 的 <ID>」）。
- 本文件**不复述**已迁移到其他五类文档的正文；能交叉引用的一律只写一句并给路径。

## 一、能力缺口（L 系列）

> 承接 `archive/2026-09-16-consolidation/known-limitations.md` 的 L1~L27。其中 **L12/L13/L14/L15/L18/L19/L20/L21/L23 九项已修复**，不属遗留，索引见 §九。
### L1 世界书 sticky / cooldown 不参与匹配

- **现状行为**：条目的 `sticky`（激发后持续轮数）与 `cooldown`（激发后冷却轮数）在转换层已解析但**固定归零**（`server-rs/src/agents/engine/worldbook.rs:267-268`、`292-293`），匹配算法（同文件 `56-133`）不消费这两个字段，也没有「递归激活」（已触发条目的注入文本不再回头触发别的条目）。
- **判定**：**有意裁剪**。Kedai 对齐 SillyTavern 世界书行为的一个子集：关键词/正则触发、概率门控、constant/triggered 两组注入位置都已实现；sticky/cooldown 依赖跨轮状态台账，与 Kedai「每次生成都从消息池重新装配」的无状态管线相冲突。
- **影响面**：重度依赖 sticky/cooldown 的 ST 卡（如进度条式世界书）在 Kedai 中表现为「条目只按关键词当下触发」——语义更弱但不错乱，属可接受降级。
- **归宿**：接受（不修）；方向见 `展望.md` 的 L1（需会话维度「条目激发台账」+ 递归激活防环路）。
- **来源**：archive/2026-09-16-consolidation/known-limitations.md §L1
### L2 契约不变量仅落地 mutex

- **现状行为**：契约（Contract）可声明三类跨字段不变量，`check_invariants()`（`server-rs/src/contracts/op.rs:214` 起）只判定 **mutex**（同组路径同时有值 ≥2 即违反）；**range / require_if 两个变体恒判为满足**（匹配分支为空操作，注释已留痕）。
- **判定**：**待办**。代码注释指明依赖「白名单谓词引擎（§17.8 CES）」这一后续里程碑；当前恒通过意味着声明了 range/require_if 的契约卡不会得到校验，也不会报错。
- **影响面**：契约卡作者会误以为不变量已生效；前端不应向用户暴露「不变量已生效」的措辞。契约（Kaleido）是 Kedai 自研体系，无 ST 生态包袱。
- **归宿**：转计划（`计划.md` L2）；补齐需实现谓词白名单解析与求值，接线在 `op.rs` 两个空分支，不要在此顺手发明语法。
- **来源**：archive/2026-09-16-consolidation/known-limitations.md §L2
### L3 MCP 孙进程不保证回收（v1 保守语义）

- **现状行为**：MCP 服务器子进程以 `kill_on_drop(true)` 托管、显式 kill 后 wait 回收僵尸（`server-rs/src/mcp/process.rs:1-10`）；但 kill 只作用于**直接子进程**——若服务器命令是 `cmd /c xxx` / `sh -c xxx` 这类包装，真正干活的孙进程不保证被杀掉。
- **判定**：**知情接受**（v1 有意保守 + 待评估）。文件头注释已声明「如需进程组级清理另起批次」。
- **影响面**：多数 MCP 服务器（npx/uvx 直起）不是包装形态，影响面有限；但用户配置了批处理包装时，禁用服务器后孙进程可能残留占端口。
- **归宿**：转展望（`展望.md` L3）；方向为 Windows Job Object（`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`）或 spawn 包一层 `taskkill /T`，跨平台需分别处理 Unix 进程组。
- **来源**：archive/2026-09-16-consolidation/known-limitations.md §L3
### L4 世界书激发条目 role=system 钳制为 user

- **现状行为**：`role=system` 也会被钳制为 `user`（`server-rs/src/agents/engine/worldbook.rs:29`，注释「role=system 在尾部钳制为 user」）；只有**常驻**条目（位置 3）的 system 才真的拼入 system 文本。
- **判定**：**有意裁剪**。尾部消息流里夹 system 角色在多数 OpenAI 兼容端点上语义不明（有的端点直接拒绝中段 system），钳制为 user 是兼容性最优解。
- **影响面**：ST 生态里激发条目写 system 的卡较少；这些卡在 Kedai 中表现为「注入仍然出现，只是角色是 user」，内容不丢。
- **归宿**：接受（不修）；无补齐方向。
- **来源**：archive/2026-09-16-consolidation/known-limitations.md §L4
### L5 跨 realm 共享全局桥只覆盖 JSON 子集

- **现状行为**：沙箱「每脚本一个不透明源 iframe」下，同角色不同沙箱 realm 之间无法直读 window；共享桥（commit `f2c10d1`，`web/src/sandbox/shared-globals.ts` + `boot-script.ts` 内联镜像 `__kdShared*`）只同步**键为合法标识符且非黑名单、值 JSON 可序列化且 ≤256KB** 的 window 自有属性快照：卡级 realm diff 上报（shared-publish）→ 宿主按角色浅合并持久化 → 广播给同角色订阅沙箱（shared-update）。
- **判定**：**有意裁剪**。函数/DOM 引用/循环结构/超大对象不跨 realm 共享（`JSON.stringify` 失败或超限即静默跳过），黑名单防覆写 window/document/location/fetch 等通信基建与 `__kd` 内部前缀。
- **影响面**：ST 真实环境同页同 realm，脚本间可挂任意函数全局；Kedai 跨沙箱只保证纯数据互通。多数生态脚本（状态栏数据、剧情数据库、消息级降级读）用的正是纯 JSON 对象（如 `window.WuWaShared = {STORY_MAP,…}`），在此子集内可工作。
- **归宿**：接受（不修）；需真函数共享的脚本应改写为数据形态，或等卡级合并单 realm（同段组共享 window）覆盖该场景后迁移到卡级脚本。方向见 `展望.md` 的 L5。
- **来源**：archive/2026-09-16-consolidation/known-limitations.md §L5
### L6 沙箱 draggable 只实现定位与钳制

- **现状行为**：宿主侧 `web/src/sandbox/draggable.ts` 复刻 jQuery UI `.draggable()` 的最小语义：支持 `handle`/`cancel`/`containment:'window'`/`distance`/`cursor` 与 `start`/`drag`/`stop` 回调（`event.ui.position` 经 jq-event 回发）。**未实现** `helper`（克隆/代理元素）、`axis`、`grid`、`snap`/`snapMode`、`revert`、`stack`、`zIndex` 管理，也不支持在 `drag` 回调里改写 `ui.position` 反写回宿主（回调是只读通知；WuWa th-5 的手写边界钳制已由宿主按 `containment` 等价实现）。
- **判定**：**有意裁剪**。生态悬浮窗脚本的拖拽诉求集中在「能拖、不跑出视口、位置能存」，复杂选项在角色卡场景几乎不用；完整移植 jQuery UI 的收益与维护成本不成比例。
- **影响面**：th-3/th-4 有 `typeof .draggable === 'function'` 守卫，缺失时静默跳过；th-5 无守卫——本实现补上后不再 TypeError 中断，是三窗能显示的前提。
- **归宿**：接受（不修）；如需 `helper`/`axis`，可按同一模式在此文件扩展（pointer 事件已在宿主侧，document 级跟踪与 cleanup 登记基建已就绪）。
- **来源**：archive/2026-09-16-consolidation/known-limitations.md §L6
### L7 记忆向量检索：精确 KNN，无 ANN 索引

- **现状行为**：记忆语义召回已落地（`server-rs/src/services/embedding_service.rs` + `memory_service.rs::select_recall_hybrid`），向量存 `vec0` 虚拟表，按「向量×0.7 + Jaccard×0.3」混合打分；但**未建 ANN 索引**，vec0 走精确 KNN。
- **判定**：**有意裁剪**。记忆量级为每角色数百至数千条（受 `memory_max_entries` 约束），精确 KNN 在 5k×512 维下约 1–15 ms，ANN 的召回率损失与索引一致性维护成本不划算。
- **影响面**：换 embedding 模型导致维度变化时，`vec0` 表维度固定无法原地迁移，服务端只记录 `dim_mismatch` 并**保留旧数据**，需用户在设置页点「重建向量索引」（清表 + 全量回填）——刻意不自动重建，避免用户未预期地消耗 API 额度。
- **归宿**：接受（不修）；触发条件为「单角色记忆量突破数万条」，届时启用 `sqlite-vec` 的分区/量化能力（接口层 `select_recall_hybrid` 无需改动）。方向见 `展望.md` 的 L7。
- **来源**：archive/2026-09-16-consolidation/known-limitations.md §L7
### L8 授权：自定义风险级无入口、外部工具区域判定受限

- **现状行为**（`server-rs/src/tools/permissions.rs`、`tools/action_class.rs`）：① `PermissionConfig.classifications`（自定义风险级）字段存在，但全仓无写入通路（无 API、无 UI），插件与 MCP 工具恒按危险级处理（`default_risk` 的未知分支）；② 插件 / MCP 工具的路径区域靠扫描参数中的路径样式（盘符 / UNC / 绝对路径 / `..`）判定：**无路径参数的调用按「非系统路径」处理**，带路径参数则一律按系统路径写/删拦截（无法区分只读与写入，故偏严）。
- **判定**：**待办**。让用户自定义风险级会扩大安全面（把危险工具降级即放开自动执行），需要独立的产品与安全设计，不在授权改造批次内。
- **影响面**：三档授权模式的硬底线（系统路径写/删恒需授权）不因风险级自定义而改变；区域判定偏严会带来「插件的只读调用也被拦截」的体验噪声。
- **归宿**：转计划（`计划.md` L8）；新增 `PUT /api/agent/tool-permissions/classifications` 与设置页入口；区域判定若需更精确，可要求插件/MCP 在工具定义中声明参数语义。
- **来源**：archive/2026-09-16-consolidation/known-limitations.md §L8、archive/2026-09-16-consolidation/授权模式.md §八
### L9 `deep` 模式主生成不启用工具

- **现状行为**（`server-rs/src/api/chat.rs`）：角色扮演四档中只有 `agent`（与 `custom`）向模型下发工具定义；`deep` 主生成无工具。2026-09 授权改造后，`deep` 的**反思轮**已放开 `read`（可查世界书/资料佐证判定），但主生成仍不调用工具。
- **判定**：**有意裁剪**。给 deep 主生成引入只读工具循环会改变其语义（从「一次生成 + 反思」变为多轮工具交互）并显著增加 token 成本，需独立评估。
- **影响面**：deep 用户当前的 prompt 与成本预期是「无工具」，变更需在前端明确标注。
- **归宿**：转展望（`展望.md` L9）；若确有需求，可为 deep 增加近似 agent 的受限只读工具循环（白名单 `tool_sets::READONLY_SCOUT`），沿用 `ToolGate` 闸门。
- **来源**：archive/2026-09-16-consolidation/known-limitations.md §L9、archive/2026-09-16-consolidation/授权模式.md §八
### L10 角色扮演 Agent 记录只恢复工具调用，不恢复推理链

- **现状行为**（`server-rs/src/api/agent.rs` 的 `session_trace` + `web/src/stores/chat.ts` 的 `restoreAgentTrace`）：切会话/重启后，右侧 Agent 面板可恢复 `agent_sessions` 的 state/plan/step_index 与 `tool_calls` 列表，但 `AgentActivity.chain`（推理链步骤明细）只存在于前端 SSE 内存，无持久层，恢复后为空。
- **判定**：**有意裁剪**。推理链是流式过程的逐条快照（`step` 事件），量级大、复用价值低；工具调用与最终产出才是复盘所需。持久化整条 chain 会显著增大写入量而收益有限。
- **影响面**：恢复的 `toolCalls` 一律置 `status='done'`（历史记录不可能处于 running），与实时 SSE 累积的形态区分，避免面板显示永不结束的「执行中」。
- **归宿**：接受（不修）；如需回看推理过程，可在 `agent_sessions.steps` 或独立表记录 `step` 事件（`SseEvent::Step` 已是结构化载荷，落库即可），前端按 `at` 升序回填 chain。方向见 `展望.md` 的 L10。
- **来源**：archive/2026-09-16-consolidation/known-limitations.md §L10
### L11 沙箱 iframe 保留 `allow-modals`，`postMessage` 无法校验 origin

- **现状行为**（`web/src/sandbox/iframe-lifecycle.ts` 的 `sandboxAttributes()` 与 `onMessage`）：iframe `sandbox="allow-scripts allow-modals"`（无 `allow-same-origin`，不透明源）；消息身份校验**仅**为「高熵 nonce + 固定 channel」，不校验 `event.origin` / `event.source`。
- **判定**：**有意裁剪 + 平台限制不可用**（2026-09-12 实测评估）。`origin`/`source` 校验属平台限制：不透明源 iframe 的 origin 恒为 `"null"`（见 `render.ts` 注释），无判别力；而 WebView2 会把跨源 iframe 的 `event.source` 包装成另一个对象，与 `iframe.contentWindow` 不相等——按「不等即拒」会误杀全部正常消息（`scriptRunner.test.ts`「接受 WebView2 source wrapper」已锁定该契约）。故 nonce（128 位随机、仅存于执行闭包、经 URL fragment 交付、不落 DOM/存储）是当前唯一可靠身份凭据。`allow-modals` 属**有意保留**：角色卡作者脚本用 `alert`/`confirm` 做协议确认与提示（赛马娘卡 `submitCreation` 经剪贴板桥回包后 `alert` 弹窗，`sandbox/uma-creation.test.ts` 锁定该链路），移除会让这类卡静默失效，前提是「沙箱内弹窗不触及宿主 DOM/存储」。
- **影响面（安全边界）**：外层仍有站点 CSP、`/sandbox.html` 下发、RPC op 白名单、innerHTML 清洗。当前未发现可实际利用的逃逸路径，故不构成现实漏洞。
- **归宿**：接受（不修）；加固路径（若未来平台支持）见 `展望.md` 的 L11 —— 改用 `MessageChannel` 端口传递（端口对象天然只有双方持有），可彻底摆脱 origin/source 判别与 `'*'` targetOrigin。
- **来源**：archive/2026-09-16-consolidation/known-limitations.md §L11
### L16 MCP 服务器死亡后工具不注销，且无热重连

- **现状行为**：MCP 客户端仅在**启动时**装配（`server-rs/src/mcp/mod.rs:1-5`，改设置需重启生效、无热重连）；服务器进程中途退出时，其工具**不从 `ToolRegistry` 注销**，注册表内这些工具会持续报错直到进程重启。另 `client.rs:252` 的 `read_line` 对服务器单行输出无长度上限。2026-09-13 复核补充：`mcp/client.rs` 已补 **8MB 行长上限**，超限判协议异常并结束读循环；**EOF 注销工具未做**（需改注册表生命周期）。
- **判定**：**待办**（韧性）。
- **影响面**：MCP 服务器崩溃/退出后，模型仍会「看到」它的工具并反复调用失败，浪费轮次与 token；超长行在补齐前曾是内存风险面。
- **归宿**：转计划（`计划.md` L16）；补齐需 EOF 时从注册表注销该服务器全部工具并标记禁用；`read_line` 加最大行长（已部分完成）；孙进程回收见 L3（Windows Job Object）。
- **来源**：archive/2026-09-16-consolidation/known-limitations.md §L16、archive/2026-09-16-consolidation/三结合落实核对表.md §E.3
### L17 Windows 产物无 Authenticode 签名，首装触发 SmartScreen 告警

- **现状行为**：`dist\kedai-server.exe`、`dist\Kedai-portable\Kedai.exe` 与项目根 `Kedai.exe` 均无 Authenticode 签名（实测 `Get-AuthenticodeSignature` → `NotSigned`）；NSIS 安装包同。从网络渠道下载分发时，Windows SmartScreen 弹「Windows 已保护你的电脑」拦截启动。
- **判定**：**有意裁剪**（是否购买代码签名证书属产品决策，当前未购买；自签证书对 SmartScreen 无效）。
- **影响面**：首次安装用户会遇到拦截提示，需手动「仍要运行」；无法把告警完全归零（OV 证书仍需 SmartScreen 信誉积累，非即时消除）。
- **归宿**：接受（不修）；用户指引与转正式签名的证书选型/构建改动要点见 archive/2026-09-16-consolidation/代码签名与SmartScreen说明.md。
- **来源**：archive/2026-09-16-consolidation/known-limitations.md §L17
### L22 同类工具不同参数的空转不被熔断

- **现状行为**：`server-rs/src/utils/loop_guard.rs` 的重复调用熔断按「工具名 + **完整参数**」指纹判定（窗口 8 轮内同一指纹 ≥3 次）。因此它能抓住「同一工具同一参数反复调用」这类真死循环，但**抓不住「同一工具、参数每次略变」的空转**——例如模型连续 54 轮调用 `bash`，每次命令都不同（`ls` → `cat a` → `cat b` → …），指纹各不相同，熔断不触发，只能靠 `max_tool_rounds`（默认 32，可配至 200）兜底。
- **判定**：**有意裁剪**。收窄到「同工具名 >N 次即熔断」会误杀合法工作（真实任务确实可能需要连续执行几十条不同命令）。要可靠区分「空转」与「有进展的多步工作」需要判断**任务状态是否推进**（如结果是否变化、目标是否更近），这属语义级判定，误杀代价高于收益。
- **影响面（2026-09-14 实测数据）**：一次 solo 任务在该形态下跑满 54 轮、耗时 300 秒、累计 prompt 137 万 token（单轮受裁剪约束稳定在 4k–13k，**上下文已收敛**，与 L23 的裁剪失效是两回事），最终正常完成。成本上限只剩 `max_tool_rounds` 兜底。
- **归宿**：转展望（`展望.md` L22）；候选解法为「同工具连续 >N 轮 且 输出连续 K 次无实质变化」双条件，或对 `bash`/`read` 引入「重复读同一目标」的语义去重。`LoopGuard` 已支持自定义窗口/阈值（`LoopGuard::new(window, threshold)`），扩展无需改熔断算法本体。务实缓解：调低 `max_tool_rounds`；perf 门禁（`tools/bench/task-probe.mjs` 的「上下文收敛性」）会提示 prompt 增长是否异常。
- **来源**：archive/2026-09-16-consolidation/known-limitations.md §L22
### L24 无 metrics / OTLP 导出，无 `/metrics` 端点

- **现状行为**：可观测性只做到「结构化日志 + requestId + 访问日志 + health 依赖探测」（见 archive/2026-09-16-consolidation/工程韧性修复-变更说明.md §2.2）。**没有** metrics 计数/直方图、没有 Prometheus/OpenTelemetry 导出、没有 `/metrics` 端点。
- **判定**：**有意不做**（2026-09-15；等价知情接受）。本应用是**本地单用户**形态，没有集中采集端与跨实例聚合需求；引入 metrics 栈（新依赖 + 指标口径设计 + 生命周期管理）的收益需独立评估，不应挂在「可观测性最小骨架」批次里顺手加。
- **影响面**：无集中采集需求，故当前无实际损失。登记此项是为避免后续误判为遗漏。
- **归宿**：接受（不修）；触发条件为「出现『需要计时序指标做容量规划』的真实需求」，届时优先从既有结构化日志派生（访问日志已含 `status`/`duration_ms`，可离线聚合），再评估是否引入 exporter crate。方向见 `展望.md` 的 L24。

### L25 无 down 迁移

- **现状行为**：L18 修复后新增了 `SCHEMA_VERSION` 与「库比代码新则拒绝启动」，但**只做单向**：没有降级脚本、没有升级前自动备份。回滚仍依赖用户手工备份。
- **判定**：**有意不做**（2026-09-15；等价知情接受）。本轮目标是把「库比代码新」从**静默**变**显式**（启动即失败并给出两个版本号），而非提供回滚能力。down 迁移的成本随每次 schema 演进累积（schema 至今只增不减，写降级脚本意味着长期维护两条路径）。

- **归宿**：接受（不修）；若出现「必须让新版库退回旧版 exe 运行」的真实场景，优先做**升级前自动备份**（成本低、覆盖所有降级路径），而非逐版本 down 迁移。方向见 `展望.md` 的 L25 / DB-2。**该首选路径已落地**（2026-09-16，见本文 DB-2「已封堵」）。
- **来源**：archive/2026-09-16-consolidation/known-limitations.md §L25
### L26 事件流无持久化与回放

- **现状行为**：任务事件经 `broadcast` 通道转发为 SSE，接收端滞后（`Lagged`）时**丢弃积压事件**——本轮只把该情况从 `debug` 提为 `warn` 并记录 `skipped` 条数（L21 同批次的 4.2），**没有**改为事件持久化 / 断线续传。
- **判定**：**有意不做**（2026-09-15），属**设计取舍**而非缺口。
- **影响面**：无。前端已有补偿设计：`web/src/stores/task.ts` 的 settle 全量刷新 + 5s 兜底轮询——事件是「提示刷新」的信号，不是唯一事实源，**丢了也能靠 REST 收敛**。事件持久化会引入事件表、保留策略、回放游标三套新机制，与本应用的规模不匹配。
- **归宿**：接受（不修）；若将来出现「必须逐条审计任务事件」的需求，应先评估是否直接查 `task_messages` / `task_llm_calls` 落库记录（它们已是持久事实），而不是新建事件流存储。方向见 `展望.md` 的 L26。
- **来源**：archive/2026-09-16-consolidation/known-limitations.md §L26
### L27 413（请求体过大）未统一为 JSON 错误体

- **现状行为**：批次 1 把畸形 JSON(400)、方法不允许(405)、未知路径(404)统一为 `{error, code}` JSON，**唯独 413 仍是 axum 内建的 `text/plain`**。
- **判定**：**有意保留例外**（2026-09-15；等价知情接受）。根因：`DefaultBodyLimit`（35MB 层）在**提取器被调用前**就由 tower 中间件拒绝，产生 `LengthLimitError`，自研的 `JsonBody<T>` 的 `FromRequest` 根本不执行——要统一 413 形状必须自定义 tower 层拦截 body `Frame` 错误流，改动面覆盖**全站请求体**。
- **影响面**：收益低（体积超限本就罕见，且前端上传前已做体积校验，用户几乎撞不到），成本高（动全站 body 流，回归面大）。
- **归宿**：接受（不修）；若将来 413 真的成为用户可见问题，可在 `DefaultBodyLimit` 之外包一层自定义 `Layer`，把 `LengthLimitError` 映射为 `{error, code}` + 413。原因写在 `server-rs/src/api/json_body.rs` 头部注释。方向见 `展望.md` 的 L27。
- **来源**：archive/2026-09-16-consolidation/known-limitations.md §L27

- **影响面**：模型未按模板输出 END 时不会被判为截断，半截产出可能被当作完整结果。
- **归宿**：转计划（`计划.md` CHG-3）；候选落点为 `classify_subtask_result` 增加「要求 END 的指令 + 末尾缺 END → Truncated」分支。
- **判据修正（2026-09-16 复核，落点方案不成立）**：上述候选落点**不能照字面实现**。模板原文（`agent_tools_agent.rs:39`，agentgo 的 description）是「长度: 目标 ≤ N 字;**若被迫截断，须以单独一行 END 收尾**」+「结果末尾缺 END 即视为截断」——**END 只在截断时才被要求输出，正常完成的产出本来就不带 END**。故「有要求 END 的指令 + 末尾无 END → Truncated」会把**每一次正常完成**判成截断（另有 `prompt.rs:294-298` 的护栏测试锁定「END 只属子任务指令」）。可机器判定的那条判据仍只有 `finish_reason == "length"`。若仍要做，须先重新设计判据（例如仅当「指令显式要求 END」**且**存在其它截断迹象时才降级判定），并接受启发式必然带来的误杀风险；**该重新设计未做**。
- **来源**：archive/2026-09-16-consolidation/任务编排契约与plan模式加固-变更说明.md §4

## 六、数据与迁移风险

### DB-1 无官方降级/回滚路径（部分已变更，仍成立）

- **现状行为**：仍没有 down 迁移（不 `DROP COLUMN`、不重建表），降级仍依赖用户自己的备份（已登记为 L25「有意不做」）。**但「无『库版本 > 代码版本』检测」已不成立**：批次 3 起 `Db::open` 会在建表批前读取 `user_version`，库比代码新时**拒绝启动**并给出两个版本号。
- **判定**：**知情接受**（部分已变更）。把「库比代码新」从静默继续改为启动点显式失败，是**有意**的兼容性变更（副作用：测试版/便携版共用库且一端为旧 exe 时旧端打不开——属期望的更早暴露）。
- **影响面**：回滚仍只能靠用户升级前的手工备份。
- **归宿**：接受（不修）；与 L25 合并处理。
- **来源**：archive/2026-09-16-consolidation/数据库版本与降级行为.md §三 第 1 条
### DB-2 升级前不自动备份（已封堵）

- **现状行为（原）**：`Db::open` 的升级链**没有任何前置快照**。唯一自动快照（`snapshot_database`）只服务于**跨目录搬迁**与**合并**，**不服务于 schema 升级**（实测全仓调用点仅 `migration/merge.rs:72,74` 与 `migration/mod.rs:740` 的测试）。
- **判定**：**已封堵（2026-09-16）**，不属遗留。`Db::open` 在建表批**之前**新增条件快照：`migration/backup.rs::snapshot_before_upgrade` 落 `<data_dir>/backups/kedai-preupgrade-v<旧版本>-<时间戳>.db`（时间戳为唯一性所必需——底层 `snapshot_database` 会删同名目标），保留最近 3 份；**备份失败只记 warn 并继续升级**（硬不变量，否则备份失败会把「能升级」变成「打不开」）。需要升级的判据区分两种 `user_version=0`：**无任何业务表 = 全新库（不备份）**、**有业务表 = 未标记旧库（备份）**——只判 `> 0` 会漏掉后者，而那正是真实用户的升级主路径。
- **影响面（封堵后）**：用户退回旧版 exe 时有自动快照可用，不再完全依赖自己事前的备份。
- **归宿**：接受（已修）；4 例集成测试锁定（含「备份失败不阻断启动」不变量与「快照确是升级前状态」），变异验证三条：改回 `> 0` 判据 / 让失败向上传播 / 对全新库也备份，各使对应用例 FAIL。修复记录见 `功能-变更史.md`。
- **残余**：down 迁移仍不做（已判「接受不修」，见 L25）；「升级前自动备份」是 L25 的首选补齐路径，本项即该路径的落地。
- **来源**：archive/2026-09-16-consolidation/数据库版本与降级行为.md §三 第 2 条

- **判定**：**待验证**（推断未锁定）。
