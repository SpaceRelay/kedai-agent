# 任务引擎六模式(批次 4)

本文档定义任务模式的六种执行模式(语义/契约/复用路径),是 `services/task_engine/`
的设计依据。分层归属:契约在 L1(models/),引擎在 L2(services/task_engine/,
legacy 执行器仍驻 task_service),模式选择 UI 在 L3。

## 一、六模式语义

| 模式 | 语义 | 执行路径 |
|---|---|---|
| `legacy`(默认) | 现有三段式:规划 → 逐步执行 → 汇总。**行为逐字节不变** | task_service/executor.rs 的 run_task_background,原样保留 |
| `solo` | 单主 agent 工具自循环:目标直接进 run_tool_loop,工具全量,步数上限 max_tool_rounds | task_engine/solo.rs |
| `multi` | solo + 子 agent 工具化:主 agent 可经 agentgo 派子 agent(走 run_tool_loop + 工具白名单,agent_depth+1 深度守卫生效) | task_engine/multi.rs(复用 solo 主循环 + tools/agent_tools_agent.rs 的工具化子任务路径) |
| `plan` | 只规划不执行:产出计划进 `planned` 待批准态,零副作用;`POST /api/tasks/{id}/approve`(可携修改后计划)批准后消费已批准计划逐步骤续跑(每步独立 agent 调用 + 汇总);放弃 = stop | task_engine/plan.rs |
| `team` | 规划器拆子目标(全局上限 15)并归并为 2~4 个主 agent,每主领 1~4 个子目标;首版仅自动拓扑(规划器动态决定;**手动拓扑预留,待前端入口批次落地**,见 §五);各主并行跑 solo 循环(主内按子目标逐个独立执行)并可派子 agent;末段审计 agent 做一致性/质量/覆盖度审查(缺漏打回指定主 agent 补做,最多 1 轮;补做后追加一次终审,只产出结论文本不再打回),再升华整合输出最终结果 | task_engine/team.rs |
| `custom` | 复用 AgentFlowConfig/validate_flow/流程库(L2 既有资产),配轻量 step 执行器:只吃 steps+goal,不依赖角色卡/聊天历史;每步按 step.tools 白名单走 execute_generation 或 run_tool_loop | task_engine/custom.rs |

> `tools` 三态(易误配,2026-09-10 实跑修复 F8):`None`=不使用工具,**`Some([])`=全部工具**,
> `Some(list)`=白名单。前端已在「全部工具」及「不生成正文 + 全部工具」组合下加警示文案。

### 工具可用性矩阵(2026-09 授权改造后)

任务模式工具集合由 `task_tool_policy` 编译(见 [授权模式.md](授权模式.md) 第四节),且**恒不等待授权**
(未放行工具立即拒绝为 `tool_policy_denied`)。各模式实际可用工具:

| 模式 | 规划/编排阶段 | 执行阶段 |
|---|---|---|
| `legacy` | 只读侦察 4 个(`tool_sets::READONLY_SCOUT`,≤2 轮) | **无工具**(纯生成) |
| `solo` | 无规划 | 按 `task_tool_policy` 编译的全量集 |
| `multi` | 无规划 | 同 solo(主循环逐字节复用);子 agent 用 `tool_sets::SUBAGENT` 只读白名单 |
| `plan` | 只读侦察 4 个 | 批准后逐步执行,每步按 `task_tool_policy` |
| `team` | 规划/审计/汇总均无工具 | 各主 agent 按 `task_tool_policy` |
| `custom` | — | 按 `task_tool_policy` 编译后再与步骤 `PlanStep.tools` 取交(只能收窄) |

共享白名单常量集中在 `server-rs/src/tools/tool_sets.rs`(单一出处):
`META_TOOLS`(正文元工具 `get_state`/`apply_patch`,永不进正文列表)、`READONLY_SCOUT`、
`SUBAGENT`、`REFLECT`。

> 说明:`multi` 与 `solo` 的主循环参数相同,差异仅在「子 agent 链路」由 `agentgo` 提供——
> 而 `agentgo` 在 solo 的全量集中同样可用。两者的实质区别是模式语义标注与团队协作预期,
> 执行器层面等价。`legacy` 与其余模式的差异则远大于「有无规划阶段」:其执行步骤完全不启用工具。

## 三、引擎复用路径(关键设计决策)

任务模式复用聊天引擎的 `execute_generation` / `run_tool_loop`
(agents/engine/executor.rs),**不建影子 sessions 行**。

决策依据(2026-08-29 代码实测):
- `PRAGMA foreign_keys = ON`,agent_sessions/llm_requests/messages 等表全部
  FK 到 sessions(id);影子行方案需贯穿多张表造影子数据,且 sessions 表会混入
  任务行(聊天列表污染面大);
- `run_tool_loop` 对 agent_session 的依赖仅为状态落库调用,可 `Option` 化;
- runs 互斥登记只在 `AgentEngine::run()` 内,直接调 run_tool_loop 天然绕开,
  任务级互斥由 task_service/cancel.rs 的 token 机制承担(既有)。

最小改动清单:
1. 可见性:`pub(super) mod executor` → `pub(crate)`;`execute_generation` /
   `run_tool_loop` / `ExecutorResult` / `AbortFlag::new` → `pub(crate)`;
2. `run_tool_loop` 的 `agent_session: &AgentSessionRecord` 参数改为
   `Option<&AgentSessionRecord>`(内部 update/add_tool_call 调用点改 if let Some),
   任务模式传 None,聊天路径传 Some(行为不变);
3. llm_requests 落库(execute_generation 内 save_llm_request/save_llm_cache_usage)
   对 `task:` 前缀 session_id 跳过——任务侧调用追踪走 task_llm_calls(批次 3),
   llm_requests 仅聊天链路,避免 FK 失败告警刷屏;
4. 构造顺序:app_state 先建 AgentEngine,再以 `Arc<AgentEngine>` 注入 TaskService
   (engine 不依赖 tasks,无循环);
5. 事件通道:task_engine 自建 mpsc,起 drain 任务把引擎事件映射为
   `SseEvent::Task`(kind=agent_status 等)经 broadcast 转发,并按批次 3 口径
   落 task_llm_calls(phase=agent/subagent/audit);
6. 工具授权:任务模式无 UI 授权上下文,run_tool_loop 的 step_whitelist 恒传
   `Some(&[])`(solo/custom 全量放行)或显式白名单(multi 子 agent),避免
   危险工具 300s 授权等待;TaskService 的 bypass 设置语义不变。

## 四、task_engine 底座

```
services/task_engine/
  mod.rs       TaskEngine 结构体(Arc<TaskService> + Arc<AgentEngine>)、模式派发入口
  sink.rs      引擎事件桥:自建 mpsc 通道 + drain 任务,把引擎事件翻译为任务事件
               (SseEvent::Task kind=agent_status/delta)经 broadcast 转发(非 trait,无 EventSink 抽象)
  executor.rs  ModeExecutor trait:run(ctx) -> TaskOutcome
  context.rs   TaskRunContext(task_id/goal/settings 快照/character_id/cancel)
  solo.rs / multi.rs / plan.rs / team.rs / custom.rs
```

> legacy 派发在 `services/task_service/executor.rs`(按 `TaskRunMode::Legacy` 走
> `run_task_background` 原路径),不在 task_engine 侧;无独立 `legacy_dispatch.rs` 文件。

`ModeSettings` 的每子模式独立覆盖字段(`task_modes`)**为设计预留,尚未落地**:
当前 `services/settings_service/params.rs` 的 `ModeSettings` 无该字段,子模式共享
同一份任务模式设置。后续落地时数值字段默认继承,进 system 的文本字段按
[docs/模式提示词边界.md](模式提示词边界.md) 走类型级隔离 + untrusted 包裹。

## 五、team 模式细化

- 拓扑:首版(批次 4.3b)只做自动拓扑(规划器决定);手动拓扑(用户在 UI 指定
  主 agent 数量/人设/分工,手动优先)预留,待前端入口批次落地;
- 拆目标:规划器输出 ≤15 个子目标,归并映射到 N 个主 agent(自动 N∈[2,4],
  每主 1~4 个子目标;4×4=16 可超 15,全局封顶由解析侧从末位主倒序截断保证);
- 并行:各主 agent 各自跑 solo 循环(独立 TaskRunContext + 派生运行身份),
  主内按子目标逐个独立执行(每子目标一次 agent 调用,各写各自步骤的
  result/status;同一主的多个子目标复用同一虚拟 session `task:{id}:main:{n}`
  保持人设一致),可经 agentgo 派子 agent(深度守卫 agent_depth+1);
- 审计升华:审计 agent 收齐各主产出,做一致性/质量/覆盖度审查;
  发现缺漏 → 打回指定主 agent 补做(最多 1 轮);补做完成后追加一次终审
  (只产出结论文本,不再打回);通过后升华整合为最终结果
  (区别于 legacy 的机械拼接);最终 result 的「## 审计结论」段:
  无打回 = 首次审计结论,有打回 = 终审结论;
- 可观测:主/子/审计/终审全部经 EventSink 落 task_llm_calls
  (phase=agent/subagent/audit/final_audit)并发射 agent_status 事件,
  调用情况面板按模式渲染分工卡 + 审计结论。

## 七、批次 4.3b 落地要点(multi / custom / team + usage 口径)

共享骨架:solo.rs 抽出 `run_agent_loop`(AgentLoopCall{task_id/session_id/goal/
settings/phase/step_index/label}),内含完整 system 组装(EXECUTOR_PROMPT + 人设 +
世界书 + 注入,外部段落一律 untrusted_boundary 包裹)+ run_tool_loop(全量工具,
step_whitelist=Some(&[]))+ record_llm_call 统一出口;solo/multi/team 各主共用。

- **multi**(task_engine/multi.rs):主 agent = solo 同款 run_agent_loop;子 agent
  链路工具化改造(tools/agent_tools_agent.rs 的 run_subtask):engine 就绪时走
  `run_subtask_with_tools`——run_tool_loop + `SUBAGENT_TOOL_WHITELIST`
  (read/search/todo/sleep/calculator/memory_read,写类与编排类剔除,agentgo
  双保险)+ agent_depth+1 深度守卫(子 agent 不得再派子 agent);engine 缺省
  回退纯生成(旧行为)。ToolDeps 以 `OnceLock<Weak<AgentEngine>>/Weak<TaskService>`
  后注入(app_state 构造完成后各 set 一次,Weak 防循环)。**FK 守卫**:
  agent_subtasks 表 FK 到 sessions(id),`task:` 前缀虚拟 session 经
  AgentSubtaskService 内存覆盖层(mem map,不落 DB,与 llm_requests 跳过守卫
  同口径);stop() 末尾 `end_by_session_prefix("task:{id}")` 连带结束全部孤儿
  子 agent。子 agent 事件经 sink.rs(label="子 agent")桥发 agent_status,LLM 调用
  落 task_llm_calls/task_usage(phase="subagent")。并发/截断沿用
  settings.subagent_max_* 参数。
- **custom**(task_engine/custom.rs):取 AgentFlowService::get() 当前启用流程
  (None/未启用 → error 文案提示「请先在设置中启用一个 Agent 流程」),validate_flow
  校验;逐启用 step 顺序执行,plan 步骤名=flow step 名、状态随执行推进;system =
  EXECUTOR_PROMPT(direct)/ CUSTOM_REFLECT_PROMPT(reflect)+ 宏渲染 agent prompt
  后经 untrusted_boundary("flow_step") 包裹 + untrusted_boundary("task_goal", 目标);
  上一步产出串入下一步 user(任务目标全程贯穿);step.tools None → generate_text
  统一出口,Some(list) → run_tool_loop(白名单∩已注册,tool_choice 映射
  auto/none/required/function);每步 record_usage(phase="step", step_index=序号);
  result=末个 generates 步骤产出,含 error 步骤时 status=partial。
- **team**(task_engine/team.rs,首版仅自动拓扑):a) 规划器(TEAM_PLANNER_PROMPT,
  低温度分级重试,parse_team_topology 剥围栏+归并:>4 主归并进第 4 位、每主 >4
  子目标截断、全局 >15 从末位主倒序截断(每主至少留 1)、1 主降级接受)拆 ≤15
  子目标归并 2~4 主,plan 步骤名 `【主Agent-N】子目标名`,phase="planner";
  b) 各主 JoinSet 并行跑 solo 同款循环(独立 run_id、`task:{id}:main:{n}` session、
  AbortFlag、cancel 同源),主内按子目标逐个独立执行(每子目标一次 agent 调用,
  各写各自步骤的 result/status,**同主前序子目标产出注入后续子目标供衔接**,
  同一主复用同一虚拟 session),可派子 agent,主 phase="agent"
  step_index=子目标全局步骤下标,每主完成即推进 plan 步骤 + record_usage;
  c) 审计 agent(TEAM_AUDIT_PROMPT)输出 JSON {通过/打回
  [{main,step?,instruction}]/结论},**parse_audit 解析失败按未通过兜底**
  (审计是质量闸门,读不出明确通过不判通过);有打回且未打过回 →
  指定定位补做(最多 1 轮,`step` 提供时只重跑该主该子目标并**替换其旧版本**,
  缺省整主),补做完成后追加一次终审(TEAM_FINAL_AUDIT_PROMPT,
  phase="final_audit",**结构化 JSON {通过,结论}**,空输出回退首次审计结论);
  d) 升华整合(SUMMARIZER_PROMPT,phase="summary",**输入携带审计结论并要求
  只整合已选定版本、不得另起一版**),result = 整合文本 +
  `\n\n## 审计结论\n` + 审计文本(无打回 = 首次审计结论,有打回 = 终审结论);
  e) 任一主失败,或审计/终审未通过:有产出 partial,全灭 error。
  手动拓扑(用户 UI 指定主 agent 数量/人设/分工,手动优先)预留,待前端入口批次。
- **usage 口径**:solo/plan/multi/custom/team 收尾统一 record_usage(入参
  executor.rs::usage_as_output);phase 命名与 legacy 对齐:planner(规划)/
  agent(主执行)/subagent(子 agent)/step(custom 步骤)/audit/final_audit(team
  终审)/summary;plan 的 AwaitApproval 路径在 approve 续跑完成后由续跑执行器
  (ApprovedPlanExecutor,逐步 phase=agent step_index=步骤下标;汇总复用 legacy
  summarize_task_retry,phase=summarize)补记;legacy 不动。
- **测试钩子**:mock 连接器新增 `[[reply_if:子串|内容]]`(可多条按序取首个命中,
  只查 system 消息,钩子语法自身出现不计命中),支撑 multi/custom/team 集成用例
  按提示词针定向回包。

## 八、2026-08-31 / 09-02 实测修复(截断自愈 / 规划器侦察 / 错误文本 / 孤儿恢复 / 工具历史回灌上限)

五项真实模型实测驱动的行为变化(均带集成测试,tests/tasks.rs):

1. **截断自愈(问题①)**:run_tool_loop 单轮生成被 max_tokens 截断到「不可用」
   (空正文且 finish_reason=length,或任一 tool_call 参数 JSON 非法/连接器流尾
   flush 报「arguments 不是合法 JSON」)时,该轮 max_tokens 翻倍(上限
   `TRUNCATION_HEAL_MAX_TOKENS_CAP = 8192`)原样重发一次;重发仍失败才透出原
   错误。普通文本截断(非空正文)不算,维持「截断仍 done」语义。触发记录经
   `ExecutorResult.self_heals` 透出,任务模式(solo/multi/team/plan 续跑/custom/
   子 agent)补落 task_llm_calls 标注行(status=error,response_summary 含
   「(截断自愈)…重发」),调用情况面板可见完整链路。legacy 路径的空输出分级
   重试(plan/step/summary 无工具纯生成)是既有同问题不同层机制,不受影响。
2. **规划器只读侦察(问题②)**:legacy 与 plan 共用的 plan_task 在产出计划 JSON
   前允许先调用只读白名单工具收集信息(`PLANNER_SCOUT_TOOLS = read/search/
   memory_read/calculator`,∩ 已注册工具;严禁写操作与编排类,agentgo/agentend/
   run_subtask 天然不在名单)。侦察轮上限 `PLANNER_SCOUT_MAX_ROUNDS = 2` 轮,
   随后最终轮不带工具强制产出计划 JSON(计划契约不变);模型幻觉白名单外工具
   名时回填拒绝错误 JSON 不执行;侦察轮失败(如协议异常)回退无工具直接规划,
   不沉任务。侦察轮与计划轮均经 generate_text 统一出口落 task_llm_calls
   (phase=planner);PLANNER_PROMPT 已加入「信息不足可先调用只读工具」指引。
   team 规划器(plan_team)维持无工具单次生成,未启用侦察。
3. **步骤 error 文本落库(问题③)**:步骤失败时失败原因与 status=error 同一次
   set_plan 落库,不得只置状态不留文本。ApprovedPlanExecutor(plan.rs)与 team
   主循环(team.rs run_mains_parallel)两条路径同口径;错误文案带 finish_reason
   /截断定性(如「返回空内容(finish_reason=length)」「工具参数 JSON 截断
   (已达 token 上限,提高预算重发仍失败)」),前端步骤卡可读。
4. **孤儿任务恢复(问题④)**:TaskService 构造(AppState 装配,Db::open 之后)
   时把上次进程遗留的 running/planning 任务置 ended 终态 + error 文本
   「服务重启,任务中断」,并逐个发射 status 事件(先写库后发射);planned
   (待批准,approve 续跑语义可跨重启存活)、pending 与终态不动;幂等
   (重复执行零命中)。db.rs::recover_orphan_tasks 专测覆盖「插 running 行 →
   重开库 → 断言终结」。
5. **工具循环历史回灌上限(R3b,2026-09-02 实测)**:run_tool_loop 此前每轮
   全量回灌 assistant/tool 交替历史,3 步任务 prompt 3,119 → 26,679 token
   无界膨胀。现每轮 execute_generation 前执行 trim_tool_history
   (engine/messages/trim.rs),按「assistant(带 tool_calls)+ 后续连续 tool
   消息」分轮,keep-recent + 预算双闸门在「轮」粒度操作:完整轮数超出
   `tool_history_keep_rounds`(默认 4,钳 1..=32)时,最老轮的 tool 结果原地

## 十一、team 纯生成点截断自愈(2026-09-03 真实模型复验驱动)

实测 team 全链路(DeepSeek 推理模型,default_max_tokens=1024)发现:审计
agent 的 reasoning 烧光预算,finish_reason=length 产出腰斩 JSON
(`{"通过":false,"打回":[{"main":2`),腰斩原文直接进最终 result 的
「## 审计结论」卡——既难看又误导(parse_audit 虽按通过兜底不沉任务,
但结论=原文的旧语义把协议残片暴露给了用户)。

根因:solo/custom 的截断自愈在 run_tool_loop 层,而 team 的审计/终审/汇总
是 generate_text 直调点,不在自愈覆盖内。修复(team.rs):

1. **generate_text_healed 包装**:审计/终审/汇总三处统一走新出口——先按
   原预算调 generate_text,finish_reason=length 时预算翻倍重发一次
   (纯函数 `trunc_heal_budget` 决策,封顶 TEAM_RETRY_MAX_TOKENS_CAP)。
   两次调用均经 generate_text 落 task_llm_calls,调用情况面板可见
   「截断 → 提高预算重发」链路;token 用量与 record_usage 两次都入账
   (与 solo 自愈留痕同口径),并发 agent_status 事件告知前端。
2. **腰斩 JSON 末层兜底**:parse_audit 对「以 `{` 开头但解析失败」的
   截断形态不再把原文塞进结论段,改为干净说明「(审计输出不完整,按通过
   兜底)」,原文前 120 字符记 warn 日志备查;纯文本回复维持旧语义
   (结论=原文)。

测试:team.rs `trunc_heal_budget_only_on_length`(仅 length 触发/翻倍/
封顶/越顶不触发)、`audit_truncated_json_fallback_clean_conclusion`
(腰斩 JSON 兜底通过、结论段不含 `{`)。

## 十二、2026-09-10 六模式实跑修复(F1~F8)

隔离数据目录 + 真实 `deepseek-flash` 对六模式各跑「创建 → run → 多轮 followup」,
plan 补跑 plan-chat → approve → followup,依据实测暴露的 8 个问题修复:

1. **F1 custom 非生成步骤产出正文**(custom.rs):`generates=false` 的 direct 步骤
   此前复用 `EXECUTOR_PROMPT`(「直接输出最终结果」),无视步骤自身「只做内部规划」
   而吐出完整正文,并被下一步原样回显。现改用新常量 `TASK_INTERNAL_PLAN_PROMPT`
   (只做分析规划、不产出正文),其产出加「(内部规划)」标注、仅供后续步骤参考、
   不计入最终成果(`draft` 仅由 `generates=true` 步骤产出)。
2. **F2 任务模式注入污染**(`task_prompt_inject_enabled`,默认 false = 隔离):
   角色扮演的 `prompt_floors.json` 文章要求(1200 字/第三人称/禁词表)此前注入任务
   执行/汇总/followup 轮次,与任务目标对抗(实测「压缩到 200 字」后结果反涨)。
   三处消费点(legacy 步骤/汇总、solo 主循环)加开关守卫;预览层同步门控。
3. **F3 记账缺口**(一致性口径):凡落 `task_llm_calls` 的调用都补落 `task_usage`——
   规划器侦察轮、截断自愈 heal 行、规划失败重试轮、步骤/汇总首调空输出轮次。
   新不变量(集成测试锁定):`/calls` 各行 token 求和 == 详情 `usage_total`。
4. **F4 plan 续跑步数矛盾**:approve 组 goal 追加约束句「步骤数量与内容一律以本
   清单为准」,修用户经 plan-chat 改步数后汇总仍沿用原始目标旧步数的矛盾
   (实测「标题三步、正文两步」)。
5. **F5 followup 重写模式**(`mode: append|replace`,缺省 append 向后兼容):
   append 无法表达「压缩/重写/改前面」;replace 用新产出整体替换 result
   (段标「修订 N」),前端追加条加模式选择。
6. **F6 带工具轮 finish_reason 落空串**（sse_parser.rs）:finish_reason=tool_calls 时
   在 flush 工具调用后同样产出 `Finish{tool_calls}`,调用面板 finish 列不再空白;
   截断自愈只认 length,行为不受影响。
7. **F7 legacy 前端子任务区重复**(TaskBoard.vue):legacy 的 subtasks 与计划步骤
   同源,前端两区各渲染一次;现 legacy 不渲染子任务区(multi 照常)。
8. **F8 tools 空数组陷阱**(前端提示):`tools: []` 语义是「全部工具」而非「不使用」,
   AgentFlowSection 在「全部工具」及「不生成正文 + 全部工具」组合下加警示
   (纯函数 `stepToolsWarnings`,单测覆盖)。
