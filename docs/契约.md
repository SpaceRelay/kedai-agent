## HTTP API

> 本节是 `archive/2026-09-16-consolidation/API.md` 的**逐端点全文移植**。字段名、类型、取值域、默认值、状态码、错误语义、示例一律按原文；本节末尾另附 `MAINTENANCE.md` §6「维护红线路由总表」（含 API.md 未列的若干事实，如 `/api/token/count` 的「每条 +4、末尾 +2」）。

### 通用约定

- 基地址：开发模式 `http://127.0.0.1:3001`（前端经 Vite 代理 `/api`）；生产模式同域。
- 所有请求/响应均为 `application/json`（除文件上传与 SSE 流）。
- 除 `/api/health`、`/api/bootstrap` 与 `/api/avatars/*` 外，API 请求必须携带服务启动时生成或由 `KEDAI_API_TOKEN` 固定配置的 Bearer token；非 loopback 监听还必须显式设置 `KEDAI_ALLOW_REMOTE=1`，且固定 token 至少 32 字符。
- 运行时主 Agent 提示词统一来自 `DATA_DIR/AGENTS_RUNTIME.md`，不是仓库开发用 `AGENTS.md`。
- 全部时间字段为 ISO 8601 字符串。

### 聊天

#### POST `/api/chat/send` — 发送消息，触发 Agent 全流程

**请求体**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `message` | string | ✅ | 用户消息（去空） |
| `session_id` | string | 条件 | 目标会话；与 `character_id` 二选一（缺省时取该角色首个会话/自动创建） |
| `character_id` | string | 条件 | 目标角色 |
| `agent_mode` | `"fast" \| "deep" \| "agent" \| "custom"` | 否 | 默认 `fast`；`deep` 启用完整计划-执行-反思；`agent` 同 deep + 工具循环；`custom` 按「Agent 执行流程」配置的步骤序列执行（需先在设置中启用并保存，否则 400） |
| `temperature` | number | 否 | 默认取运行期设置（初始 0.8） |
| `top_p` | number | 否 | 默认取运行期设置（初始 0.9） |
| `max_tokens` | number | 否 | 默认取运行期设置（初始 1024）；simple 字数注入启用且字数要求更高时自动上调（需 = min(字数×2+512, 8192)） |
| `resend_message_id` | integer | 否 | 编辑后重发锚点；服务端仅接受当前会话最后一条、角色为 `user` 且正文与 `message` 一致的消息，否则返回 409 |

**响应**：`text/event-stream` SSE。事件类型：

| 事件 | 负载 | 说明 |
|---|---|---|
| `step` | `{step, detail?}` | Agent 步骤（计划中/执行中/生成中/反思/出错…）；custom 模式额外携带 `{index, total}`（第几步/共几步），fast/deep/agent 不带 |
| `token` | `{text}` | 文本片段（逐字渲染） |
| `tool_call` | `{name, input}` | 工具调用预告 |
| `tool_result` | `{name, output}` | 工具结果 |
| `vars` | `{stat_data}` | 酒馆助手变量树同步：模型回复中的 `<UpdateVariable>` 补丁被应用后推送最新 `stat_data`（仅变量更新时出现，先于 `finish`） |
| `interrupted` | `{}` | 被停止 |
| `finish` | `{usage, content}` | 结束，含 usage（`prompt/completion/total/context_tokens`）；`content` 已剥离 `<UpdateVariable>` 协议块 |

**错误**：400 消息为空；404 会话不存在；409 会话正在生成中；400 custom 模式未启用/流程未保存或非法。

> **对账提示**：`types.rs` 的 `SseEvent` 另有 `error` / `tool_authorization_required` / `task` 三个变体与 `finish.finish_reason` 字段，本表（API.md 原文）未列出——完整清单见「SSE 线格式」一节。

#### POST `/api/chat/stop` — 停止当前生成

请求：`{ "session_id": string }` → `{ "ok": true }`

#### GET `/api/chat/history?session_id=…` — 消息历史

响应：`{ "messages": [{ id, session_id, role, content, extra, created_at }] }`

> 酒馆助手：assistant 消息 `extra.mvu = { stat_data }` 携带当轮更新后的变量树快照（仅变量更新时），前端按消息顺序回放即可得到会话最新状态；`content` 为剥离 `<UpdateVariable>` 块后的干净文本。**纯变量更新消息（正文为空）同样落库**（带快照），保证刷新/回放不把变量树回滚到更新前。

#### PUT `/api/chat/messages/:id?session_id=…` — 编辑消息

请求：`{ "content": string }` → 更新后的消息

#### DELETE `/api/chat/messages/:id?session_id=…` — 删除消息

成功 → `204`

#### POST `/api/chat/clear` — 清空会话（保留角色定义）

请求：`{ "session_id": string }` → `{ "ok": true }`

### 设置

#### GET `/api/settings` — 读取运行期设置（API Key 脱敏）

响应：`{ openai_base_url, api_key_masked, has_api_key, model, default_temperature, default_top_p, default_max_tokens, max_context_tokens, agent_system_prompt, search_endpoint, mvu_vars_position, reflect_prompt }`

#### PUT `/api/settings` — 更新运行期设置（部分字段）

请求（任意子集）：`{ openai_base_url?, openai_api_key?, model?, default_temperature?, default_top_p?, default_max_tokens?, max_context_tokens?, agent_system_prompt?, search_endpoint?, mvu_vars_position?, reflect_prompt? }`

### Agent 执行流程（custom 模式）

流程为**全局流程库**（持久化 `data/agent_flows.json`）：可保存多个流程、切换当前选中、导入导出。所有响应统一携带：

- `library`: `{ current_flow_id: string|null, flows: [流程…] }` — 完整流程库
- `config`: 当前选中流程（无选中时为 `null`，兼容旧调用方）

单个流程：`{ id, name, description?, enabled: bool, steps: […] }`；步骤字段：`{id, name, enabled, goal, action, generates?, system_prompt?, temperature?, max_tokens?, tools?}`。

`tools` 语义：`null`/缺省 = 该步不使用工具；`[]` = 全部工具；`[name…]` = 白名单（按注册名过滤）。

#### GET `/api/agent-flows` — 读取流程库

响应：`{ ok, library, config }`。

#### PUT `/api/agent-flows` — 保存（创建或更新）流程并设为当前选中

请求：`{ config: {…单个流程} }` → `{ ok, library, config }`。`config.id` 为空/缺省视为**新建**（后端分配 id）；id 已存在则覆盖该流程。适合「保存」「新建」「导入」「复制」。

#### POST `/api/agent-flows/select` — 切换当前选中流程

请求：`{ id }` → `{ ok, library, config }`；id 不存在 → 400。

#### DELETE `/api/agent-flows/{id}` — 删除流程

→ `{ ok, library, config }`；删除当前选中流程时自动回退到第一个；id 不存在 → 400。

校验（`enabled=true` 时）：步骤非空且至少一条启用；至少一个 `action=direct` 且 `generates=true`；`action` 仅 `direct|reflect`；reflect 步不得带 `generates=true` 与 `system_prompt`；温度 0–2；输出上限 1–32768。失败 → 400 中文错误；`enabled=false` 时允许保存任意状态（先编辑后启用）。

#### 数据迁移

旧版单流程格式 `{ enabled, steps }` 首次加载自动迁移为流程库（旧步骤保留，`name="默认流程"`）；从未编辑过的空配置替换为内置「文学创作协调流程」。文件缺失时同样注入内置流程，开箱即用。

#### custom 模式执行语义

- 步骤按 `enabled=true` 顺序执行；每步 `system_prompt` 经酒馆宏展开后追加 `[本步指令]` 到 system 末尾（独立消息视图）。
- `{{setvar}}`/`{{addvar}}` 在每步生成后持久化到会话变量，后续步骤可用 `{{getvar}}` 读取（跨步骤状态传递）。
- 步骤级 `temperature`/`max_tokens` 覆盖全局参数；`tools` 决定该步工具可见性（agent 模式整体下发全部工具，custom 按步控制）。
- `POST /api/agent/plan` 支持 `agent_mode=custom`：返回流程摘要「自定义流程：共 N 步」与各步骤名称。

> 来源：`archive/2026-09-16-consolidation/任务引擎六模式.md` §九第 1 条（「GET /api/tasks/{id} 响应新增 `messages` 数组（created_at 升序；无消息任务为空数组，前端零特判）」）。

#### POST `/api/tasks/{id}/followup` — 终态追加指令（done/partial/error/ended 可追加，solo 续跑续写成果）

请求体 `{ content, mode? }`：`mode` 缺省/空 = `append`（新产出以「追加 N」段附加进
`result`，保留原文）；`replace` = 用新产出整体替换 `result`（段标「修订 N」，用于
「压缩/重写/改前面」类指令）；未知值 400（VALIDATION）。

**校验顺序与 code（来源：`archive/2026-09-16-consolidation/任务引擎六模式.md` §九）**：
空指令 400（VALIDATION）→ 不存在 404（NOT_FOUND）→ 非终态 409（CONFLICT；仅
`done`/`partial`/`error`/`ended` 可追加，`running`/`planning`/`planned`/`pending` 拒绝）
→ service 层复核（竞态失败同样 409）。

**链路与终态映射**：用户指令落 `task_messages`（kind=followup, role=user）→ 任务回 `running`
→ spawn 续跑（不经 TaskEngine 派发；收尾语义为 append 而非覆盖）→ 产出落 assistant 消息并
append 进 `result`（分隔段 `\n\n---\n\n**追加 N：**指令概要（截 80 字符）\n\n` + 产出；
N = followup 序号，即 kind=followup 的 user 消息计数）→ 终态映射：原 `partial` 保持 `partial`
（失败步骤历史不抹平），`done`/`error`/`ended` 追加成功后回 `done`。取消/失败与 legacy 同款
`finalize_run` 收尾（stop → `ended`，失败 → `error` 文本）。**事件纪律**：消息落库不发射独立
事件，生命周期复用既有 `status` 事件（running → done/partial），前端经事件驱动重拉详情携带
`messages`；**不引入新事件 kind**。

#### POST `/api/tasks/{id}/plan-chat` — 批准环节规划对话（planned 态按反馈修订计划）

请求体 `{ message }`。**校验顺序与 code（来源：`archive/2026-09-16-consolidation/任务引擎六模式.md` §十）**：
空反馈 400（VALIDATION）→ 不存在 404（NOT_FOUND）→ 非 `planned` 409（CONFLICT）→
LLM 上游/解析失败 502（UPSTREAM）；修订期间 stop 竞态中断按 409。

**链路**：用户反馈落 `task_messages`（kind=plan_chat, role=user）→ 规划器修订（同步等待；
`register_cancel` 登记使 stop 可中断）→ `set_plan` 替换（发射 `plan` 事件）→ `planned` 态
`result` 计划清单文本同步刷新（「计划已修订，共 N 步：…」，`set_planned_result`）→ assistant
修订说明落库（「计划已修订，共 N 步：步骤名清单」，名清单截 200 字符）→ **重发
`approval_required` 事件**（前端据此刷新批准区）。与 followup 不同：plan-chat 是同步 handler
（`planned` 态无并发执行，响应直接携带修订后计划），不经 `tokio::spawn` 后台化。

**修订提示词**：system = `PLANNER_PROMPT` + 世界书 + 修订指引段（新常量
`PLANNER_REVISE_GUIDANCE`，含独特词「计划修订指引」，mock 测试据此经 `[[reply_if:]]` 区分

请求：`{ messages: [{role, content}], character_id?, temperature?, top_p?, max_tokens? }`
（role 仅 `system`/`user`/`assistant`；条数 ≤200、单条 ≤64KB、总长 ≤256KB）。
提供 `character_id` 时按该角色世界书做关键字匹配注入（常驻条目置顶、触发条目插到最后

响应：`{ ok: true, text, injected: string[] }`。`injected` 为本次注入的世界书条目
comment 清单——卡片诊断时用它区分「世界书未注入（`injected` 为空）」与「输出被截断
（`text` 偏短）」两类不同故障。

**预算与截断自愈**（常量见 `server-rs/src/api/chat.rs`）：

- 未显式指定 `max_tokens` 时取「用户设置 vs 8192（`GENERATE_RAW_MIN_TOKENS`）」的较大者
  ——结构化输出下限：卡片要求「整个回复有且仅有一个 JSON」，1024 默认值会把 JSON 腰斩
  （2026-09-13 Android「掉格式」根因）；显式值原样尊重并钳在 `1..=65536`，
  `max_tokens: 0` 返回 400 `VALIDATION`；
- 上游 `finish_reason=length` 时预算翻倍重发（封顶 32768，最多 2 次）；
- **重发失败或自愈用尽时仍返回 200 + 最后一次（半截）文本**：卡片自带解析器可从半截
  文本尽力提取，整体报错反而更无用；此时错误只留服务端日志
  （`generate_raw_retry_failed_fallback_partial` / `generate_raw_still_truncated`）。

**已知限制**：客户端断开不取消在途重发（最多 3 次上游调用）；本端点不落 usage/审计，
重发消耗只能从服务端日志统计。

### 契约引擎 HTTP 出口（方案 A）

供 ST 前端与外部工具调用同一契约引擎（与 Agent 多步工具 `apply_patch` 共用同一管线，单库无分叉）。契约不存在时补丁原样放行（存量卡零行为变化）。

> **并发语义**：本出口与 Agent 生成共用存储；外部更新应避免与进行中的生成并发调用，并发时运行态快照以引擎收尾为准（变量表不丢，快照可能短暂回退）。`writer` 是子系统标识而非身份认证——持有 bearer token 的调用方可任意声明 `writer`（含 `"agent"`）；所有权校验防的是「子系统误写」，认证边界在 token（与前端同级信任）。

#### POST `/api/variable/update` — 契约引擎统一写入

请求：`{ session_id, patches: [{ op, path, value?, from?, confidence? }], writer? }`

- `patches`：JSON Patch 子集（replace/set/insert/delta/remove/move）；`confidence` 可选（"low"/"medium"/"high"，非法值按 low 处理——不写入、进待复核队列）；
- `writer`：写者子系统 id，缺省 `"external"`；契约 `updateRules` 的 `ownership.writers` 须包含该 id 或 `"*"`（默认 `[agent, manual]`），否则 `not_owner` 拒绝；
- 门控：未声明字段 `unknown_field` 拒绝、低置信入 pending、契约生效时逐 op 留痕（kaleido_changelog）并维护 meta.pending。

响应（部分被拦仍 200，已生效部分生效）：`{ ok, stat_data, entries, warnings?, breaker_hashes? }`；`ok=false` 表示全部被拦（树未变；低置信场景提议已入队，全部被拒场景无任何写入）。请求体结构不符 → 422。

#### GET `/api/variable/state?session_id=…` — 契约运行态整行

`{ session_id, contract_version, stat_data, meta, revision_seq, revision_hash, updated_at }`；尚无契约运行态 → 404。

#### GET `/api/variable/changelog?session_id=…&limit=50` — 逐 op 变更流水

`{ entries: [ChangelogEntry] }`（最新在前，limit 夹取 [1, 1000]）。

### 命令执行（exec 端点）

来源：`archive/2026-09-16-consolidation/命令执行层与Android三档执行器-变更说明.md` §一「新增 API」；实现 `server-rs/src/api/exec.rs`。该批次**不改既有 API 线格式**（仅新增 exec 端点）、**不改既有 DB schema**（仅新增 `exec_audit` 表）。

| 端点 | 说明 |
|---|---|
| `GET /api/exec/tier` | 当前执行器等级 + 中文标签 |
| `GET /api/exec/audit?limit&source&risk` | 审计列表（时间倒序，limit 上限 500） |
| `DELETE /api/exec/audit` | 清空审计 |

**`GET /api/exec/tier` 响应**：`{ "tier": <等级>, "label": <中文标签> }`。等级取值 `root` / `shizuku` / `sandbox` / `disabled`（`ShellTier::{Root,Shizuku,Sandbox,Disabled}` 的 `as_str`）；中文标签分别为 `ROOT 提权` / `Shizuku(ADB 权限)` / `沙箱(应用自身权限)` / `已禁用`。前端授权面板据此展示「等级可见」并可提示用户开启通道。

**`GET /api/exec/audit` 响应**：`{ "entries": [ExecAuditEntry…] }`。query 参数全部可选：`limit`（缺省 100，实现侧 `clamp(1, 500)`）、`source`（`chat | task | android`）、`risk`（`safe | sensitive | destructive | admin`）；过滤值空串视为不传。排序 `ORDER BY ts DESC, id DESC`。

**`ExecAuditEntry` 字段**（线格式与前端 `web/src/api/exec.ts` 对齐，机检映射 7）：
`{ id, ts, source, task_id, session_id, command, shell, tier, risk, decision, exit_code, stdout_summary, stderr_summary }`；
其中 `task_id` / `session_id` / `exit_code` 可为 null；`decision` ∈ `allowed` / `denied`。

**`DELETE /api/exec/audit` 响应**：`{ "ok": true, "deleted": N }`；DB 失败 → `{error, code: DB}` + 500。

**审计写入纪律**（同源文档「审计」段）：`exec_audit` 表字段为
`id, ts, source(chat|task|android), task_id, session_id, command, shell, tier, risk, decision, exit_code, stdout_summary, stderr_summary`；
**每次尝试都落一行，含被拒绝的**——「有人试图跑 rm -rf」同样要留痕；输出摘要截断 2000 字符，避免审计表被长输出灌爆。

**工具面契约（同源文档「新增工具」段）**：工具名 `bash`，参数 `command`（必填）/ `cwd` / `timeout_ms`；平台默认 shell：Windows 用 `cmd /c`，其他平台用 `sh -c`；风险恒 `Dangerous`；**不加入任何只读白名单**（READONLY_SCOUT / SUBAGENT / REFLECT）。命令分级四级 `safe` / `sensitive` / `destructive` / `admin`，多命令串联逐段判定取最高危；`destructive`/`admin` 命令**逐条确认，不受任何授权豁免**（判定链最前）。

### 健康检查

#### GET `/api/health`

`{ ok: true, ts }`

**完整响应形状（源：`server-rs/src/api/mod.rs:110-153`；`archive/2026-09-16-consolidation/MAINTENANCE.md` §4/§6）**：

```
{ ok, ts, version, build_id, build_time, data_dir, dependencies: { db } }
```

- `ok` **恒 true（liveness 冻结点）**：`src-tauri` 的 `health_ok()` 以此字段判定「已有实例在运行」，用于单实例复用/端口竞态，**不得改为依赖态**。
- `ts` 为 `chrono::Utc::now().timestamp_millis()`。
- `version` = `CARGO_PKG_VERSION`；`build_id` = 编译期注入的 `env!("KEDAI_DIST_HASH")`；`build_time` = `env!("KEDAI_BUILD_TIME")`。
- `data_dir` 供桌面壳/启动器复用已运行实例前校验指向同一数据目录，防止静默挂到另一套库。
- `dependencies.db`：db 不可用时置 `"error"`，但 `ok` 仍为 true（依赖降级 ≠ 进程不活）。
- 查询参数：`?deep=1`（或 `deep=true`）触发整库 `PRAGMA quick_check`（大库代价高，仅显式触发；跑在 `spawn_blocking` 里，避免阻塞 tokio worker）；缺省走轻量探测。
- 设置中心底部常驻显示「版本 · 构建时间 · 指纹前 8 位」，两端各开一次对比即可肉眼确认同步。

**构建指纹 sidecar 契约（源：`archive/2026-09-16-consolidation/MAINTENANCE.md` §4「两版同步机制（构建指纹）」）**：
每个 dist 产物旁边写 `<exe>.build.json`（`{version, build_time, dist_hash}`，算法见 `tools/Write-BuildStamp.ps1`）；
`start.ps1` 与图形启动器（`Kedai.exe`，源码 `launcher/`）启动前比对两端 sidecar 的 `dist_hash`，不一致自动执行 `build.ps1` 双端重建。

> **注意（不要直接比对）**：二进制内嵌的 `build_id`（`KEDAI_DIST_HASH`）与 sidecar 的 `dist_hash` **算法不同，不可直接比对**——前者为 FNV-1a 64-bit，后者为聚合 SHA256（见 `契约-协议与配置.md`「二进制内嵌 `build_id`」条）。

#### SSE 事件格式（chat/send）

```
data: {"type":"step","step":"计划中…","detail":"..."}\n\n
data: {"type":"token","text":"片"}\n\n
data: {"type":"tool_call","name":"calculator","input":{...}}\n\n
data: {"type":"tool_result","name":"calculator","output":{...}}\n\n

data: {"type":"finish","usage":{prompt_tokens,completion_tokens,total_tokens,context_tokens},"content":"..."}\n\n
```

- 格式：`data: {json}` + 空行，`type` 编码在 JSON 内，无 `event:` 字段

- 全部时间字段为 ISO 8601 字符串

## SSE 线格式

### 帧格式（两条流共用）

- 格式：`data: {json}` + 空行（`\n\n`）。
- 事件类型（`type`）**编码在 JSON 体内**，**无 `event:` 字段**；SSE 规范中的 `event:` 行从不出现。
- 前端按 `type` 分派；`kind`（任务流内层分类）与 `type` 是两个层级：任务流的 `type` 恒为 `task`，分类在 `kind`。
- 客户端断开时自动中断生成（engine 检测 mpsc send 失败）。

### 聊天流（`POST /api/chat/send`）

`SseEvent` 的 serde 属性为 **`#[serde(tag = "type", rename_all = "snake_case")]`**（`server-rs/src/models/types.rs:458-459`），因此每个变体名折算为 snake_case 后即 `type` 字面值：

| `type` 字面值 | Rust 变体 | 负载字段 | 说明 |
|---|---|---|---|
| `token` | `SseEvent::Token` | `text: String` | 文本片段（逐字渲染） |
| `step` | `SseEvent::Step` | `step: String`；`detail?: String`；`index?: usize`；`total?: usize` | Agent 步骤；`detail`/`index`/`total` 均 `skip_serializing_if = "Option::is_none"`（None 时字段整体省略）。`index`/`total` 为 custom 模式步骤进度，其余模式不携带 |
| `tool_call` | `SseEvent::ToolCall` | `name: String`；`input: Value`；`call_id?: String`；`render_kind?: String` | 工具调用预告；`render_kind` 为「工具展示意图（render intent）」，前端据此分派渲染，缺省走 JSON 直出 |
| `tool_authorization_required` | `SseEvent::ToolAuthorizationRequired` | `name: String`；`risk: ToolRisk`；`reason: String`；`run_id: String`；`call_id: String` | 工具未获授权因而**没有执行**；前端据此提供会话/角色授权入口。全部字段必填（无 skip_serializing_if） |
| `tool_result` | `SseEvent::ToolResult` | `name: String`；`output: Value`；`call_id?: String`；`render_kind?: String` | 工具结果 |
| `vars` | `SseEvent::Vars` | `stat_data: Value` | 酒馆助手变量树同步（每次应用 `<UpdateVariable>` 补丁后推送最新 `stat_data`；仅变量更新时出现，先于 `finish`） |
| `interrupted` | `SseEvent::Interrupted` | 无 | 被停止 |
| `error` | `SseEvent::Error` | `code: String`；`message: String`；`retryable: bool` | **顶层生成错误终态**：模型失败/上游错误时发送，取代「空内容 `finish` 伪装正常结束」；前端据此展示错误而非「完成」。`retryable` 表示是否可重试（网络类可重试，鉴权/参数类不可） |
| `finish` | `SseEvent::Finish` | `usage: TokenUsage`；`content: String`；`finish_reason?: String` | 结束；`content` 已剥离 `<UpdateVariable>` 协议块。`finish_reason` 为上游 `finish_reason`（`stop` / `length` / `content_filter` 等），`length` = 输出被 `max_tokens` 截断；`None` 时序列化省略（旧客户端忽略未知字段即可，线格式向后兼容） |
| `task` | `SseEvent::Task` | 见下「任务事件流」 | 任务模式事件（同时由 `GET /api/tasks/events` 转发为 SSE） |

**`TokenUsage` 线格式**（`server-rs/src/models/types.rs:247-260`）：

```
{ prompt_tokens, completion_tokens, total_tokens, context_tokens,
  prompt_cache_hit_tokens, prompt_cache_miss_tokens }
```

`prompt_tokens` / `completion_tokens` / `total_tokens` / `context_tokens` 为 `i64`（必填）；`prompt_cache_hit_tokens` / `prompt_cache_miss_tokens` 带 `#[serde(default)]`，无缓存字段的提供商恒为 0。`MAINTENANCE.md` §6 的示例帧只列前四个键（`prompt/completion/total/context_tokens`），后两个为后续新增且缺省有值——旧客户端按前四键读取不受影响。

**`SseEvent::Error.code` 五个冻结值**（来源：`archive/2026-09-16-consolidation/工程韧性修复-变更说明.md` §2.4「验收证据」）：

```
request_timeout / rate_limited / auth_failed / upstream_error / generation_failed
```

> 同节明确：`[G]` 类改造**不影响线格式**——这五个值**冻结不变**；`tests/api_integration.rs` 的
> `assert_eq!(err["code"], "request_timeout")` 与 `retryable == true` **原样通过**；`check-contract.mjs` exit 0。
> `types.rs` 的 `code` 字段 doc 注释举的三个例子（`upstream_error` / `request_timeout` / `tool_loop_failed`）
> 与上述冻结五值**并非同一清单**【待核实】（见文末「源文档之间的不一致」第 3 条）。

### 任务事件流（`GET /api/tasks/events`）

任务事件由 `TaskService` 的 broadcast 通道推送，该端点转发为 SSE，取代前端 1s REST 轮询。
`SseEvent::Task` 的**全部字段除 `task_id` 外均为可选**（`#[serde(default, skip_serializing_if = "Option::is_none")]`），旧客户端缺字段即忽略（向后兼容）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `task_id` | String | 必填 |
| `kind` | `TaskEventKind`（可选） | 事件分类（见下表） |
| `title` | String（可选） | 任务标题 |
| `status` | `TaskStatus`（可选） | 任务状态 |
| `detail` | String（可选） | 简短中文说明（供前端事件监控面板展示）；`kind=delta` 时为攒批后的正文增量文本 |
| `finish_reason` | String（可选） | 上游 `finish_reason`（仅 `kind=llm_call` 且成功调用携带；`"length"` 即 max_tokens 截断标记）；None = 不适用/未知，序列化时省略 |
| `phase` | String（可选） | 调用归属阶段（仅 `kind=delta`/`llm_call` 携带：`planner` \| `step` \| `summarize` \| `summary` \| `agent` \| `subagent` \| `audit` \| `final_audit` 等，与 `task_llm_calls.phase` 同口径；前端流式缓冲 key 的前半） |
| `step_index` | usize（可选） | 调用归属步骤下标（0 起，与 `task_llm_calls.step_index` 同口径；仅步骤类调用携带，非步骤阶段省略；前端缓冲 key 的后半） |

#### `TaskEventKind` 全部取值（10 个）

serde 属性：**`#[serde(rename_all = "snake_case")]`**（`server-rs/src/models/types.rs:431-433`；该枚举同时 `Deserialize`）。原文注释：「序列化为 snake_case，与前端手写 union `TaskEventKind`（`web/src/api/types.ts`）逐值对齐——改此处须同步前端 union 与 `tools/check-contract.mjs` 的映射表」；「用枚举而非 `String`：后端拼错分类名从前只会在前端静默失效（未知 kind 不刷新），现由编译器拦住；**线格式与字符串时代逐字节一致**」。

| `kind` 字面值 | Rust 变体 | 语义 |
|---|---|---|
| `created` | `Created` | 任务已创建 |
| `status` | `Status` | 任务状态迁移 |
| `plan` | `Plan` | 执行计划更新 |
| `subtask` | `Subtask` | 子任务创建 / 状态更新 |
| `usage` | `Usage` | token 用量落库 |
| `deleted` | `Deleted` | 任务已删除 |
| `llm_call` | `LlmCall` | LLM 调用落库（批次 3 调用追踪；`task_llm_calls` 落库成功后发射，面板据此重拉） |
| `agent_status` | `AgentStatus` | 主 / 子 agent 状态迁移（批次 4） |
| `approval_required` | `ApprovalRequired` | 计划待批准（批次 4 plan 模式） |
| `delta` | `Delta` | 流式正文增量（批次 R4）——**暂态事件不落库**；LLM 正文增量经攒批后透出，权威数据以 `llm_call` 落库行 / `calls` 端点为准 |

**事件纪律（不可用 `delta` 当权威数据）**：`delta` 攒批透出且**不落库**（`events.rs::emit_delta`）；前端在收到 `kind=llm_call`（携带同 `phase`/`step_index`）时清对应流式缓冲，由落库行取代对齐权威。followup / plan-chat 的消息落库**不发射独立事件**，生命周期复用既有 `status` 事件（见「任务模式」各端点）。

| `TaskRunMode` | `#[serde(rename_all = "snake_case")]`（`Serialize` + `Deserialize`） | `Legacy`→`legacy`、`Solo`→`solo`、`Multi`→`multi`、`Plan`→`plan`、`Team`→`team`、`Custom`→`custom` | `server-rs/src/models/types.rs:692-745` |

| `TaskFollowupMode` | `#[serde(rename_all = "snake_case")]` | `Append`→`append`、`Replace`→`replace` | `server-rs/src/models/types.rs:761-789` |

**容错解析口径（读写不对称，属线格式契约的一部分）**：

- `TaskRunMode`：`as_str` 与 serde 输出一致；**DB 读取**走 `from_str_lossy`（未知值记 warn 回退 `legacy`，不 panic 不丢行）；**API 入参**走 `from_str_strict`（未知值返回 `None`，由调用方回 400「未知任务模式」）。
- `TaskStatus`：`from_str_lossy` 未知值回退 `pending`；另有 `as_str` 与 serde 输出一致。
- `TaskStepStatus`：`plan` JSON 反序列化经 `#[serde(deserialize_with = "de_step_status_lossy")]`（先读 `String` 再 `from_str_lossy` 回退 `Pending`）——「LLM 产出的 plan JSON 里 status 偶发未知值……严格 derive 会让整个 plan 解析失败」；字段缺失仍走 `#[serde(default)]`。
- `TaskSubtaskStatus`：`is_terminal()` = `done` | `error` | `ended`；**终态不再被后续状态写入改写**，首次进入时记 `finished_at`；`pending` 无写入点，仅 `stop` 的防御性比较保留。
- `TaskStep` 结构体字段：`{ name, goal, status, result }`，四字段**全部带 `#[serde(default)]`**（缺失即取默认：空串 / `Pending`）——plan JSON 缺字段不会导致整表解析失败。
- `TaskRecord` 结构体字段：`{ id, title, status, plan, result, error, character_id?, created_at, updated_at, task_mode }`；`status` 缺省 = `pending`，`task_mode` 缺省 = `legacy`（旧 JSON 无此字段即 legacy），`character_id` 为 `Option<String>` 且 `skip_serializing_if = "Option::is_none"`（None 时整体省略，前端须标为可选）。
- `TaskSubtaskRecord` 结构体字段：`{ id, task_id, name, instruction, status, result, error, created_at, updated_at, finished_at }`（`finished_at` 为**必填 string**，`pending`/`running` 期间为空串）。

## 错误体与状态码契约

### 结构化错误体

已接入结构化错误码的端点响应形状为：

```
{ "error": "消息", "code": "<SCREAMING_SNAKE 码值>" }
```

未接入处仍是**裸** `{"error": "消息"}`（历史形态，前端按无 `code` 兜底处理）。`error` 字段保持不变的目的是向后兼容（`server-rs/src/api/errors.rs:1-3`）。

### 七个 `code` 取值（`server-rs/src/api/errors.rs:17-56`）

`ErrorCode` 的 `as_str()` 返回值即线格式字面值（SCREAMING_SNAKE，**属对外稳定契约**）：

| `code` | Rust 变体 | 语义与配套 HTTP 状态 |
|---|---|---|
| `VALIDATION` | `Validation` | 参数缺失 / 校验失败（HTTP 400）；「contract 回滚的 422 语义校验也归此码」 |
| `UNAUTHORIZED` | `Unauthorized` | 未认证 / token 失效（HTTP 401；预留给鉴权出口接入） |
| `NOT_FOUND` | `NotFound` | 资源不存在：角色 / 会话 / 消息 / 历史记录等（HTTP 404） |
| `CONFLICT` | `Conflict` | 状态冲突：会话正在生成中、重发/重生成锚点失效等（HTTP 409） |
| `DB` | `Db` | 数据库 / 阻塞任务失败（`db_call` / `db_read` / `db_write` 的 Err 出口，HTTP 500） |
| `UPSTREAM` | `Upstream` | 上游 LLM 连接器错误（预留，供 connectors 错误出口接入） |
| `INTERNAL` | `Internal` | 未归类的服务端内部错误（HTTP 500） |

**码与状态码必须匹配**——`err_with_code(code, msg, status)` 的调用方勿跨档使用（`errors.rs:50-56`）；
另有「按 HTTP 状态码推断默认错误码」的辅助路径（「供仅知状态码的旧辅助函数平滑迁移」）：
`400 → VALIDATION`、`401 → UNAUTHORIZED`、`404 → NOT_FOUND`、`409 → CONFLICT`（其余映射见该文件）。

### 状态码语义

| 状态码 | 语义 |
|---|---|
| `201` | 创建成功（如 `POST /api/chat/sessions`、`POST /api/characters/upload`、`POST /api/world-books/upload`） |
| `204` | 删除成功（如 `DELETE /api/chat/messages/:id`、`DELETE /api/chat/sessions/:id`、`DELETE /api/characters/:id`、`DELETE /api/world-books/:id`、`DELETE /api/memory/:id`）。`DELETE /api/memory/{id}` 为「204 无正文」 |
| `400` | 缺参 / 校验失败（含非法 `authorization_mode`、`agent_mode=custom` 未启用/流程未保存或非法、`followup`/`plan-chat` 空指令与未知 `mode`、`max_tokens: 0`、覆盖层非法值） |
| `404` | 资源不存在（含 `GET /api/variable/state` 尚无契约运行态） |
| `409` | 状态冲突（会话正在生成中；`resend_message_id` 锚点失效；`followup` 非终态；`plan-chat` 非 `planned`；plan-chat 修订期间 stop 竞态中断） |
| `413` | **已知例外**：`DefaultBodyLimit` 在提取器执行前由 tower 层拒绝，**形状不统一**（统一 413 形状需自定义层拦截 body `Frame` 错误，成本远高于收益——已在 `json_body.rs` 头部写明原因） |
| `422` | 请求体结构不符（`POST /api/variable/update`）；contract 回滚的语义校验归 `VALIDATION` |
| `405` | 方法不允许（如 `DELETE /api/health`）：由 `method_not_allowed_fallback` 返回 JSON + `code`（此前为**空 body**） |
| `500` | `DB` / `INTERNAL`；固定文案 + `tracing::error!` 记原文，**不泄露内部细节**（`DB_ERR_USER_MESSAGE`） |
| `501` | `POST /api/agent/execute` 固定桩未实现 |
| `502` | 上游失败（`plan-chat` 的 LLM 上游/解析失败为 `UPSTREAM`；`api/resource.rs` 出口为 `{error, code}` + 原有真实状态码 400/500/502） |

### 错误面收口纪律（来源：`archive/2026-09-16-consolidation/工程韧性修复-变更说明.md` §2.1）

- **提取器统一**：`api/json_body.rs` 的 `JsonBody<T>` 薄包装把 `JsonRejection` 收口为 `{error, code: VALIDATION}` + 400（不新增第三方依赖）。已接入：`chat`(5)、`tasks`(4)、`settings`(3)、`characters`(1)、`sessions`(8)。畸形 JSON → `400 application/json` + `code: VALIDATION`（此前 `text/plain`）。
- **未知 `/api/*`** 由 `spa_fallback` 给出 `404 application/json` + `code: NOT_FOUND`（此前 404 无 `code`）。
- **假成功封堵**：`api/static_files.rs:34,48`（目录穿越拒绝 / 头像不存在）由「错误体 + 200」改为真实 `404` + `code: NOT_FOUND`。
- **泄露封堵**：`api/util.rs:21 db_err`（真正的活泄露出口）原文改由 `tracing::error!` 记录，响应统一为固定文案 `DB_ERR_USER_MESSAGE` + `code: "DB"`；签名不变。
- **正常业务上报不改为非 2xx**：`api/settings.rs:766`（embedding 测试）**保留 200 + `ok:false`**，仅补 `code`/`error`（「改非 2xx 会把『测试未通过』变成异常弹窗」）。
- **反馈业务数据与 `code` 并存**：`api/plugins.rs:82` **保留** `ok`/`loaded`/`errors` 业务数据，补 `code`/`error`；`errors` 逐项文案属用户排障必需，保留透出。
- **真实状态码判定**：前端 `web/src/composables/useResourceFrames.ts` 同步改为**按 HTTP 状态判成败**（原按 `body.ok` 分支会把后端 `code`/错误文案丢掉）。
- **测试断言辅助**：`assert_error_shape`（真实状态码 + `code`）与 `assert_no_internal_leak`（`api_integration.rs`）。

### 时间字段

**全部时间字段为 ISO 8601 字符串**（`MAINTENANCE.md` §6「约定」）。例外/特例须显式标注：`GET /api/health` 的 `ts` 为 Unix 毫秒整数（`timestamp_millis`），**不是** ISO 8601 字符串【待核实】——该事实出自 `server-rs/src/api/mod.rs:143` 的实现，与本条「全部时间字段为 ISO 8601」的表述不一致（见文末「源文档之间的不一致」第 4 条）。

### 1. `tools/check-contract.mjs` —— 前后端类型契约快照

**定位**：前端 `web/src/api/types.ts` / `web/src/api/memory.ts` 的类型是手写的，与 Rust 后端契约逐字对齐靠人；本脚本把「已知高变更面」的字段集合做差集比对，漂移即非零退出，纳入 `tools/check-all.ps1` 门禁（stage `contract: check-contract`）。

**判定规则（刻意宽严有别）**：

| 情形 | 判定 |
|---|---|
| 后端有字段、前端缺 | **FAIL**（真漂移，前端会读到 undefined） |
| 前端有字段、后端无 | **FAIL**（前端在臆造契约） |
| 后端可选、前端非可选 | WARN（后端可能省略该字段） |
| 前端可选、后端非可选 | 容忍（前端放宽类型是安全的） |

**解析口径**：`rustFields` 按顶层逗号切分字段（`<> () []` 内逗号不算分隔符），处理多行类型、`serde(rename)`、`serde(skip)`；`Option<T>` 本身**不算可选**（序列化为 null），只有 `skip_serializing_if` 才让字段在 None 时整体省略、前端才应标为可选。`rustVariants` 按 `rename_all = snake_case` 折算变体名为线格式文本。

**守什么**：`MAINTENANCE.md` 中记录的测试数字是否与实际统计一致（`--check` 模式下不一致即 exit 1）。
**统计口径**：后端单测 = `server-rs/src/**/*.rs` 中 `#[test]` / `#[tokio::test]` 出现次数；后端集成 = `server-rs/tests/**/*.rs` 同上（文件数另计）；前端测试文件 = `web/src/**/*.test.ts` 数量；前端用例 = 上述文件内行首 `it(` / `test(` 调用次数（排除 `it.each`/`test.each` 等链式误配）。
**比对格式**：`MAINTENANCE.md` 中形如「N 个测试(M 单测 + K 集成)」与「N 个(M 文件)」的文本；格式缺失即判为问题。
**与契约的关系**：不守线格式本身，但守住「文档里的数字」不漂移——契约文档中若引用测试数字，须走脚本而非手抄。
