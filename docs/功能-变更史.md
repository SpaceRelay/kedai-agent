## <a id="2026-08-21-performance"></a>2026-08-21 性能基线与第一轮改造（来源：archive/2026-09-16-consolidation/perf-baseline.md）

**改了什么（§五「本轮落地的修复」，10 项）**

| 项 | 改动 | 落点 | 证据 |
|---|---|---|---|
| P0-1 工具参数计入 token 计数 | 计入 `tool_calls` 的 name/arguments；新增 `count_single_message_tokens` 统一口径 | `services/token_service.rs` | 3 个单测 |
| P0-1 裁剪回收工具参数 | 新增 `reclaim_round_arguments`，占位保持**合法 JSON**（严格后端会 400），id/name 保留以维持配对 | `agents/engine/messages/trim.rs` | 4 个单测 |
| P0-1 收敛信号 | `trim_tool_history` 返回 `ToolHistoryTrimOutcome`，未达标记 warn（不再静默） | 同上 | — |
| P0-2 重复调用熔断 | 新增 `utils/loop_guard.rs`（FNV 指纹 + 环形窗口，N=8/K=3），`run_tool_loop` 接入，中止理由经 step 事件透出 | `utils/loop_guard.rs` | 6 单测 + 1 端到端 |
| P1-1 世界书正则预编译 | 进程级正则缓存 + 小写化外提 | `parsing/world_book.rs` | 2 单测 |
| P1-2 token 计数缓存 | 按 (编码, 文本哈希, 长度) 缓存 | `token_service.rs` | 2 单测 |
| P2-1 推理感知自愈 | 识别「推理耗尽预算」并一次给足预算（原为盲目翻倍） | `agents/engine/executor.rs` | 3 单测 |
| P2-2 性能门禁 | `perf-baseline.mjs` 加 p95 阈值 + `perf-baseline.json` 基线 + `check-all.ps1 -Perf`（默认关闭） | `tools/` | 退出码实测 1/0 |
| P3-1 工具定义快照 | 缓存 + 写路径失效（注册/注销） | `tools/registry.rs` | 2 单测 |
| P3-2 世界书条目缓存 | 按 `character_id` 缓存，5 条写路径全失效 | `world_book_service.rs` | 2 单测 |

**为何这么改**：两处缺陷叠加。**缺陷 A**——`count_message_tokens` 只累加 `content`，完全忽略
`tool_calls[].arguments`，而连接器会把 arguments 原样序列化进请求（`to_openai_messages`），
它们真实占用 prompt。**缺陷 B**——`trim.rs` 的 `summarize_round` 只替换 tool 消息 `content`
并清空 reasoning，**`tool_calls[].arguments` 原封不动**。两者叠加使预算闸门**永远判定「未超预算」**
→ 工具历史裁剪失效。实测日志佐证：裁剪确实触发 72 次仍失控，因为它裁的不是大头。
影响面超出任务模式：`count_message_tokens` 同时被 `trim_to_context` 使用，即**聊天主链路的
上下文窗口裁剪也同期失效**。缺失防线：普通 agent 工具循环**没有任何重复调用检测**，
唯一终止条件是 `max_tool_rounds`（实测配置为 64）。

**验证证据（实测数值）**

- 基线：记录日期 2026-08-21，基线 commit `5f9a55a`（优化前）；环境 Windows 11 / debug 构建。
  测试基线 `cargo test` **643 绿**（538 单测 + 105 集成，0 失败；单测 5.88s，集成约 100s）、
  `npm test -w web` **295 绿**（33 文件）、`npm run build -w web` 通过（4.17s）（当时数值）。
- 端到端实测（debug 构建，token 与构建类型无关）：`fast` 7,679 ms / TTFT 7,025 ms / prompt 8,829；
  `agent` 68,064 ms / TTFT 30,868 ms / prompt 40,943、**零工具调用**、两次截断自愈约 37 s；
  `solo` 19,096 ms / prompt 27,432、4 次工具调用；`plan` **失控**——累计 prompt **1,502,300**、
  7 分钟不收敛、94 个 provider 轮次，需人工 stop。plan 逐步骤 prompt 增长
  `9,762 → 28,784 → 576,312 → 885,378`（90 倍）。
- 本地热路径（release 微基准）：世界书一轮匹配（33 条）**9.439 ms → 0.062 ms**（正则预编译，**152×**），
  其中纯正则编译 9.293 ms → ~0；token 计数摘要循环（12 轮）**237 ms → 1.7 ms**（**136×**，O(N²)→O(N)）；
  `count_message_tokens`（30 条 × 2k）29.4 ms → 命中缓存 <1 ms。
- 前端（node 实测）：markdown-it 渲染 16.5k 字符 **0.453 ms**；sanitize-html 处理 16.8k 字符
  **3.057 ms**（约 markdown 的 7 倍）；模拟流式 60 帧全量重渲累计 18.1 ms。
- 写路径实测：单条独立 INSERT 提交 **0.686 ms/条**，同事务批量 **0.013 ms/条**（52×）；
  一次任务约 12 条写入 ≈ 8 ms → **事务化不做**（收益低于语义风险）。
- 实测修正静态审计（避免为已证伪假设浪费工时）：`prompt_kit` 6 次链式 `replace` **撤销**（0.042 ms/次）；
  `settings_snapshot()` 整体 clone **撤销**（clone 0.007 ms，真成本在工具定义的锁内 clone+sort）；
  TaskBoard 全量 markdown 重算 **降级**；世界书「重复 to_lowercase」与「正则编译」**拆分**（小写化仅省 0.35 ms）；
  任务写路径各抢一次写锁 **不做**；plan 模式每次 `agent_status` 重复发射 **伪问题**（mock 裁决测试证明每类事件恰好一次）。

**未做项**：见文末索引（`perf-baseline` §七「明确不做清单」）。

## <a id="2026-09-13-v030a"></a>2026-09-13 0.3.0-A-beta（来源：archive/2026-09-16-consolidation/0.3.0-A-beta-变更说明.md）

> 本版是 0.3.0-beta 的**加固与修复版**：修掉卡片生成截断、补齐数据安全与工程门禁，
> 并完成一次三轮架构评审后的分批治理。版本号 `0.3.0-A-beta`（semver 预发布后缀，与 0.3.0-beta 同密钥可覆盖安装）。

**用户可感知的变化**

1. **任务模式支持命令执行（bash）**：`bash` 在任务模式默认策略下下发（仅此工具按名开例外）；
   **危险命令的硬门未动**——删除/格式化/提权/包管理在任务模式下直接拒绝（无 UI 确认通道），
   普通命令经任务白名单授权执行；仍受 `exec_enabled` 总开关约束（默认关）。
2. **角色卡「掉格式」修复（Android 真机复现）**：根因是 Android 首装默认 `max_tokens=1024`
   把 JSON 腰斩，卡片解析器全回退失败。修复——`generate-raw` 路径专属下限 **8192**（不动用户设置语义）、
   `finish_reason=length` 时**预算翻倍重发**（封顶 32768、最多 2 次）、重发失败或用尽时
   **仍返回 200 + 最后一次文本**、显式 `max_tokens=0` 返回 400；新增诊断日志与
   `kedai.tavern-call-log` 记录（注入条目数 / 产出长度 / 截断重试）。
3. **「更新内容」文案更新（2026-09-13 治理批次）**：改为反映本轮工程治理的用户可感知结果
   （用量统计事务化、消息删除的孤儿数据清理、截断自愈统一、引擎异常状态迁移留痕、
   内部结构收敛、ESLint 与依赖扫描加固、EJS 冻结门禁）；文案在 `AboutSection.vue` 的 `changelog` 数组。

**稳定性与数据安全（加固项）**

- **API Key 不再被静默清空**：换机/换用户后密文解密失败时，保存设置不再用空值覆盖磁盘密文，
  而是保留原密文并留日志提示重填。
- **生成中断不再卡死会话**：`pending_runs` 占位改 RAII（drop 守卫），引擎异常/panic 也会清理，
  修复「一次失败 → 该会话此后所有发送都 409」。
- **生成期间可正常保存设置**：连接器读锁改为快照，不再跨整轮流式生成持有。
- **长会话/长列表更流畅**：补齐 `sessions(character_id, updated_at DESC)`、`tasks(character_id)`、
  `tasks(status)` 索引；世界书列表条目数随编辑实时更新。
- **无界增长收敛**：压缩摘要（每会话保留最近 20 条）、命令审计（最近 2000 行）、会话删除时清理
  回退快照 / 契约日志 / message 作用域变量。
- **写连接锁中毒可恢复**：中毒时留痕并对未完成事务显式 `ROLLBACK`。

**工程与供应链**

- 依赖漏洞修复：`sanitize-html 2.17.7`（存储型 XSS 公告）、`nanoid 3.3.19`；
  `npm audit --omit=dev` 归零并进检查（警告档）；`cargo audit` 默认**硬门禁**。
- **双 Cargo.lock 对齐**：17 个 crate 分歧清零（含已被 yank 的 `chacha20 0.10.1` 与 `cc`/`find-msvc-tools`）；
  新增 `tools/check-lock-sync.mjs` 门禁（0 漂移为基线，新增即 FAIL）。
- **迁移元测试**：冻结 0.3.0-beta 建表基线，老库升级后与全新库逐表比对结构指纹
  （`tests/schema_migration_meta.rs`），防「加列漏写迁移」只在老用户机器上炸。
- CI 工作流落盘（`.github/workflows/ci.yml`，仓库配置远端后自动生效）；
  构建清理路径跟随 `-RustTargetDir`；本机临时脚本/构建日志不再污染仓库。
- 新增 `威胁模型与残余风险.md`（活文档）与 `模式提示词边界.md` 的预览口径澄清。

## <a id="2026-09-14-scanwindow"></a>2026-09-14 角色卡世界书扫描窗口修复（来源：archive/2026-09-16-consolidation/角色卡世界书扫描窗口修复-变更说明.md）

**现场证据（本机真实数据）**：`%APPDATA%\com.kedai.app\logs\kedai-2026-09-14.log` 的 generate-raw 调用记录
`{"messages":3,"total_chars":20884,"msg":"generate_raw_call"}` 与
`{"character_id":"00b005fb-…","entries":54,"injected":17,"msg":"generate_raw_worldbook_inject"}`。
三个关键读数：`entries=54`（角色卡内嵌世界书解析正常）；`character_id` 非空（注入流程**已进入**）；
`injected=17`——**恰好等于该卡的常驻（constant）条目总数**。第 3 条是决定性的：带 `keys:["system log"]` 的
**响应格式规范条目一条都没进**；且本次调用**没有任何** `generate_raw_truncated_retry` / `still_truncated`
日志（排除 09-13 修复覆盖的「未注入」与「被截断」两种情况）。

**根因：`depth` 与 `scanDepth` 语义混用。** 该卡权威数据（数据库实读）：

| 条目 | keys | `extensions.depth` | `extensions.scan_depth` | 内容长度 |
|---|---|---|---|---|
| `[INS]🔗响应格式🔗[FORMAT]` | `system log` | **1** | 缺省（无） | 6837 |
| `🔗故事编写🔗` | `system log` | **1** | 缺省（无） | 1095 |
| `[TMP]🔗响应格式🔗[FORMAT]` | `system log` | 1 | 缺省（无） | 6288（该条 `enabled=false`，本就应跳过） |

对照 SillyTavern 原版语义（`public/scripts/world-info.js`）：`entry.depth` ↔ `originalData.extensions.depth`
是**插入深度**（`position=atDepth` 即 `position=4` 时决定插到倒数第几条），**不是关键词扫描窗口**；
扫描窗口是**另一个字段** `entry.scanDepth` ↔ `extensions.scan_depth`（`get(entry)` 用
`entry.scanDepth ?? 全局扫描深度`，从不读 `depth`）。**失误链条**：①2026-09-12 的 F1 修复
（[实测四轮修复章](#2026-09-12-round4)）给 `depth` 补了 `extensions` 回退并把它**当作扫描窗口**用
（`scan_depth_window = e.depth`），对赛马娘卡是对的但**语义张冠李戴**；②吸血鬼卡格式条目
`extensions.depth=1` 因此被当成「只扫最近 1 条消息」；③作者页（`v2.1.html` 的 `Bk`/`ph` 函数）
把整段 `<chat_history>` **压成一条 user 消息**发出，触发词 `system log` 只出现在该消息**开头的注释行**
`/* system log(IGNORE the line): … */`——它落在窗口第 1 条，而窗口只剩最后 1 条（尾部的 `<user_input>` 那条）
→ **永不命中**；④格式规范不注入 → 模型自由发挥 → 卡片 `$y.extract()` 多重回退全失败 → 弹「布豪!丢格式了!😭」。

**改了什么**

- **3.1 `scan_depth` 独立成字段（语义归位）**：`parsing/world_book.rs` 的 `WorldEntry` 新增
  `scan_depth: Option<i64>`（预留 None = 未声明）；解析兼容 `scan_depth` / `scanDepth` / `extensions.scan_depth`；
  **不再**用 `depth` 顶替；`depth` 的文档注释更正为「插入深度（position=atDepth 用），不是扫描窗口」；
  新增共享纯函数 `scan_window_len(e, texts_len, fallback)`（scan_depth 优先、未声明用调用方兜底、
  `<=0` 表示全部、按可用条数封顶）。
- **3.2 两条路径各自取正确口径（收敛到共享函数）**：
  `api/chat.rs::inject_worldbook_for_raw`（卡片生成）用 `scan_window_len(e, len, **0**)` = 未声明则**扫全部**
  （作者页自组的是扁平完整上下文，不存在"最近聊天"概念）；
  `agents/engine/worldbook.rs`（角色扮演主引擎）用 `scan_window_len(e, len, e.depth)` = 未声明则**沿用 depth 兜底**
  （保持赛马娘卡等存量卡行为**逐字节不变**）。
- **3.3 顺带修复：编辑保存会抹掉 `extensions`（让本修复不白做）**：`view_to_value` 的注释写着
  「未改动的 extensions 保留」，但 `merge_entries_into` 实际是**整体替换条目对象**——而 `extensions` 里的
  `depth` / `scan_depth` / `role` 都**不在**前端视图里，于是任何一次条目编辑保存都会静默抹掉它们。
  改动——`merge_entries_into` 改为**字段叠加**（`overlay_view`：视图字段覆盖到原始条目对象上，
  未承载的键原样保留；数组形态同样按 uid 叠加）；`view_to_value` 的 `regex`/`role` 在视图为空时写显式 `null`；
  `keysecondary` 与 `secondary_keys` 两侧同写，避免原始键残留成"影子值"被优先读到。

## <a id="2026-09-14-perf2"></a>2026-09-14 性能实测与修复（第二轮性能治理）（来源：archive/2026-09-16-consolidation/perf-baseline.md）

**端到端实测（debug 构建；token 与构建类型无关，可信）**

**不做**（实测 8 ms/任务）；plan 模式每次 `agent_status` 重复发射 **伪问题**（用 mock 裁决测试证明
链路每类事件恰好一次；先前观察系探针脚本分帧所致）。本轮的 10 项落地修复与实测数值同第一轮表。

**经验总结（先读，决定后面怎么改）**

- **这批 bug 的共同形态：状态被「静默改写」**——平台在传递语义时丢掉了定性信息，或悄悄替换了调用方的意图。
  五处现象：子任务被喂 `max_tokens=64`（`clamp(64, 4096)` 静默抬升）、`agentend` 拼错 id（恒返回 `ok: true`）、
  `read` 未命中（返回与正常结果同构的 `content`，实为候选清单 15 条）、聊天被截断
  （`SseEvent::Finish` 不带 `finish_reason`）、`ended` 同时表示「完成后被召回」与「中途中断」。
  **判据**：凡「调用方无法从返回体/事件自证真实语义」的地方，就是下一个 bug 的温床。
  修法不是加文档说明，而是**让返回结构自证**（显式字段/显式失败），或在日志里留下可诊断线索。
- **推理模型的预算语义是「推理与正文共享同一池」**：本机实测（`deepseek-flash`）——`max_tokens=64` →
  推理烧掉全部 64、正文为空、自愈到 128 依然如此；`max_tokens=10000` → `reasoning_tokens=9894`、
  正文只剩 178 字符即 `finish_reason=length`；单次子任务仅推理就能吃掉近万 token。
  **结论**：任何「小预算」档位对思考模型都等于「必然截断」，下限必须按推理消耗量级设（16384），
  且**自愈的封顶必须高于下限**（本次 `TRUNCATION_HEAL_MAX_TOKENS_CAP` 8192 < 新下限 16384 正是这个陷阱）。
- **「四处同源」的常量必须一起改**：截断自愈的预算决策收敛在 `utils/retry.rs`，但**封顶常量仍分散在四处**，
  改校验上限时四处封顶与注释都要同步（否则出现「设置页允许 131072、重试封顶仍 65536」的自相矛盾）。
- **与并行写者共处**：本轮实施期间有另一个会话在同一分支并行写同一批文件（R5 测试基建）；
  交织文件无法用 `git add <path>` 干净剥离，只能按「文件归属一个主题」合并提交；
  **依赖倒挂**——新测试用了并行批次的 `dummy_for_test()` 新签名，提交粒度受**编译依赖**约束。
- **顺带修掉的既有缺陷要写进提交信息**：R5 批次把两个权限测试改用 `TempDataDir` 后，

  WAL 下 `synchronous=NORMAL` 意味着掉电可能丢最近若干次提交（最坏丢最后一条消息/状态），

- **P-2 · 静态资源缓存**：`cache_control_for(target)` 分三档——`index.html` 恒 `no-store`（版本指针）；

- **P-4 · 运行时提示词读缓存**：按 `(mtime, 长度)` 指纹缓存。三个正确性要点（均有对应用例）：

  15.6ms 粒度，同长度改写可能同 tick，只靠 mtime 会返回旧值（用例刻意不 sleep）；
  ③**旧文件指纹也进缓存键**——否则「首次读时新旧文件都不存在 → 缓存内置默认 → 用户之后放进旧文件但

  `/api/memory` 甚至在循环内逐条新建）；新增 `MemoryService::get_many`（一条 `IN (...)`、
  **保持入参顺序**、跳过缺项、空输入短路）；蒸馏补向量由「逐条 get + 逐条 embed + 逐条 upsert」改为
  「一次 `get_many` + 一次 embed（内部 32 分片）+ 一次 `upsert_vectors`（单事务）」；
  `embed_one_entry` 不再接收调用方传入的 content，改按 id 读库，消除两个真值源。
- **P-6 · 任务引擎落库让出 worker**：新增 `utils/blocking.rs::park_worker`——**按 runtime flavor 分派**
  （multi-thread 的 worker 走 `block_in_place`；current_thread、spawn_blocking 线程、无 runtime 三种场景

- **① 5xx 泄露分档**：`internal`/`upstream` 的入参是内部错误串，改为 `tracing::error!` 记原文 + 响应体给固定文案（与 `util.rs:29` 的 `db_err` 同策略）。顺带修掉 `chat.rs:685` 的真实泄露点——该 502 此前把上游报错文本直接拼进响应体。
- **① 分档边界按「入参是否为内部串」而非状态码**：`world_books.rs:169` 的 `"保存失败"` 是给用户的固定文案，故保留 `err_status` 不降级为通用文案，否则反而丢信息。
- **② 上传重试为何安全**：401 由鉴权中间件在 handler **之前**返回，首请求未被执行，故非幂等的 multipart POST 重试不会产生重复写入。流式 POST（`/chat/send`）仍**不自动重试**（重放会重复触发上游计费），只复用错误分类。
- **② 为何不强行统一两条流**：聊天流是「必发终态」（非 2xx 须补合成 `step`+`finish` 复位 `generating`，否则 UI 卡在生成中），任务流是「长连接」（非 2xx 抛错交调用方退避重连）。底座只收敛共通机制，语义留在各调用方。
- **③ 为何必须扩展提取器**：现有 `kind:'union'` 以**第一个分号**收尾（`check-contract.mjs:173-177`），对含内部分号的判别式联合会在第一个成员内部截断，得到残缺变体集并**静默通过**——比不检查更危险。递归展开是为 `SseEvent` 联合里引用的 `TaskEvent` 别名。
- **③ 断言位置有讲究（实测得出）**：`never` 断言必须写在 **`default` 子句内**。放到 switch 之后时，`break` 的 case 会带着未收窄的成员跳到该位置，`never` 永不成立（TS2322 恒报）。
