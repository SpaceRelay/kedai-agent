## 一、产品与分发方向

本节是**产品决策**与**分发形态**层面的长线判断（钱的归属、商店的归属、默认视图的归属）。共同特征是「取决于产品定位而非技术可行性」，故不设批次、只看触发。

### L17 Windows 产物无 Authenticode 签名，首装触发 SmartScreen 告警
- **方向**：转向正式代码签名——购买 OV/EV 证书，每个 exe 产出后执行 `signtool sign /fd SHA256 /td SHA256 /tr <RFC3161 时间戳服务>`（**时间戳必须加**，否则证书过期后已签文件随之失效），接入 `build.ps1` 的三处产物（`dist\kedai-server.exe`、`tools/build-portable.ps1` 产出的 `dist\Kedai-portable\Kedai.exe`、项目根 `Kedai.exe`），NSIS 包可在 Tauri 的 Windows signing 配置中声明或构建后补签；OV 成本较低但 SmartScreen 信誉需时间与下载量积累，EV 首装即获信任但私钥必须存硬件令牌或云 HSM；**自签证书对 SmartScreen 无效**（与「未签名」表现相同、还增加密钥保管负担），故不做自签的 Authenticode。
- **为何现在不做**：证书是付费产品、需以真实主体实名申请并按年续费；当前分发定位为内测/自用，使用者在可核对的渠道拿产物，接受「未知发布者」的一次性确认成本（配合指纹自查）。是否购买、买 OV 还是 EV 属产品决策，源文档只列要点、不实施。
- **触发条件**：源文档未给触发条件【待核实】（源文档「决策归属」明确「是否购买、买 OV 还是 EV 属产品决策，本文不代决」）。候选触发：①分发从内测/自用转为公开下载；②出现真实冒充/替换产物的安全需求；③签名密钥需注入 CI。
- **关联**：`遗留.md` 的 L17（现状行为与判定）；本文 D2（指纹链闭环）、AND-1（APK 自签是另一套签名体系）。
- **来源**：archive/2026-09-16-consolidation/known-limitations.md L17；archive/2026-09-16-consolidation/代码签名与SmartScreen说明.md §四

### D2 构建指纹链不闭环（sidecar 与二进制内嵌指纹不可直接比对）
- **方向**：若必须闭环，**优先「`exe_sha256` 路径」**——`Write-KedaiBuildStamp` 额外写 `exe_sha256 = Get-FileHash -Algorithm SHA256 <exe>`（哈希对象是 **exe 字节**、不是前端资产），由已持有 `Get-FileHash` 的 `start.ps1` 在启动前重算比对、不一致即拒绝启动：真正覆盖「exe 被替换」，且不动 Rust、不新增 build-dep、不动任何 `Cargo.lock`、不触碰内嵌指纹与 Android、launcher「零第三方依赖」约束也不需要动（校验放 PS 侧）。**次选方案②**（sidecar 增 FNV 字段）。**不选方案①**（`build.rs` 改算 SHA256：内嵌值形态 16→64 hex、Windows 双端 + Android `.so` 全变、新增 `sha2` build-dep 与锁同步门禁，且需精确复刻 PS 侧「小写绝对路径排序 + 前导 `/` + 大写 hex + `\n` 序列化」三处坑）。本轮结论是**「维持现状 + 补文档」**：在 `MAINTENANCE.md`、`tools/Write-BuildStamp.ps1` 与 `server-rs/build.rs` 头注释各补一句「本机制用于**两版同源一致性**检查，不构成对 exe 的完整性/防篡改保证；后者需代码签名」。
- **为何现在不做**：收益被高估——两张指纹的输入**都是 `web/dist`，exe 自身字节不在任一哈希的输入集合内**；现有比对只发生在两个 sidecar 之间（测试版 vs 便携版），即便闭环，比对的一方由**被检 exe 自报**（`/api/health.build_id`）、无签名/信任根、可被伪造；攻击者同时换 exe 与 sidecar，或换掉作为校验宿主的 launcher 本体，即绕过全部校验。成本却落在最敏感的发行链路上，而唯一净增益「配错包」场景已被 `build.ps1:404-411` 的双端 `dist_hash` 一致性断言半覆盖。Android 天然不在闭环内（APK 内没有 sidecar 可比），这是方案能力边界、交付时须一并声明。
- **触发条件**：源文档已明确三条——①引入代码签名；②出现真实「替换 exe」威胁场景；③需要发布 QA 同源机检。届时**优先 `exe_sha256` 路径，次选方案②，不选方案①**。
- **关联**：`遗留.md` 的 D2（登记为设计边界，不修）；本文 L17（真正防冒充需 Authenticode）。
- **来源**：archive/2026-09-16-consolidation/构建指纹链评估-2026-09-13.md §四、§六；archive/2026-09-16-consolidation/威胁模型与残余风险.md §二 D2

### AND-1 Android 分发形态：含 root/Shizuku 能力走自签 APK 侧载，上架需另做 Play 变体
- **方向**：含 root/Shizuku 能力的构建**不进 Play**，以自签 APK 侧载分发；若将来要上架，需另做一个「**无 root 能力**」的 Play 变体（同一代码库按能力面切两套产物）。APK 与 Windows exe 走不同签名体系：APK 用 release keystore 自签、构建即签名，且 Android 要求**同包名 + 同签名密钥**才能覆盖升级（换密钥必须先卸载、**丢失应用数据**），故必须始终坚持同一 keystore（别名 `kedai`），**切勿重新生成密钥**。
- **为何现在不做**：Android 方案交付形态是「全内嵌单机版」，当前只出 arm64 真机（+ x86_64 模拟器）构建，尚未进入分发决策；root/Shizuku 通道默认关闭、逐条确认、带审计日志，合规与安全等级在源文档中被评为「高」。
- **触发条件**：源文档未给触发条件【待核实】（阶段 5 只给分发方向，未给触发条件）。候选触发：①准备把 Android 版发给非自用用户；②决策要上应用商店（此时「无 root 变体」是前置条件）。
- **关联**：`计划.md`（Android 阶段 5 的构建与签名、阶段 4 移动适配）；本文 L17（两套签名体系不可互相替代）。
- **来源**：archive/2026-09-16-consolidation/android-port-plan.md §三 阶段 5、§四 风险表、§五之六（源文档无编号，本文新分配 ID）

### WF-10 二维画布对普通用户是负担：保留线性列表为默认视图
- **方向**：线性列表保持**默认视图**；二维画布作为「高级模式」可切换。存量流程进入画布时**自动布局为纵向链**，视觉上仍是一维，不惊吓用户（ComfyUI 式画布的价值在表达能力、代价是门槛）。
- **为何现在不做**：整个二维化方案仍是**分析稿（未开工）**，其中三项远超「加个功能」量级（图执行器 + 前端画布需引入图库 + 多套 API 触及凭据加密）；在画布价值被真实用户验证前，先落默认视图策略只会限制后续取舍空间。
- **触发条件**：源文档未给触发条件【待核实】（该条是「建议写进 UI 文案」的产品风险）。候选触发：二维画布进入实现批次（批次 3）时，本条作为默认视图与存量流程迁移策略的**约束**先落地。
- **关联**：`计划.md`（二维自定义工作流的批次 0~7 与「里程碑二：画布可用」）；本文 WF-11。
- **来源**：archive/2026-09-16-consolidation/二维自定义工作流-可行性与实施计划.md §一、§四 产品风险 10

### WF-11 并行 = 成本倍增：并发节点数默认保守并在 UI 提示
- **方向**：节点并行**要做**（否则二维图相对一维只多一个画布），但必须配并发上限：默认保守（如 2），并在 UI 明确提示「并行节点会成倍消耗 token」；同时需配取消传播、usage 汇总与「多节点并发不丢更新」的防护。
- **为何现在不做**：并行调度（`JoinSet` + `max_parallel_nodes`）属批次 2 的 L 级改动，且与 `set_plan` 整列覆写（多节点并发 = 丢失更新）、`TaskStep.node_id` 契约、取消传播同时交织；源文档另给出实测先例表明嵌套/反复调用的成本失控风险真实存在（7 分钟 150 万 token）。
- **触发条件**：源文档未给触发条件【待核实】（给的是产品风险与批次计划）。候选触发：批次 2 开工时本条作为默认并发值与 UI 文案的约束；或出现真实的「并行成本超预期」反馈。
- **关联**：`计划.md`（批次 2 的并发回归与 usage 汇总验收）；本文 LD-2（并行工具执行同域）。
- **来源**：archive/2026-09-16-consolidation/二维自定义工作流-可行性与实施计划.md §四 产品风险 11

## 二、能力边界的方向（有意裁剪的补齐路径）

本节每一条在源文档里的判定都是「**有意裁剪 / 有意不做 / 有意保留例外**」，**不是待办**。它们完整的「现状行为（带文件:行号）+ 判定 + 影响面 + 生态兼容考量」归 `遗留.md`（按同编号）；此处只登记「未来方向 + 触发条件」。**重开任一条之前先读 `遗留.md` 对应条目。**

### L1 世界书 sticky / cooldown 不参与匹配，也无递归激活
- **方向**：补齐路径是**会话维度的「条目激发台账」**（哪条何时触发、剩余 sticky 轮数），落库表 + `collect_context` 装配时读取；递归激活则要在注入文本上再跑一轮匹配并**防环路**。
- **为何现在不做**：有意裁剪——sticky/cooldown 依赖跨轮状态台账，与 Kedai「每次生成都从消息池重新装配」的无状态管线相冲突。Kedai 已对齐 ST 世界书的一个子集（关键词/正则触发、概率门控、constant/triggered 两组注入位置）；ST 卡若重度依赖 sticky/cooldown（如进度条式世界书），在 Kedai 中表现为「条目只按关键词当下触发」——语义更弱但不错乱，属可接受降级。
- **触发条件**：源文档未给触发条件【待核实】（只给「若要补齐」的路径）。候选触发：ST 生态出现**必须依赖 sticky/cooldown 才能正确工作**的高频卡；或装配管线改为有状态。
- **关联**：`遗留.md` 的 L1；`计划.md`（世界书注入三处合一的收敛）。
- **来源**：archive/2026-09-16-consolidation/known-limitations.md L1

### L4 世界书激发条目 `role=system` 钳制为 `user`
- **方向**：维持钳制（只有**常驻**条目、位置 3 的 system 才真的拼入 system 文本）；源文档未给出将来放开的路径。
- **为何现在不做**：有意裁剪——尾部消息流里夹 system 角色在多数 OpenAI 兼容端点上语义不明（有的端点直接拒绝中段 system），钳制为 user 是兼容性最优解。ST 生态里激发条目写 system 的卡较少；这些卡在 Kedai 中表现为「注入仍然出现，只是角色是 user」，**内容不丢**。
- **触发条件**：源文档未给触发条件【待核实】。候选触发：端点侧普遍支持中段 system，且出现「因钳制导致语义错误」的实测案例。
- **关联**：`遗留.md` 的 L4。
- **来源**：archive/2026-09-16-consolidation/known-limitations.md L4

### L5 跨 realm 共享全局桥只覆盖 JSON 子集
- **方向**：需要**真函数共享**的脚本应改写为**数据形态**（存配置、让对端按数据重建）；或等「**卡级合并单 realm**」（同段组共享 window）覆盖该场景后，迁移到卡级脚本里。
- **为何现在不做**：有意裁剪——函数/DOM 引用/循环结构/超大对象不跨 realm 共享（`JSON.stringify` 失败或超限即静默跳过），黑名单防覆写 window/document/location/fetch 等通信基建与 `__kd` 内部前缀；共享桥只同步「键为合法标识符且非黑名单、值 JSON 可序列化且 ≤256KB」的 window 自有属性快照。ST 真实环境同页同 realm、脚本间可挂任意函数全局；多数生态脚本（状态栏数据、剧情数据库、消息级降级读）用的正是纯 JSON 对象（如 `window.WuWaShared = {STORY_MAP,…}`），在此子集内可工作。
- **触发条件**：源文档给定的迁移条件——「卡级合并单 realm（同段组共享 window）覆盖该场景」落地后，且存在确实需要真函数共享的生态脚本。
- **关联**：`遗留.md` 的 L5；`计划.md`（沙箱 realm 模型若有后续批次）。
- **来源**：archive/2026-09-16-consolidation/known-limitations.md L5

### L6 沙箱 draggable 只实现定位与钳制
- **方向**：需要 `helper`（克隆/代理元素）、`axis`、`grid`、`snap`/`snapMode`、`revert`、`stack`、`zIndex` 管理，以及在 `drag` 回调里改写 `ui.position` 反写回宿主的卡，可在 `web/src/sandbox/draggable.ts` **按同一模式扩展**（pointer 事件已在宿主侧、document 级跟踪与 cleanup 登记基建已就绪）。
- **为何现在不做**：有意裁剪——生态悬浮窗脚本的拖拽诉求集中在「能拖、不跑出视口、位置能存」，复杂选项在角色卡场景几乎不用，完整移植 jQuery UI 的收益与维护成本不成比例。（th-3/th-4 有 `typeof .draggable === 'function'` 守卫、缺失时静默跳过；th-5 无守卫——本实现补上后不再 TypeError 中断。）
- **触发条件**：源文档未给触发条件【待核实】（只给补齐路径）。候选触发：出现依赖上述某个未实现选项的卡，且改动可局部化在该文件内。
- **关联**：`遗留.md` 的 L6。
- **来源**：archive/2026-09-16-consolidation/known-limitations.md L6

### L7 记忆向量检索：精确 KNN，无 ANN 索引
- **方向**：若单角色记忆量突破数万条，可启用 `sqlite-vec` 的**分区/量化**能力，接口层 `select_recall_hybrid` 无需改动；换 embedding 模型导致维度变化时，方向仍是**用户手动重建向量索引**（清表 + 全量回填），刻意不自动重建以免用户未预期地消耗 API 额度。
- **为何现在不做**：有意裁剪——记忆量级为每角色数百至数千条（受 `memory_max_entries` 约束），精确 KNN 在 5k×512 维下约 1–15 ms；ANN 的召回率损失与索引一致性维护成本不划算。
- **触发条件**：**单角色记忆量突破数万条**（源文档给定）；或引入交叉编码器 reranker / 本地 embedding（见本文 GPU-1、GPU-2）。另注：来源 §九 核验到一处**文档与代码不一致**——L7 描述为「`vec0` 走精确 KNN」，但代码路径并非 `vec0` 的 KNN 查询，而是「按 id 取向量 + Rust 侧标量余弦」（`vec0` 只作存储），该差异**不影响 L7 结论**（都是精确检索、无 ANN），但描述应更正。
- **关联**：`遗留.md` 的 L7；本文 GPU-2、PB-5、RD-2。
- **来源**：archive/2026-09-16-consolidation/known-limitations.md L7；archive/2026-09-16-consolidation/GPU加速可行性分析.md §九

### L9 `deep` 模式主生成不启用工具
- **方向**：若确有需求，可为 deep 增加近似 agent 的**受限只读工具循环**（白名单 `tool_sets::READONLY_SCOUT`），沿用 `ToolGate` 闸门。（现状：2026-09 授权改造后 deep 的**反思轮**已放开 `read`，主生成仍不调用工具。）
- **为何现在不做**：有意裁剪——给 deep 主生成引入只读工具循环会改变其语义（从「一次生成 + 反思」变为多轮工具交互）并显著增加 token 成本，需独立评估；deep 用户当前的 prompt 与成本预期是「无工具」。
- **触发条件**：源文档未给触发条件【待核实】（只写「若确有需求」）。候选触发：出现「deep 事实性错误因缺读工具而无法纠正」的实测案例；且变更须在前端明确标注成本变化。
- **关联**：`遗留.md` 的 L9；`计划.md`（若该变更进入路线图）；本文 LH-1。
- **来源**：archive/2026-09-16-consolidation/known-limitations.md L9

### L10 角色扮演 Agent 记录只恢复工具调用，不恢复推理链
- **方向**：若需回看推理过程，可在 `agent_sessions.steps` 或独立表记录 `step` 事件（现有 `SseEvent::Step` 已是结构化载荷、落库即可）；前端恢复时按 `at` 升序回填 `chain`。
- **为何现在不做**：有意裁剪——推理链是流式过程的逐条快照，量级大、复用价值低；工具调用与最终产出才是复盘所需，持久化整条 chain 会显著增大写入量而收益有限。（恢复的 `toolCalls` 一律置 `status='done'`，与实时 SSE 累积形态区分。）
- **触发条件**：源文档未给触发条件【待核实】（只写「若需回看推理过程」）。候选触发：出现「复盘必须依赖推理链」的真实场景（如排查某类失败步骤）。
- **关联**：`遗留.md` 的 L10。
- **来源**：archive/2026-09-16-consolidation/known-limitations.md L10

### L11 沙箱 iframe 保留 `allow-modals`，`postMessage` 无法校验 origin
- **方向**：**加固路径（若未来平台支持）**——改用 `MessageChannel` 端口传递（端口对象天然只有双方持有，取代「广播 channel + nonce」模型），可彻底摆脱 origin/source 判别与 `'*'` targetOrigin。
- **为何现在不做**：`origin`/`source` 校验属**平台限制、当前不可用**——不透明源 iframe 的 origin 恒为 `"null"`（无判别力）；WebView2 会把跨源 iframe 的 `event.source` 包装成另一个对象、与 `iframe.contentWindow` 不相等，按「不等即拒」会**误杀全部正常消息**。故 nonce（128 位随机、仅存于执行闭包、经 URL fragment 交付、不落 DOM/存储）是当前唯一可靠身份凭据；`allow-modals` 属**有意保留**（角色卡作者脚本用 `alert`/`confirm` 做协议确认与提示，移除会让这类卡静默失效）。外层仍有站点 CSP、`/sandbox.html` 下发、RPC op 白名单、innerHTML 清洗。
- **触发条件**：平台侧变化——WebView2/浏览器在**不透明源** iframe 下可可靠传递 `MessageChannel` 端口（源文档口径「若未来平台支持」）。
- **关联**：`遗留.md` 的 L11。
- **来源**：archive/2026-09-16-consolidation/known-limitations.md L11

### L22 同类工具不同参数的空转不被熔断
- **方向**：可考虑「同工具连续调用 >N 轮 **且** 该工具输出连续 K 次无实质变化」的双条件；或对 `bash`/`read` 这类只读工具引入「重复读同一目标」的语义去重。接口层 `LoopGuard` 已支持自定义窗口/阈值（`LoopGuard::new(window, threshold)`），扩展无需改动熔断算法本体。
- **为何现在不做**：有意裁剪——收窄到「同工具名 >N 次即熔断」会**误杀合法工作**（真实任务确实可能需要连续执行几十条不同命令）；可靠区分「空转」与「有进展的多步工作」需判断**任务状态是否推进**（结果是否变化、目标是否更近），属语义级判定、误杀代价高于收益。务实缓解手段是**调低 `max_tool_rounds`**（设置页可配，默认 32），perf 门禁的「上下文收敛性」一栏会提示 prompt 增长异常。
- **触发条件**：源文档未给触发条件【待核实】。候选触发：再次出现该形态的成本失控——实测先例是一次 solo 任务在该形态下跑满 54 轮、耗时 300 秒、累计 prompt 137 万 token（单轮受裁剪约束稳定在 4k–13k、上下文已收敛），且调低 `max_tool_rounds` 无法缓解。
- **关联**：`遗留.md` 的 L22；`经验.md`（对照案例：L23 裁剪失效时同形态 7 分钟不收敛、需人工 stop）。
- **来源**：archive/2026-09-16-consolidation/known-limitations.md L22

- **触发条件**：出现「需要计时序指标做容量规划」的真实需求（源文档给定）。

### L26 事件流无持久化与回放

### L27 413（请求体过大）未统一为 JSON 错误体
- **方向**：若将来 413 真的成为用户可见问题，可在 `DefaultBodyLimit` 之外包一层自定义 `Layer`，把 `LengthLimitError` 映射为 `{error, code}` + 413。
- **为何现在不做**：有意保留例外——根因是 `DefaultBodyLimit`（35MB 层）在**提取器被调用前**就由 tower 中间件拒绝、产生 `LengthLimitError`，自研 `JsonBody<T>` 的 `FromRequest` 根本不执行；要统一形状必须自定义 tower 层拦截 body `Frame` 错误流，改动面覆盖**全站请求体**。权衡是收益低（体积超限本就罕见、前端上传前已做体积校验）而成本高（回归面大），原因写在 `server-rs/src/api/json_body.rs` 头部注释。
- **触发条件**：413 成为**用户可见**问题（源文档给定）。
- **关联**：`遗留.md` 的 L27。
- **来源**：archive/2026-09-16-consolidation/known-limitations.md L27

## 四、架构演进与晋升

本节是**代际流动**与**工程化收尾**的长线方向：三结合的门槛本身是长期规则而非批次；未采纳的结构手术与「持续项」保留作决策溯源；数据库两条例是方向性缺口。

### ARCH-1 晋升门槛：L2→L1「协议稳定 + 外部依赖成型」、L3→L2「≥2 调用点复用 + 测试覆盖」
- **方向**：青层创新成熟 → 过晋升门槛 → 升入中层打磨 → 沉淀为老层契约。**L3→L2**：能力被 **≥2 个调用点复用**且**有测试覆盖**；**L2→L1**：**协议稳定**且**外部依赖成型**。三关：①通过既有测试套件（测试套件本身是 L1 经验库、晋升门槛的裁判）；②不破坏兼容协议；③经评审确认边界。新能力一律**先进 L3 验证**（沙箱/开关/注册表三者至少有一），再按门槛逐级晋升；禁止「新代码直接改写 L1 契约而不带测试」。
- **为何现在不做**：这是长期演进规则而非一批改动；门槛此前只有文字描述、无记录，2026-09-14 起由 §6.1 晋升台账补上「有据可查」（见本文 ARCH-3）。
- **触发条件**：当某 L3 能力出现**第 2 个调用点**且已有测试覆盖（→ 评估 L3→L2）；当某协议不再变动且外部依赖稳定（→ 评估 L2→L1）。每次晋升须补台账行并在 `arch-layers.json` 同步代际。
- **关联**：本文 ARCH-3、ARCH-2；`计划.md`（代际归属变更须先改 `tools/arch-layers.json`，否则规则 I 直接 FAIL）。

## 五、本机算力与 GPU

> 本节是对 `GPU加速可行性分析.md`（分析日期 2026-09-15，基线 commit `5d04de4`；方法：全仓静态审计——server-rs 224 文件 / 76,855 行 + web/src 227 文件 / 40,605 行——并复用 `perf-baseline.md` 的实测微基准）的**全文移植**。原文档只做可行性判断、未改代码，此处保持同样口径。
> **结论前提（原 §一）**：①**对现有代码做 GPU 加速：不可行，收益为负**——本地没有任何一项计算的规模达到 GPU 的经济门槛；唯二候选（向量余弦 0.3 MFLOP、BPE token 计数）即使被 GPU 算到零耗时，端到端也只快千分之几毫秒量级（`fast` 档实测总耗时 7,679 ms）。②**前端渲染层不需要动手**：Tauri 2 在 Windows 上走 WebView2、未传 `--disable-gpu`，合成与光栅化已由 Chromium 的 GPU 路径承担；前端瓶颈是 `sanitize-html`（3.057 ms/16.8k 字符）与 DOM 节点数，属 JS/DOM 成本，没有 GPU 可编程接口可用。③**唯一有价值的 GPU 落点是「新增本地模型推理能力」**，即把远端算力搬回本机（本地 LLM / embedding / ASR / TTS / 图像）——这是**架构增量**而非性能优化：其算力需求比现有本地计算**高 3~6 个数量级**，只有到那个量级 GPU 才有意义；其中本地 embedding 性价比最高，**且在 CPU 上就能达成目标、并不需要 GPU**，故下文四条落点中只有第 4 条（ASR/TTS/图像）把 GPU 当作必需项。
> **事实基础与逐项可行性（原 §二、§三）**：远端占绝对多数——唯一 LLM 通路是 OpenAI 兼容 HTTP 客户端（`connectors/mod.rs:27-30`，仅 Mock/OpenAi 两个变体），embedding 同样是远端接口（`services/embedding_service.rs:1-10,86` 调 `POST {base}/embeddings`），全仓 grep `gguf|onnx|safetensors|llama|candle|ort|tch|whisper|cuda|gpu|vulkan|metal|wgpu|directml|SIMD|AVX` 零命中。本地真在算的量级：世界书关键词匹配（54 条目 × 扫描窗口）正则预编译后 **0.062 ms**；BPE token 计数（30 条 × 2k token，最坏单次 88 万 token）**29.4 ms → 命中缓存 <1 ms**；向量余弦（单角色全部记忆，默认上限 200 条 × 维度 16..8192）**<1 ms**；markdown 渲染 16.5k 字符 **0.453 ms**；HTML 净化 16.8k 字符 **3.057 ms**；角色卡解析（只读容器 chunk 头、不解码像素）可忽略。**关键推断**：`fast` 档那「约 1 s 本地预处理」里上述各项微基准加起来**不足 5 ms**，主体是 SQLite/文件 IO 与「每轮一次远端 embedding 往返」而非本地算力（建议用一次火焰图确认；若属实，治理方向是减少 IO 与调用轮次、**与 GPU 无关**）。逐项可行性（原 §三，仅就现有代码）：向量余弦/KNN（200×1536 ≈ 0.3 MFLOP）**不值得**——kernel launch（5~20 µs）+ 传输（1.2 MB ≈ 0.1 ms）已超过全部计算，要撑起 GPU 数据量需再涨约 3 个数量级；BPE token 计数**不适合**——每字节十余次整数运算且是**串行 merge**（260 KB 上下文 ≈ 2.6 M 次操作），GPU BPE 的收益在大批量训练吞吐、单文档延迟赢不过已缓存 CPU 路径，正解是「少算/缓存」（已有）而不是换处理器；正则/JSON/PNG chunk/EJS/Migration、前端 DOM/字符串、Tauri/Rust 侧（`src-tauri/src/lib.rs` 只有启动后端、健康检查、文件复制、DB 路径改写）、构建耗时（CPU 并行编译）、SQLite（`vec0` 是上游 C 扩展、CPU 标量、无 GPU 后端）一律**不适用**。
> **与既有架构约束的冲突（原 §五）**：①**「单 exe、无需分发 dll」是明确设计约束**（`server-rs/Cargo.toml:18-21` 静态链接 sqlite-vec；`api/static_files.rs:209` 用 `include_dir!` 内嵌 `web/dist`）——CUDA 版运行时需随包分发 cudart/cublas（+200 MB~2 GB）直接冲突，若必须做应优先选 Vulkan / DirectML / wgpu 后端（单 dll、跨厂商）；②**Android 分支已存在**（交付形态「全内嵌单机版」），GPU 方案必须在 Windows（WebView2 + D3D/Vulkan）与 Android（Vulkan/OpenCL/NNAPI）**双端成立**，移动端显存与散热约束更硬、后端选择自由度更低；③**并发模型是两套资源管理**——后端为 axum/tokio 异步 + r2d2 读池 + 单写连接，本地推理是重阻塞任务，需要独立线程池 + 显存/内存预算，与现有池化模型平行，必须设计隔离与排队；④**数据面已就绪的部分不多**——记忆向量存 `vec0`、`embedding_dim` 支持 0（自动探测）与 16..8192，若要换本地 embedding 模型，维度切换与「重建向量索引」流程已有入口（维度不匹配时保留旧数据、由用户手动重建，见 L7）。

### GPU-1 本地 embedding（推荐先做）
- **方向**：替换 `embedding_service` 的远端实现为**本地小模型**（如 bge-small 级），**保留远端作为可切换后端**；验收标准是 CPU 批量耗时与远端往返时延持平，**不引入新分发物**。收益：省掉每轮一次远端往返与网络依赖，聊天正文不再外发。**GPU 判断：不需要 GPU**——小模型在 CPU 上每批约几十毫秒即达标；只有批量大幅上调（如离线重建整个记忆库向量）时 GPU 才有意义。
- **为何现在不做**：现状每轮最多 32 条 × 4000 字符走远端 HTTP，往返成本已被接受（`fast` 档 TTFT 7,025 ms 的主体是上游等待、服务端本地预处理约 1 s）；引入本地模型要连带决定模型下载/校验/磁盘占用与分发形态。
- **触发条件**：原 §六 给定——②产品决定上「离线模式 / 隐私优先 / 免 API 成本」（即本地 LLM 进入路线图）；④出现实测证据表明**本地**阶段（而非上游等待）成为用户可感知的瓶颈。另见本文 PB-5。
- **关联**：本文 GPU-2、GPU-3、PB-5、RD-2；`遗留.md` 的 L7（维度切换与手动重建索引流程）。
- **来源**：archive/2026-09-16-consolidation/GPU加速可行性分析.md §四 1、§六、§七 1

### GPU-2 本地 reranker / ANN 索引
- **方向**：引入交叉编码器 reranker 与 ANN 索引（`sqlite-vec` 的分区/量化能力）。现状是 `memory_service.rs:545-590` 按 id 取全部候选向量、再在 Rust 里逐条算余弦（`:263`），候选量受 `DEFAULT_MEMORY_MAX_ENTRIES=200` 约束；L7 明确不建 ANN。**只有在那个量级下，GPU 与批处理才第一次成为「结构性必需」。**
- **为何现在不做**：精度与成本当前都不构成问题——精确 KNN 在 5k×512 维下约 1–15 ms，ANN 的召回率损失与索引一致性维护成本不划算。
- **触发条件**：原 §六 给定——①记忆条目规模从「每角色 ≤200」涨到 **10^5 量级**，或引入 **reranker/交叉编码器**。
- **关联**：`遗留.md` 的 L7；本文 GPU-1、RD-2、PB-5。
- **来源**：archive/2026-09-16-consolidation/GPU加速可行性分析.md §四 2、§六

### GPU-3 本地 LLM（改动最大）
- **方向**：收益是**产品级**的——「离线可用」「正文不出本机」「无 API 成本」，不是延迟优化。建议路线（原 §七 2）：先做「**本地推理 spike**」——单文件、可开关、独立进程或独立 dll 边界，先用 Vulkan/DirectML 后端验证「**单 exe + 可选 DLL**」的交付形态是否可接受，再谈模型管理（下载/校验/磁盘占用）；**先 spike，不直接落地**。全程**不动现有 CPU 热路径**：世界书正则缓存、token 内容缓存、工具定义快照这些已验证的优化与 GPU 无关，不要借 GPU 立项把它们推翻。
- **为何现在不做**：代价与既有架构约束直接冲突（原 §五 ①②③：单 exe 无 dll 的分发约束、必须双端成立、需要独立的线程池与显存预算）；源文档明确「建议先做 spike」。
- **触发条件**：原 §六 给定——②产品决定上「离线模式 / 隐私优先 / 免 API 成本」，即**本地 LLM 进入路线图**。
- **关联**：本文 GPU-1、GPU-4、RD-1；`计划.md`（若 spike 立项）。
- **来源**：archive/2026-09-16-consolidation/GPU加速可行性分析.md §四 3、§五、§六、§七 2/4

### GPU-4 本地 ASR / TTS / 图像生成
- **方向**：若做语音对话或角色立绘，**GPU 是必需项**（whisper.cpp / sherpa-onnx / 扩散模型）——这是本仓库未来**最可能出现真实 GPU 需求**的方向。现状 `services/audio_service.rs` 只管播放列表状态与 URL、`api/audio.rs` 三个路由，不解码不合成；全仓无 canvas/WebGL/`<video>`/OCR/缩略图。路线（原 §七 3）：**语音/图像另立专项，不与应用主链路捆绑**。
- **为何现在不做**：功能未立项；且与「单 exe、无需分发 dll」约束冲突（需先定 Vulkan/DirectML/wgpu 后端并验证移动端可行性）。
- **触发条件**：原 §六 给定——③语音对话、本地图像生成、Live2D/表情差分等**富媒体功能立项**。
- **关联**：本文 GPU-3；`计划.md`（音频/渲染面板历史批次见 `archive/plan5-audio-render-panels.md`）。
- **来源**：archive/2026-09-16-consolidation/GPU加速可行性分析.md §四 4、§六、§七 3

**附：低成本证伪上述 GPU 结论的路径（原 §八）**——① 对 `fast` 档做一次 profiler（Windows 可用 ETW / `tracing` 已有 span 基建），拆出那 1 s 本地预处理的构成——若其中算力占比 <5%，则「GPU 无用」成立；② 写一个 500 行内的微基准：对 200×1536 的余弦打分，比较 CPU 标量、CPU SIMD、GPU 三条路径的端到端（含传输与启动）耗时，预期 GPU 不占优；③ 对极端 `plan` 任务（累计 150 万 token）统计 token 缓存命中率——若命中率高，说明连「最大的本地算术负载」也已被缓存消化。（另：原 §二「1 s 的主体是 IO 与远端 embedding 往返」这一推断，也建议用一次火焰图确认。）
**附：核验到的一处文档与代码不一致（原 §九）**——`known-limitations.md` L7 描述为「`vec0` 走精确 KNN」，但代码路径并非 `vec0` 的 KNN 查询：`services/memory_service.rs:545-590` 的 `get_vectors` 是 `WHERE memory_id IN (?)` 取回 BLOB，再在 `:263` 用 Rust 侧 `cosine_similarity` 打分（`embedding_service.rs:191`）。即当前实现是「**按 id 取向量 + Rust 内标量余弦**」，`vec0` 只作存储用。该差异**不影响 L7 的结论**（都是精确检索、无 ANN），但描述应更正。

## 六、已实测证伪的方向（不要再提）

本节收「曾被当作优化方向、但已被**实测**证伪」的条目。写进来的目的是**避免后来者重复提议**：每条都附源文档的实测数字；重开任一条之前，先拿出推翻该数字的新证据。

### GPU-0 对现有代码做 GPU 加速
- **方向**（已被实测证伪的提议，登记备查）：把现有 CPU 热路径（向量余弦/KNN、BPE token 计数、正则/JSON/PNG chunk/EJS、前端 DOM 与 `sanitize-html`、SQLite `vec0`）搬到 GPU。
- **实测证伪证据**：① 算术强度——余弦 200×1536 ≈ **0.3 MFLOP**，低于 kernel launch（5~20 µs）与传输（1.2 MB ≈ 0.1 ms）的固定成本之和，要撑起 GPU 数据量需再涨约 3 个数量级；BPE 是**串行 merge**（260 KB ≈ 2.6 M 次操作），GPU 的赢面在大批量训练吞吐、不在单文档延迟。② 端到端——`fast` 档实测总耗时 **7,679 ms**，其中上游等待 **7,025 ms**，本地预处理约 1 s 而各项微基准加起来**不足 5 ms**。③ 前端——合成与光栅化已由 WebView2/Chromium 的 GPU 路径承担，瓶颈是 `sanitize-html`（**3.057 ms** / 16.8k 字符）与 DOM 节点数，无 GPU 可编程接口。结论：**不可行、收益为负**——即使被 GPU 算到零耗时，端到端也只快千分之几毫秒量级。
- **为何现在不做**：上述三项实测/静态分析已把该方向的收益上界钉死为「千分之几毫秒」，而成本（新分发物、双端与移动端后端选择、与单 exe 约束冲突、独立线程池与显存预算）远超收益。
- **触发条件**：源文档未给触发条件【待核实】（§七 只列「不做」与实测数字，未给重开条件）。候选触发：①出现实测证据表明**本地**阶段（而非上游等待）成为用户可感知瓶颈，且瓶颈落在**可并行算力**上；②引入本地模型推理（算力需求高 3~6 个数量级）——即本文 GPU-1~GPU-4 立项时，GPU 的讨论才重新有意义，届时先跑原 §八 的三条低成本证伪路径。
- **关联**：本文 GPU-1~GPU-4、PB-5；`遗留.md` 的 L7。
- **来源**：archive/2026-09-16-consolidation/GPU加速可行性分析.md §一、§二、§三、§八

### PB-1 `prompt_kit` 链式 `replace`
- **方向**（已被实测证伪）：把 `prompt_kit` 的 6 次链式 `replace` 合并为一次扫描以减少字符串拷贝。
- **实测证伪证据**：**0.042 ms/次**，收益可忽略（2026-09-14 第二轮性能治理，release 微基准）；源文档在「实测修正静态审计」表中把该结论标为**撤销**。
- **为何现在不做**：实测收益低于改动风险；该段代码是提示词共享原语，动它要重新跑引擎与任务双侧的注入回归。
- **触发条件**：源文档未给触发条件【待核实】（§七 只列「不做」）。候选触发：渲染量级出现数量级变化（如单请求注入段从「几十段」涨到「数万段」）**且**实测该段进入热点。
- **关联**：本文 PB-2、PB-4（同批被撤销/降级的静态审计结论）。
- **来源**：archive/2026-09-16-consolidation/perf-baseline.md §七、§四

### PB-2 `settings_snapshot()` 整体 `clone`
- **方向**（已被实测证伪）：消除 `settings_snapshot()` 的整体 clone。
- **实测证伪证据**：clone 本身 **0.007 ms**；真正成本在**工具定义的锁内 clone + sort**，该处已改为快照缓存（P3-1，写路径失效）。
- **为何现在不做**：剩余成本已在噪声量级；继续拆只会引入引用生命周期复杂度。
- **触发条件**：源文档未给触发条件【待核实】（§七 只列「不做」）。候选触发：工具定义数量出现数量级增长（从十余个到数十上百个）**且**该处再次进入热点。
- **关联**：本文 PB-1；`经验.md`（工具定义快照缓存的实现）。
- **来源**：archive/2026-09-16-consolidation/perf-baseline.md §七、§四

### PB-3 任务写路径事务化
- **方向**（已被实测证伪）：把任务写路径的逐条 INSERT 合并为单事务批量写入。
- **实测证伪证据**：单条独立 INSERT 提交 **0.686 ms/条**，同事务批量 **0.013 ms/条**（**52×**），但一次任务约 12 条写入 ≈ **8 ms**——相对 LLM 往返的秒级延迟**不足以构成优化理由**。
- **为何现在不做**：**收益低于语义风险**（事务化会改变写失败语义与锁粒度，牵动取消/收尾路径）。
- **触发条件**：源文档未给触发条件【待核实】（§七 只列「不做」）。候选触发：单任务写入条数或频率出现数量级变化（如每任务数百条写入、写路径进入端到端瓶颈实测）。
- **关联**：本文 PB-1；`计划.md`（若写路径改动的批次立项）。
- **来源**：archive/2026-09-16-consolidation/perf-baseline.md §七、§三

### PB-4 TaskBoard 全量 markdown 重算
- **方向**（已被实测降级）：TaskBoard 不再全量重算 markdown。
- **实测证伪证据**：markdown-it 渲染 16.5k 字符仅 **0.453 ms**；模拟流式 60 帧全量重渲累计 **18.1 ms**；真正较重的前端路径是 `render_html=true` 时的 `sanitize-html`（**3.057 ms** / 16.8k 字符，**约 markdown 的 7 倍**）。
- **为何现在不做**：源文档裁定为**降级（低优先）**——前端该管的是 sanitize 路径，不是 markdown 重算；聊天侧流式的「每帧全长重渲」也已由按帧节流（rAF）改善，残余成本并非当前瓶颈。
- **触发条件**：源文档未给触发条件【待核实】（§七 只列「不做」）。候选触发：①消息长度/节点数出现数量级增长使重算进入实测热点；②`render_html` 成为默认开启且 sanitize 路径成为可感知延迟。
- **关联**：本文 GPU-0（前端瓶颈的同一结论）；`遗留.md` 的 L13（逐 token 重渲染的历史记录与残余）。
- **来源**：archive/2026-09-16-consolidation/perf-baseline.md §七、§四

### PB-5 每请求 embedding HTTP
- **方向**（暂不做，需单独立项）：优化「每请求一次 embedding 远端 HTTP 往返」。
- **实测证伪证据**：`embedding_enabled=false` 时该路径**根本不触发**——即多数用户在关闭 embedding 时为零成本，仅开启语义召回的用户承担该往返。
- **为何现在不做**：源文档结论是「**暂不做，需单独立项**」——它不是一个局部优化，而要与「本地 embedding / 缓存 / 批量重建」成套设计（见本文 GPU-1）。
- **触发条件**：源文档未给触发条件【待核实】（§七 只写「暂不做，需单独立项」）。候选触发：①embedding 默认开启成为常态且往返进入 TTFT 实测瓶颈；②本文 GPU-1（本地 embedding）立项——两者是同一方向的两种解法，应合并评估。
- **关联**：本文 GPU-1、RD-2；`遗留.md` 的 L7。
- **来源**：archive/2026-09-16-consolidation/perf-baseline.md §七

### LH-3 会话分层持久化（turn ckpt + event-index + content_digest + recovery）

- **触发条件**：源文档未给触发条件【待核实】（原文口径「可后续加」）。候选触发：出现「会话数据部分损坏 / 需要按轮回滚」的真实场景。

### LH-4 工具结果 post-execute 管道（censor / mvu 剥离迁入统一管道）

- **触发条件**：源文档未给触发条件【待核实】。候选触发：出现第三处「结果后处理」实现（统一管道要收口的第三个调用点），或某次改动需要在三处同时改同一语义。
- **关联**：archive/learn-deepseek-harness.md 借鉴点 3（**同一方向**的更完整表述，两者应合并评估）；`计划.md`。

- **触发条件**：源文档未给触发条件【待核实】。候选触发：出现多用户/多实例共享上游配额的需求（与本文 T5 的触发同源）。

### LH-6 消息队列 steer/drop 策略（Reasonix bot 借鉴）
- **方向**：对用户连发消息引入 steer（插队进当前轮）与 drop（丢弃/合并）策略。
- **为何现在不做**：源文档口径「对 RP 连发消息**有参考价值，暂缓**」。
- **触发条件**：源文档未给触发条件【待核实】。候选触发：出现「流式生成中连发消息导致语义混乱」的高频反馈，或 followup/plan-chat 的排队语义需要扩展时。
- **关联**：`计划.md`（followup 与 plan-chat 的现状、任务事件 SSE）。
- **来源**：archive/learn-harness-2026-08.md §方向参考

### LD-1 append-only 会话日志 +「model-visible ⟺ logged」不变量
- **方向**：保证**模型看到的每个输入都能从会话日志回溯**（append-only session log + 「可见即已记录」不变量），对提示词缓存、调试、SillyTavern 导入导出都有利。
- **为何现在不做**：改造大——kedai 已有 SQLite 落库，但「模型可见即已记录」还需覆盖 system / 工具定义 / 注入合成等**拼装侧产物**，属长期方向。（`任务引擎六模式.md` §六 亦把该文登记的 append-only 会话日志记为「**暂不落地·长期方向**」，并特别提醒：该节对 `EventSink`/`ModeExecutor` 的 seam 表述是**本项目自身**的演进方向，勿误读为该 harness 的既有特性。）
- **触发条件**：源文档未给触发条件【待核实】。候选触发：①前缀缓存诊断显示「前缀漂移」而**无法从日志定位**；②出现「需要从会话日志完整重放某轮请求」的调试场景。
- **关联**：`计划.md`（缓存感知压缩管线与 `/api/diagnostics/cache` 现状）；本文 LH-3、ARCH-2；`任务引擎六模式.md` §六。
- **来源**：archive/learn-deepseek-harness.md §方向参考

### LD-2 并行工具执行（`isConcurrencySafe` + 并行池）
- **方向**：对 `read` / `search` 等**只读**工具并行执行（kedai 当前工具串行）。
- **为何现在不做**：角色扮演场景工具调用少、收益有限（源文档口径「暂缓」）；任务模式下并行会与 `set_plan` 整列覆写、usage 记账口径、取消传播同时交织（参见本文 WF-11 的并行节点风险）。
- **触发条件**：源文档未给触发条件【待核实】。候选触发：出现「单轮多只读工具调用导致 TTFT 明显拉长」的实测证据；或 WF-11 的节点并行落地后可复用同一套调度。
- **关联**：本文 WF-11；`计划.md`（任务模式工具循环的现状）。
- **来源**：archive/learn-deepseek-harness.md §方向参考
