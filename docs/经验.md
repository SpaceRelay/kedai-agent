## 一、环境与工具链

### 经验 1 —— cargo 必须 vcvars64 环境（原 `MAINTENANCE.md` §10 条目 1）

- **现象**：新开终端里直接 `cargo build` 报 `link.exe not found`。
- **根因**：MSVC 工具链未注入当前 shell，链接器不在 PATH 上；裸 PowerShell/cmd/Git Bash 里也可能没有 cargo 环境。
- **做法**：用 `build.ps1`（内部已做该处理），或先 `call "C:\Program Files (x86)\Microsoft Visual Studio\2022\BuildTools\VC\Auxiliary\Build\vcvars64.bat"`，再在同一 shell 里执行 build.ps1 / cargo（脚本直接调 cargo/npm，继承环境）；Git Bash 中可用 `cmd //c "<包装.bat>"` 形式嵌套调用。

### 经验 3 —— PowerShell 5.1 中文乱码（原 `MAINTENANCE.md` §10 条目 3）

- **现象**：`start.ps1` 中文乱码；用默认写出的 JSON 交给 curl 会带 BOM 导致解析失败（冒烟曾踩坑）。
- **根因**：PowerShell 5.1 脚本与文件编码处理不统一——`Get-Content` 默认非 UTF-8，而所谓「`Write-Content`」默认 UTF-16。
- **做法**：`start.ps1` 需 **UTF-8 with BOM**；`Get-Content` 读中文文件建议 `-Encoding UTF8`；写 JSON 给 curl 时显式用 UTF-8 无 BOM。

### 经验 4 —— PowerShell 里 `curl` 是别名（原 `MAINTENANCE.md` §10 条目 4）

- **现象**：在 PowerShell 里敲 `curl` 实际走的是 `Invoke-WebRequest`，参数语义与真 curl 不同。
- **根因**：PowerShell 内置别名遮蔽了可执行文件。
- **做法**：要用真 curl 就写 `curl.exe`。

### 经验 5 —— axum 0.8 路由语法（原 `MAINTENANCE.md` §10 条目 5）

- **现象**：旧写法 `:id` 的路由参数不生效；multipart 解析在测试里挂起。
- **根因**：axum 0.8 的路径参数语法改成了 `{id}`；multipart 由 `axum::extract::Multipart` 提供，而 multer 在 one-shot 测试流下会 **挂起**，故 upload 采用了手动字节解析。
- **做法**：路径参数一律写 `{id}`；上传类接口沿用仓库既有的手动字节解析，不要换回 multer。

### 经验 6 —— 端口残留（原 `MAINTENANCE.md` §10 条目 6）

- **现象**：重新编译前报文件被占用，或新实例起不来。
- **根因**：后台/被 kill 的旧实例会短暂占用 exe 句柄。
- **做法**：编译前确认无 `kedai-server.exe` 进程（`Get-Process kedai-server`）；端口被占用 `netstat -ano | findstr ":3001"` → `taskkill /f /pid <pid>`（注意可能残留 Node 旧服务）。

### 经验 7 —— tiktoken-rs 首次运行需联网下载 BPE 词表（原 `MAINTENANCE.md` §10 条目 7）

- **现象**：离线环境首次运行 token 计数相关功能会失败/变慢。
- **根因**：tiktoken-rs 需要下载 BPE 词表（与 js-tiktoken 一致）。
- **做法**：首次运行保证联网；token 计数按模型映射 o200k/cl100k/p50k，**未知模型回退 cl100k**。

### 经验 9 —— `.env` 修改的即时性（原 `MAINTENANCE.md` §10 条目 9）

- **现象**：改了 `.env` 后行为不变。
- **根因**：配置在启动时读取一次。
- **做法**：改 `.env` 后必须重启服务；运行期可改的只有设置界面里的模型等内存项（重启失效）。

### 经验 10 —— 日志编码（原 `MAINTENANCE.md` §10 条目 10）

- **现象**：Windows 控制台上日志中文显示乱码。
- **根因**：控制台 GBK 与落盘 UTF-8 混排。
- **做法**：乱码不影响落盘内容，用编辑器以 UTF-8 打开 `logs/` 下的 log 查看即可；排查问题先看当天日志文件。

### 经验 22 —— `server-rs\target` 下新建的 exe 可能被安全软件拦截执行（原 `MAINTENANCE.md` §10 条目 22）

- **现象**：2026-09-13 实测踩坑，`cargo build/check/test` 在 **默认 target 路径**下报 `failed to run custom build command for native-tls … 拒绝访问。 (os error 5)`，失败在这个 build script 上。
- **根因**：逐步排查结论——**不是目录权限**（`icacls` 显示 ACL 与可用外部目录完全一致）；**不是残留产物**（`rm -rf target` 全量清空后仍在同一位置失败）；**不是目录性质**（`dir /AL` 与 `Get-Item … -Force` 确认它不是 junction/符号链接）；**关键线索**是把一个**既有**的 `cmd.exe` 复制进 `server-rs\target\` 能正常执行，而 cargo**刚编译出来的**`build-script-build.exe` 一执行就「拒绝访问」——即拦截针对「在该目录下新建的可执行文件」，典型的实时防护（杀软）行为。
- **做法**：把后端产物外置到白名单目录，两种等价写法——`.\build.ps1 -RustTargetDir D:\kedai-build`（**推荐给构建脚本**，只作用于 server-rs）；或设环境变量 `CARGO_TARGET_DIR=D:\kedai-build`（作用于所有 cargo 调用，含 src-tauri；但 `build-portable.ps1` 期望 `src-tauri\target\release\kedai-portable.exe`，用此变量会让便携版产物落到别处，故 **优先用 `-RustTargetDir`**）。`build.ps1` 已支持该参数，并把「后端产物目录」统一解析给新鲜度检测与 exe 校验使用；以前它硬编码 `server-rs\target`，外置产物时会误报「Rust 编译失败:未生成 …」（2026-09-13 批次 1 起 **清理路径也跟随该参数**，外置目录不再漏清）。同一现象在 `archive/2026-09-16-consolidation/优化实施方案-2026-09.md` 亦有历史记录（当时以 `CARGO_TARGET_DIR` 降级处置）。

### 经验 31 —— 360 安全卫士拦截 cargo 新生成的 build script 可执行文件（原 `MAINTENANCE.md` §10 条目 31）

- **现象**：2026-09-15 实测，os error 5。release 构建在 `icu_normalizer_data`/`icu_properties_data` 等 build script 处失败：`error: failed to run custom build command for <crate>`，细节为 `could not execute process ...\build-script-build (never executed)` + `拒绝访问。 (os error 5)`。**注意它看起来像依赖或权限问题，实际都不是**。
- **根因**：逐步排除（照此自查，别绕远路）——`Get-MpComputerStatus` 显示 Defender `RealTimeProtectionEnabled=False` → **不是 Defender**；SAC（`HKLM\SYSTEM\CurrentControlSet\Control\CI\Policy` 的 `VerifiedAndReputablePolicyState`）为 `0` → **不是 Smart App Control**；**决定性证据**是把一个**既有**的 `cmd.exe` 复制进同一目录能正常执行，而 cargo**刚编译出来**的 build script exe 一执行就「拒绝访问」，且随后**被安全软件删除**（手动补放同名文件，重跑后仍消失）→ 拦截针对「新生成的可执行文件」，**与条目 22 同源**（同一台机器上 360 安全卫士的实时防护；`Get-CimInstance -Namespace root/SecurityCenter2 -ClassName AntiVirusProduct` 可确认其存在）。
- **做法**：临时关闭 360 实时防护，或把 `server-rs\target` 与 `src-tauri\target` 加入信任区，再重跑 `.\build.ps1`。**实测无效的绕法（别试）**：`-j 1` 降并发、外置 `CARGO_TARGET_DIR`/`-RustTargetDir`（条目 22 的规避对本例 **无效**——拦截对象是 cargo 的 build script，不是最终链接出的 rlib/exe）、清理 `.fingerprint` 与新产物。以上均复测仍被拦。**影响面提示**：本例中 **测试版 `dist\kedai-server.exe` 已正常产出**，只有 `src-tauri` 便携版链路被阻断——故「便携版缺失」时先按本条查杀软，不要怀疑 Rust 代码。

### 经验 E1 —— Windows 上 curl 直接 `-d` 中文 JSON 会被编码破坏（原 `AGENTS.md`）

- **现象**：Windows 上 `curl -d '<中文 JSON>'` 报 `invalid unicode code point`。
- **根因**：命令行参数编码在 Windows 下被破坏，中文无法原样传入。
- **做法**：中文请求体一律写成 UTF-8 文件，再用 `--data-binary "@file"` 发送。

### 经验 E2 —— 文档里写的函数名可能全库零命中，照文档改代码会改错位置（原 `archive/2026-09-16-consolidation/三结合彻底落实-实施计划.md` §〇之二）

- **现象**：计划文档要求改 `run_task_background`，实际 `grep` 全库 **零命中**。
- **根因**：计划文档由静态审计产出，未逐条与代码现状核对（同类问题在本文「文档与回填」组多次出现）。
- **做法**：动手前先 `grep` 交叉验证文档所述符号/路径是否真实存在；工具链方面同节确认：Rust 测试必须经 vcvars64（MSVC toolchain），`tools/check-all.ps1` 已封装该逻辑。

### 经验 E3 —— bash 里传 Windows 绝对路径要加引号（原 `archive/2026-09-16-consolidation/残余任务与后续计划-2026-09-13.md` §八 2）

- **现象**：`-RustTargetDir D:\kedai-build` 在 bash 里反斜杠被吃掉，变成 `D:kedai-build`（相对路径），产物散落进仓库。
- **根因**：bash 对反斜杠做转义处理。
- **做法**：写成 `-RustTargetDir 'D:\kedai-build'`（加引号）。

## 二、构建与发布

### 经验 11 —— 便携版 README.txt 保留 UTF-8 BOM（有意）（原 `MAINTENANCE.md` §10 条目 11；源文档编号重复，此处照录）

- **现象**：`dist\Kedai-portable\README.txt` 带 `EF BB BF` 头。
- **根因**：Windows 记事本对无 BOM 的 UTF-8 中文按 ANSI 猜解会乱码，BOM 是 **兼容性刻意选择**。
- **做法**：不要在构建脚本里「修复」掉它（2026-09 D-8 注明）。

### 经验 16 —— 改完必须重跑 `build.ps1` 才进 exe（原 `MAINTENANCE.md` §10 条目 16）

- **现象**：2026-09 实测八项修复复核时发现，代码改了但 exe 版行为未变。
- **根因**：`cargo test`/`npm run build` 只更新 `server-rs/target/` 与 `web/dist/`；`dist\kedai-server.exe`、`dist\Kedai-portable\Kedai.exe` 与项目根 `Kedai.exe` 都 **不会自动更新**。
- **做法**：交付前必须跑一次完整 `.\build.ps1`（前端 + release + 便携版 + 指纹 sidecar）。**只跑 debug 不代表 exe 版已更新**；快速迭代可用 `.\build.ps1 -TestOnly`，但便携版会因此未同步，交付前补一次完整 `.\build.ps1`。

### 经验 20 —— 压缩/备份仓库报「系统找不到指定的路径」= jniLibs 里的 .so 符号链接悬空（原 `MAINTENANCE.md` §10 条目 20）

- **现象**：2026-09 实测。`tauri android build` 为省空间不在 `gen\android\app\src\main\jniLibs\<abi>\` 存真文件，而是 **建符号链接**指向 `src-tauri\target\<triple>\release\libkedai_desktop_lib.so`；构建收尾又会删除 `src-tauri\target` 回收磁盘 → 链接悬空。此后用资源管理器 / 7-Zip / HaoZip 压缩或备份仓库，工具跟随不到目标即报 `...libkedai_desktop_lib.so: 系统找不到指定的路径` 并中断，产物不完整。
- **根因**：派生文件与实际存储位置分离，清理 target 后链接悬空。**判定陷阱**：悬空链接上 `Test-Path` 仍返回 `True`（PS 5.1 不穿透解析），必须比对 `(Get-Item -Force).Target` 是否存在；只看 `Test-Path` 会漏掉。
- **做法**：已自动化——`tools\Write-BuildStamp.ps1` 的 `Clear-KedaiDanglingJniLibs` 在删除 target 后清理悬空链接（`build.ps1` 的 `-Tauri` 分支与 `tools\build-portable.ps1` 收尾均已接入，幂等，只删 SymbolicLink 不碰真实文件）。这些链接与 .so 本就是派生文件（`gen/android/app/.gitignore` 已忽略），下次 Android 构建自动重建。

### 经验 21 —— 压缩工具会「跟随」junction，把外置目录的体积一起装进压缩包（原 `MAINTENANCE.md` §10 条目 21）

- **现象**：2026-09 实测确认（HaoZip 对 junction 是跟随而非跳过）。若把构建产物用 junction 外置（如 `src-tauri\gen\android\app\build` → `D:\kedai-build\...`，1.4GB），则压缩 `D:\kedai` 得到的包会明显大于目录本身——实测 218MB 的目录压出 417MB 包。
- **根因**：压缩工具默认跟随 junction 递归收集内容。
- **做法**：需要「压缩包 ≙ 目录可见体积」时，压缩前应删除或排除 junction 目标，或改用 7-Zip 的 `-xr!` 排除。另注意 **悬空 junction 会被静默跳过、不报错**，与悬空 symlink（条目 20 的报错）行为不同。

### 经验 23 —— src-tauri 内嵌 server-rs 时，两份 Cargo.lock 会静默漂移（原 `MAINTENANCE.md` §10 条目 23）

- **现象**：2026-09-13 批次 1 实测并清零。`src-tauri/Cargo.toml` 以 `kedai-server = { path = "../server-rs" }` 内嵌后端，构建便携版时 cargo **完全忽略 `server-rs/Cargo.lock`**，在 `src-tauri/Cargo.lock` 里重新解析整棵依赖树——同一份后端源码，「测试版 `kedai-server.exe`」与「便携版 `Kedai.exe`」可能编译出 **不同版本**的依赖；跨 lock 的 `links` 冲突不会报错，分歧完全静默。
- **根因**：两条编译链各自独立解析依赖。实测两锁曾有 **17 个 crate 分歧**，含 `chacha20 0.10.2` vs `0.10.1`（**0.10.1 已被 yank**，密码学实现版本不同，最危险）；`cc 1.4.0` vs `1.4.2`、`find-msvc-tools`（编译 C 依赖的工具链，影响生成的 native 代码）；`thiserror`、`crossbeam-channel/-utils`、`combine`、`indexmap`、`tinyvec`、`wasm-bindgen` 家族（0.2.126 vs 0.2.127，wasm 目标专用，影响面小）。
- **做法**：① `node tools/check-lock-sync.mjs`（已进 `check-all` 阶段 `deps: check-lock-sync`，npm `check:lock`）以 **0 漂移**为基线，新增即 FAIL；② 新增依赖后两边各构建一次（便携版构建会自动带上 src-tauri 锁，测试版锁不会）；③ 对齐手法：`cargo update -p <crate> --precise <ver>`（**不支持一次多条 `--precise`**，逐条执行），或把落后一侧整体更新到较新版本；④ 不可避免的例外登记 `tools/lock-sync-baseline.json`；⑤ **本仓自身包**（`kedai-server`/`kedai-desktop`/`kedai-web`/`kedai`/`launcher`）已从比对中排除——版本号由 `bump-version.ps1` 变更后，两锁的自身版本会暂时不一致（各自构建时才更新），属发版的正常中间态而非依赖漂移（2026-09-13 实测：发版时该门禁曾误报，已加白名单）。根治途径是 Cargo workspace 化（未做，列入批次 4 可选项）。**注意**：对齐 `cc`/`thiserror` 等版本后须重跑完整 `cargo test`（本批次已跑，全绿）。

### 经验 26 —— 外置产物目录不能整删：会连带删掉同目录下的 Android 构建目录（原 `MAINTENANCE.md` §10 条目 26）

- **现象**：2026-09-13 实测。`build.ps1` 的收尾清理在批次 1 改为跟随 `-RustTargetDir` 后 **整删外置目录**——而本机 `D:\kedai-build` 下还挂着 `src-tauri\gen\android\app\build` 的 **junction 目标**`android-app-build`。整删后 APK 构建在 `:app:mergeUniversalReleaseJniLibsFolders` 报 `Failed to create parent directory ...app\build`（悬空 junction 无法再被当作目录创建），报错文案**不指向真因**，排查成本高。
- **根因**：清理逻辑把「cargo 的产物目录」等同于「整个外置目录」，而外置目录里混放了其它数据。
- **做法**：默认路径 `server-rs\target` 可整删；**外置目录只清 cargo 自己的子目录**（`debug`/`release`/`tmp`/`CACHEDIR.TAG`/`.rustc_info.json`），保留同目录其它数据（`build.ps1` 与 `tools/build-portable.ps1` 已按此修正）。修复手法：重建 `D:\kedai-build\android-app-build`（空目录即可，gradle 会重新生成内容）。另注：压缩/备份工具会 **跟随** junction（踩坑 21），与本次「悬空 junction 无法创建目录」是两个不同现象，勿混。

### 经验 27 —— 构建/门禁报 `failed to remove file ... os error 5`，先查是不是 exe 还在跑（原 `MAINTENANCE.md` §10 条目 27）

- **现象**：2026-09-13 实测。开发时用 `cargo run` 或 `start.ps1` 起了 `kedai-server`，随后跑 `build.ps1`/`check-all.ps1`，`cargo` 重新链接时报：
  ```
  error: failed to remove file `...\target\debug\kedai-server.exe`
  Caused by:
  拒绝访问。 (os error 5)
  ```
  由 `check-all` 的 `cargo test --workspace` 阶段抛出时，汇总表只显示 `FAIL`，文案像权限/杀软问题。
- **根因**：**Windows 不允许删除 / 覆盖正在运行的 exe**（错误发生在「删除」），与踩坑 22（杀软拦截 **新建 exe 的执行**，错误发生在「执行」）是两回事，两者共用 `os error 5` 这个码，极易混淆。已验证的判定手法：用 `FileShare.None` 独占打开产物，成功=未被占用、失败=被占用（注意不能只看「能不能删」：Windows 对运行中的 exe **有时允许删除**（删除挂起，名字立即释放、进程继续跑），此时 `Remove-Item` 会成功但产物已消失，症状反变成「未生成 exe」）。
- **做法**：编译前跑 `Clear-KedaiLockedServerArtifacts`（`tools/Write-BuildStamp.ps1`，已接入 `build.ps1`/`check-all.ps1`/`build-portable.ps1`）——把被占用的产物改名让位为 `<exe>.old`，cargo 随即写入同名新文件，**无需杀进程**，旧进程继续跑旧代码；未被占用的产物一律不动（不误伤增量编译）。另注：`cargo test` 期间若有 `kedai-server` 在跑，个别用例（如 `settings_connector` 的 `mock_auto_switches_to_openai_on_save`）可能因占用 `settings.json` 报 `Os { code: 32 }` 而假红；跑门禁前先关掉手动起的服务实例。

### 经验 E4 —— 单二进制原理：改前端后必须重新构建 exe（原 `MAINTENANCE.md` §4「单二进制原理」）

- **现象**：只跑 `npm run build -w web` 后运行 exe，界面没变。
- **根因**：`kedai-server.exe` 通过 `include_dir!` **内嵌**`web/dist`（编译期快照，见 `server-rs/src/api/static_files.rs`）。运行时默认只服务内嵌版本；仅显式设置环境变量 `KEDAI_WEB_DIST` 指向磁盘目录时才用磁盘版覆盖（开发调试用，见 `server-rs/src/config.rs`）。
- **做法**：每次改前端后必须重新构建 exe 才会带上新界面；`server-rs/build.rs` 的 `rerun-if-changed=../web/dist` 保证 cargo 感知前端变化，构建脚本另有 mtime 兜底检测。

### 经验 E5 —— 两版同步机制（构建指纹）：测试版与便携版是两条独立编译链，分开构建必然漂移（原 `MAINTENANCE.md` §4「两版同步机制(构建指纹)」）

- **现象**：测试版与便携版各把编译那一刻的 `web/dist` 冻结进二进制，分头构建后两端界面/行为不一致。
- **根因**：两条独立编译链没有共同的同步约束。
- **做法**：根治手段是「默认双端同步 + 指纹可查 + 启动对齐」三层——
 1. **构建层**：`build.ps1` 默认一次产出两端；每个 dist 产物旁边写 `<exe>.build.json`（`{version, build_time, dist_hash}`，算法见 `tools/Write-BuildStamp.ps1`）。
 2. **运行时层**：`server-rs/build.rs` 把 `KEDAI_DIST_HASH`/`KEDAI_BUILD_TIME` 编进二进制，`GET /api/health` 返回 `{ok, ts, version, build_id, build_time, data_dir, dependencies:{db}}`；设置中心底部常驻显示「版本 · 构建时间 · 指纹前 8 位」，两端各开一次对比即可肉眼确认同步。
 3. **启动层**：`start.ps1` 与图形启动器（`Kedai.exe`，源码 `launcher/`）启动前比对两端 sidecar 的 `dist_hash`，不一致自动执行 `build.ps1` 双端重建；`Kedai.lnk` 指向图形启动器，双击自带过期/漂移检测（直接双击 dist 里的裸便携版 exe 没有这层保障）。

### 经验 E6 —— `bump-version.ps1` 的两个缺陷：替换偏移必须推进、semver 后缀必须用 `-` 连接（原 `archive/2026-09-16-consolidation/0.3.0-beta-变更说明.md`）

- **现象**：① `packages[""]` 版本永远改不到（真 bug）：原实现每轮都从文件头 `Match`/`Replace(count=1)`，替换后原位置 **仍是合法匹配**，于是第二轮又命中同一处（把顶层改了两遍），`packages[""]` 始终停在旧版本 → lock 自身版本与 `package.json` 不一致（严格校验下会被 `npm ci` 判为不同步）。实测：修复前顶层 `0.3.0-beta`、`packages[""]` 仍 `0.2.1`；修复后两处一致。② 不支持预发布后缀：原校验 `^\d+\.\d+\.\d+$` 且注释称「后缀请手工评估」。
- **根因**：① 全局替换未推进搜索偏移；② 版本正则不接受 `x.y.z-预发布` 形态。
- **做法**：① 改为 **替换后推进搜索偏移**再找下一处；② 改为合法 semver 校验（`x.y.z` 或 `x.y.z-预发布`），并在拒绝时提示「**后缀必须用 `-` 连接，不能写成 0.3.0beta**」，把这次踩到的坑固化成脚本行为；`MAINTENANCE.md` 的版本行正则同步支持后缀。

### 经验 E7 —— R8 混淆会重命名被 JNI 按名调用的 Kotlin 类/方法（原 `archive/2026-09-16-consolidation/android-port-plan.md` §五之五）

- **现象**：**只在 release 包出现、debug 包完全正常**：release 签名包保存 API Key 报 `500「设置保存失败: 调用 KeystoreBridge::encrypt 失败: Java exception was thrown」`。
- **根因**：release 启用 R8 混淆，它 **重命名**了 `com.kedai.app.KeystoreBridge` 及其方法；而 Rust 侧是按**字符串名**反射调用的（`FindClass("com/kedai/app/KeystoreBridge")` + `CallStaticMethod("encrypt")`），改名后自然找不到。Tauri 自动生成的 `proguard-wry.pro` 挡不住：它保留的是 `-keep class com.kedai.app.* { native <methods>; }`，即「**Java 声明、native 实现**」的方法；而 `KeystoreBridge` 是 **反向**的——Kotlin 实现、被 native 调用，方向不同，规则不覆盖。
- **做法**：两处双保险——
  ```proguard
  # app/proguard-rules.pro —— 整类保留
  -keep class com.kedai.app.KeystoreBridge { *; }
  ```
  ```kotlin
  // KeystoreBridge.kt —— 类与成员加 @Keep(androidx 注解,R8 识别)
  @Keep object KeystoreBridge {
  @JvmStatic @Keep fun encrypt(plain: String): String { ... }
  @JvmStatic @Keep fun decrypt(encoded: String): String { ... }
  }
  ```
  **关键踩坑：逐成员写签名不可靠。** 最初的规则写成 `-keep class ...KeystoreBridge { public static java.lang.String encrypt(java.lang.String); }`，结果**类名保留了、方法名仍被混淆**——在 dex 里搜得到 `KeystoreBridge` 但搜不到 `encrypt`/`decrypt`（Kotlin `object` + `@JvmStatic` 的实际描述符与手写规则未逐字匹配）。必须用 **整类保留 `{ *; }`**，并 **用 dex 字节搜索验证方法名**，不能只看类名。教训：**凡被 Rust 通过 JNI 按名调用的 Kotlin 类/方法，都必须加 keep 规则**（整类保留，并验方法名）；release 包必须实测关键路径，不能只验 debug（release 包 `android:debuggable=false`，无法用 `run-as` 读写其私有目录，排查需依赖应用内 API 或 logcat）。修复后实测：`PUT /api/settings` → **200**，`has_api_key: true`、`api_key_masked: "****7890"`；dex 内 `KeystoreBridge`/`encrypt`/`decrypt` 三者均在。

### 经验 E8 —— APK 换密钥必须先卸载旧版否则丢应用数据；发布必须始终用固定 keystore（原 `archive/2026-09-16-consolidation/代码签名与SmartScreen说明.md` §3.3）

- **现象**：换密钥签的新版无法覆盖安装，只能卸载后重装。
- **根因**：APK 与 Windows exe 走不同的签名体系：APK 用 release keystore 自签，构建即签名；Android 要求 **同包名 + 同签名密钥**才能覆盖升级。
- **做法**：发布 APK 必须始终坚持用 `D:\kedai-android\keystores\kedai-release.jks`（别名 `kedai`），口令配置在 `src-tauri\gen\android\keystore.properties`（已被 `src-tauri/gen/android/.gitignore` 忽略，不入库）。**切勿重新生成密钥**。同族一致性要求：`.build.json` 指纹（`{version, build_time, dist_hash}`）必须与构建方公布值一致——但它 **未与 exe 做密码学绑定**，可被一并替换，属一致性辅助而非信任根；`dist_hash` 只覆盖 `web/dist` 前端资源，不是 exe 二进制自身的哈希。实测核验值：证书 SHA-256 `19d79a89d87473d286b1ab4d5a45defceae70efe65fa2de0369c1de25f2f062f`，DN `CN=Kedai, OU=Kedai, O=Kedai, L=Unknown, ST=Unknown, C=CN`。

### 经验 E9 —— Android 构建：`.bat` 必须纯 ASCII + CRLF（原 `archive/2026-09-16-consolidation/android-port-plan.md` §五 / §五之二）

- **现象**：`wcargo.bat` 与 `ata.bat` 都因 UTF-8 中文注释整体崩坏（吞首字节导致命令拼接错误）。
- **根因**：cmd.exe 在本机 GBK 代码页下会误解析 UTF-8 中文注释。
- **做法**：`.bat` 脚本一律纯 ASCII + CRLF，注释改英文。

### 经验 E10 —— `tauri icon` 的输出路径坑（原 `archive/2026-09-16-consolidation/android-port-plan.md` §五之四）

- **现象**：换图标后 APK 里仍是旧图标，**资源合并不报错，只是静默不生效**。
- **根因**：`tauri icon` 不认 `--output <res 目录>`，而是按「平台名」在输出目录下建子目录（`<output>/android/mipmap-*`、`<output>/ios/...`）并顺带写一堆 Windows/iOS 资源。
- **做法**：输出到临时目录后，把 `android/` 下的 mipmap 与 values 搬进 `gen/android/app/src/main/res/`，再删掉多余平台目录。

### 经验 E11 —— Android 退出命令的两个坑（原 `archive/2026-09-16-consolidation/android-port-plan.md` §五之四）

- **现象**：① `plugin:app|exit`（壳内 AppPlugin 的命令）不可用——调用被 ACL 拒绝，报 `app.exit not allowed. Command not found`；② `getCurrentWindow().close()` 在 Android 上 **不结束 Activity**——调用后进程仍在且 Promise 悬挂。
- **根因**：① Rust 侧没有对应权限声明；② 平台语义差异。
- **做法**：自己加 `#[tauri::command] fn exit_app` + `invoke_handler`，自定义命令不受插件 ACL 约束。注意该命令 **不能加 `#[cfg(mobile)]`**——`generate_handler!` 在桌面端会因找不到宏而编译失败；桌面端无 UI 入口调用它，两端都注册不影响行为。

### 经验 E12 —— Android 工具链：镜像、init 覆盖与 `--target` 取值（原 `archive/2026-09-16-consolidation/android-port-plan.md` §五 / §五之六）

- **现象**：① `services.gradle.org` 与 `google()`/`mavenCentral()` 在本网络不可达（Gradle/Maven 直连超时）；② 补丁与镜像配置在重新 `tauri android init` 后被覆盖；③ 传 `--target arm64` 直接报 invalid value。
- **根因**：网络限制 + 生成目录被 init 重写 + tauri CLI 期望 Rust 三元组风格取值。
- **做法**：gradle wrapper 切腾讯镜像、`build.gradle.kts` 加阿里云镜像（镜像在前、官方兜底）；`src-tauri/gen/android/` 下 `BuildTask.kt`、`network_security_config.xml`、gradle 配置等原生补丁重新 init 会被覆盖，**需重打**；`--target` 取值是 `aarch64`/`x86_64`/`armv7`/`i686`；`gradle.properties` 的 `abiList`/`targetList` 对 tauri CLI 构建 **不生效**（实测仍产出 4 ABI 的 125MB universal APK），要控制 ABI 只能靠 CLI 的 `--target`（可传多个）或直接调用 gradle 构建。

### 经验 E13 —— Android 环境安装与依赖：JDK/NDK/libclang 与 cfg 按平台分离（原 `archive/2026-09-16-consolidation/android-port-plan.md` §五）

- **现象**：① `reqwest` 的 `native-tls` 在 Android 上要求系统 OpenSSL，`openssl-sys` 硬阻塞；② `rquickjs-sys` 0.12.2 与 0.13.0 均不含 `bindings/aarch64-linux-android.rs`，必须启用 `bindgen` feature（需 libclang，而 **NDK 自带 clang 但不含 `libclang.dll`**，须单独准备并设 `LIBCLANG_PATH`）；③ bindgen 的 clang 参数在 Windows 上被吃反斜杠（最隐蔽，clang 把 `\` 当转义符，`--sysroot=D:\a\b` 会变成 `D:ab`，导致 `stdbool.h`/`stdio.h` not found）；④ 系统 JDK 26 **不可用**；⑤ Gradle 缓存默认在 C: 会吃数 GB。
- **根因**：跨平台交叉编译的原生依赖与工具链路径处理。
- **做法**：① Cargo.toml 按目标分离——`cfg(not(target_os="android"))` → `native-tls`，`cfg(target_os="android")` → `rustls-tls`（桌面行为逐字节不变，已 `cargo check` 验证）；② 仅在 `cfg(target_os="android")` 启用 `bindgen`（上游 build.rs 在 `target == host` 时复用内置绑定，桌面构建不真正调用 libclang，行为不变），NDK 用 r27 `27.0.12077973`；③ 不用 `--sysroot`，改为 **逐架构显式 `-isystem`**，路径 **全部用正斜杠**：`-isystem <ndk>/sysroot/usr/include/<arch> -isystem <ndk>/sysroot/usr/include -isystem <ndk>/lib/clang/18/include`，经 `BINDGEN_EXTRA_CLANG_ARGS_<target>` 传入；④ 用 Temurin 17.0.20.1（`D:\kedai-android\jdk\temurin-17`）；⑤ `GRADLE_USER_HOME=D:\kedai-android\gradle-home`，全部落 D: 盘避免挤爆 C:（安装前实测 C: 仅剩 7.4GB）。

## 三、测量与实验

### 经验 E14 —— 资源上限的正确取值靠实测确定边界，不能凭直觉放大（原 `archive/2026-09-16-consolidation/known-limitations.md` L20）

- **现象**：rquickjs 沙箱（`scripts/runtime.rs`）设置了内存上限（64MB）与协作式中断（1s），但 **未设置栈上限**（全仓无 `set_max_stack_size`）；深递归脚本可致栈溢出，而 rquickjs 虽为独立 Runtime，宿主进程与之同栈空间，存在崩溃宿主的风险。
- **根因**：**原判断「未显式设置 = 拿到库默认值」是错的**——实测 rquickjs **不会**自动施加安全默认值，未调用 `set_max_stack_size` 时深递归以 `STATUS_STACK_OVERFLOW`**直接杀进程**（比「缺一个上限」更严重，可被单张卡挂掉整个后端）；且 **该上限不是「越大越安全」，而是越大越危险**：QuickJS 以 **原生栈指针**为基线记账，上限越大允许的 JS 帧越多，原生栈越可能在 QuickJS 检查触发前先溢出——那时是进程被杀，没有可捕获的 JS 异常。实测（Windows，单档隔离）：

| 栈上限 | 深度 30 | 深度 100 | 深度 300 |
| --- | --- | --- | --- |
| 未显式设置 | **崩进程** | **崩进程** | **崩进程** |
| 256KB | JS 异常 | JS 异常 | JS 异常 |
| **512KB（采用值）** | **正常** | JS 异常 | JS 异常 |
| 1MB+ | 正常 | **崩进程** | **崩进程** |

- **做法**：`EvalOptions.stack_limit` 缺省 `DEFAULT_STACK_LIMIT = 512KB`（`scripts/runtime.rs`），两处执行入口（`eval_js`/`eval_with_bridge`）均显式设置；回归测试 3 条（深递归返 Error 不崩进程、默认上限允许常规递归、显式上限生效）。**教训：资源上限的正确取值靠实测确定边界，不能凭「留宽裕些更好」的直觉放大。**

### 经验 E15 —— 推理模型的预算语义是「推理与正文共享同一池」（原 `archive/2026-09-16-consolidation/截断与Agent工具面修复计划-2026-09-16.md` §0.2）

- **现象**：本机实测（`deepseek-flash`）三条硬数据——`max_tokens=64` → 推理烧掉全部 64，正文为空，自愈到 128 依然如此；`max_tokens=10000` → `reasoning_tokens=9894`，正文只剩 178 字符即 `finish_reason=length`；**单次子任务仅推理就能吃掉近万 token**。
- **根因**：思考模型的推理与正文 **共享同一个 `max_tokens` 池**，任何「小预算」档位对思考模型都等于「必然截断」。
- **做法**：下限必须按推理消耗量级设（16384），而不是按交付物长度设；且 **自愈的封顶必须高于下限**，否则「翻倍」会被封顶压回原值，自愈被静默放弃（本次 `TRUNCATION_HEAL_MAX_TOKENS_CAP` 8192 < 新下限 16384 正是这个陷阱，属连带必修项）。

### 经验 E16 —— 性能基线的口径：本机 release、只作回归对比、不可当跨机 SLA（原 `MAINTENANCE.md` §0「性能门禁」）

- **现象**：`tools/perf-baseline.mjs` 支持 p95 阈值判定（`--max-p95-factor`，默认 1.25），基线值存 `tools/perf-baseline.json`；经 `check-all.ps1 -Perf` 并入总门禁（**默认关闭**）。
- **根因**：需服务已在运行；若把「没起服务」误报成门禁失败会污染结论，故服务不可用时 fail-closed 而非静默跳过。
- **做法**：判定口径 `p95 <= 基线 × 倍数` 且 `errors == 0`，`p95 < 5ms` 的端点跳过。基线是 **本机 release 口径**，换机器或数据量变化后须重采样。数据与用法见 `archive/2026-09-16-consolidation/perf-baseline.md` 的「2026-09-14 实测」小节。

### 经验 E17 —— 「环境侧」报错有固定的取证步骤，先排除再改代码（原 `archive/2026-09-16-consolidation/工程修复计划-2026-09-15.md` 「环境侧备忘」及报告 §6）

- **现象**：三类「看起来像代码/依赖问题」的报错反复出现：`required to be available in rlib format`/`can't find crate for kedai_server`；`deps/` 里只有 `.rmeta` 无 `.rlib`；集成测试目标报「找不到 rlib」。
- **根因**：分别对应 rustc 进程自身崩溃、check/clippy 模式残留、两者叠加（详见本文条目 29、30）。
- **做法**：照「现象 → 真实原因 → 处置」三步自查，不要绕远路：① 默认并行度下 **rustc 进程崩溃**（`0xc0000409 STATUS_STACK_BUFFER_OVERRUN`）→ 降并发 `-j 2` 复跑，**不要改依赖**；② check/clippy 残留（实测 183 个孤立 `.rmeta`）→ 清理孤立 `.rmeta` 与对应 `.fingerprint/*-<hash>`；③ 两者叠加 → 先清残留，再 `-j 2` 复跑。**核心纪律：报错文案指向依赖/权限时，先怀疑环境与工具链，再怀疑代码。**

## 四、架构与抽象

### 经验 8 —— history 注入（原 `MAINTENANCE.md` §10 条目 8）

- **现象**：engine 构造 LLM 消息时，历史里的 `system` 消息被跳过；`memory` 消息的注入逻辑存在但当前调用路径不传 `extra`。
- **根因**：与 Node 版行为保持一致——历史不带 `extra`。
- **做法**：维持现状，保持行为一致；改 messages 组装时不要「顺手指令化」历史。相关实现见 `agents/engine/messages/build.rs`（`build_llm_messages_with_position`）。

### 经验 11 —— mvu 系统来源澄清（重要）（原 `MAINTENANCE.md` §10 条目 11；源文档编号重复，此处照录）

- **现象**：曾有一份外部 AI 分析以某 SillyTavern 扩展的 `bundle.js`（含 `generation_id` 随机 UUID、`遵循<must>指令`、`兼容假流式`、`额外模型解析配置`、`ordered_prompts` 数组）为依据，得出「缓存命中率极低 5 因素」结论。

- **做法**：Kedai 真实的缓存注意点——变量树经 `{{format_message_variable}}`/`{{getvar::stat_data…}}` / EJS 宏展开进 system 提示词，变量更新会使 system 前缀变化、前缀缓存失效；可用设置 `mvu_vars_position=user_tail` 把变量块挪到最新用户消息尾部以提升命中率。**教训：外部材料的结论必须先核实代码是否存在，不能直接套用到本项目。**

### 经验 12 —— 导入 ST 预设的空楼层过滤（原 `MAINTENANCE.md` §10 条目 12）

- **现象**：导入酒馆预设后，纯 `{{addvar}}` 累积宏的楼层展开为空字符串。
- **根因**：宏自身输出空；engine 组装消息时已跳过空楼层/空注入（`agents/engine/messages/build.rs` `build_llm_messages_with_position`），不会产生空 user/assistant 消息。

### 经验 13 —— 变量协议示例不要写进恒存在的 system 提示词（原 `MAINTENANCE.md` §10 条目 13）

- **现象**：把 `<UpdateVariable>` 输出协议示例硬编码进默认/自定义 system 提示词后，无变量树的普通卡也会看到协议：mock `[[floors]]` 回显 system 时示例会被 `parse_update_variable` 解析成真实补丁、空树建树并推送 vars 事件（**曾有集成测试全红**）；真实场景下模型也可能模仿示例输出补丁、误激活变量系统。

### 经验 14 —— 沙箱 realm 与酒馆不同：同卡脚本共享 window 需显式机制（原 `MAINTENANCE.md` §10 条目 14）

- **现象**：2026-09 修复记录（commit f2c10d1）。Kedai 每脚本一个不透明源 iframe，同卡多个 tavern_helper 脚本 **互不可见 window 全局**——ST 生态脚本「th-A 挂 window.WuWaShared → th-B 读」的写法在这里会失效，直接裸读 `top`/`parent` 还抛 SecurityError（WuWa Solaris-3 卡崩溃根因）。
- **根因**：沙箱隔离模型与酒馆不同：同卡脚本被合并进单 iframe，跨组则分属不同 realm。
- **做法**：两条通道（按需二选一，勿混）——① **同卡同 realm**：卡级脚本已合并进单 iframe，靠逐 `<script>` 注入共享 window（`web/src/cardScriptHost.ts` + `boot-script.ts` 多段形态），同段组内的脚本可互读全局；② **跨 realm 共享桥**：不同沙箱（消息级脚本、不同时机起的卡级组）之间靠 shared-globals 快照桥（`web/src/sandbox/shared-globals.ts`），只同步合法键 + JSON 可序列化 ≤256KB 的 window 自有属性，函数 / DOM 引用不共享（见 `archive/2026-09-16-consolidation/known-limitations.md` L5）。另：**运行期注入 `<style>` 会触发 dom-rpc 的声明级清洗 + 容器作用域化**——容器必须带 `data-kd-scope`（渲染块自带，卡级容器由 cardScriptHost 设 `cardScopeId`），否则样式段退回纯白名单仍被剥，界面裸渲染。

### 经验 15 —— 悬浮窗脚本依赖的 jQuery 面比想象宽（原 `MAINTENANCE.md` §10 条目 15）

- **现象**：2026-09 修复记录（commit 280e1cf）。WuWa 卡三个悬浮窗暴露三类缺口，新增卡脚本报「悬浮球不显示/拖不动/切卡残留」时按此排查。
- **根因**：① **jQuery UI `.draggable()` 沙箱没有**——th-5 无 `typeof` 守卫会直接 TypeError 中断整段脚本（连悬浮球都不挂）；② **`$('head')` 与 `.css({...})`**：`queryScoped` 只特判 body/html 时，`$('head').append('<style>…')` 零匹配静默丢失（面板失去 position:fixed/display:none → 落进消息流）；`.css({k:v})` 对象形式若被当 getter 吞掉，`$('<div>').css({position:'fixed'})` 全部丢失；created 元素 `.attr('id',…)` 同理；③ **注入的 DOM 无人回收**：cleanup 原本只销毁 iframe/监听器/订阅，脚本 `$(window).on('unload')` 钩子在沙箱内静默失效 → 切卡后幽灵悬浮窗。
- **做法**：① 宿主侧 `web/src/sandbox/draggable.ts` 提供最小实现（handle/cancel/containment/distance + start/drag/stop 回调），能力边界见 known-limitations L6；② 补齐 `queryScoped` 对 head 与 `.css` 对象形式的处理；③ 由 `data-kd-injected` 标记 + `data-kd-overlay-root` 覆层根统一清理；**capture 登记的监听器必须带 capture 摘除**（`removeEventListener` 的 capture 不匹配会摘不掉，拖拽中切卡残留 document 监听）。

### 经验 18 —— 世界书条目的 depth/role 在角色卡里常放在 `extensions`（原 `MAINTENANCE.md` §10 条目 18）

- **现象**：2026-09 第四轮实测踩坑。顶层 `depth` 缺省 4；而真实卡（赛马娘 95 条、爱托邦 109 条、吸血鬼 54 条）**全部**把 `depth` 写在 `extensions`，顶层没有。只读顶层会让作者设的 1/2/5 一律退化到 4：depth=1/2 被放宽 → 关键词在窗口外仍命中、污染提示词；depth=5 被收窄 → 漏注入。

### 经验 19 —— 卡内 CSS 注释会吞掉紧随的声明（原 `MAINTENANCE.md` §10 条目 19）

- **现象**：2026-09 第四轮实测踩坑。`/* 说明 */\n background-image: …` 的属性名会被声明切分当成 `/* 说明 */ background-image`，不匹配属性白名单 → **整条声明被丢弃**。赛马娘卡因此丢了 `body` 的纸纹背景、`.select-item` 的 `gap`、`.description-box` 的 `padding`。

### 经验 24 —— API Key 解密失败曾在一次保存后被静默清空（原 `MAINTENANCE.md` §10 条目 24）

- **现象**：2026-09-13 批次 2 修复。`secret_store::unprotect` 解密失败返回空串（视为未配置，避免把密文当 Key 发给上游），而 `save` 直接 `protect(内存值)`——换用户/换机器/密文损坏后，用户下一次保存设置（改个温度也算）就会用空串覆盖磁盘密文，**密钥永久丢失且只有一行 stderr**。
- **根因**：读取侧「失败降级为空」与写入侧「无条件回写内存值」组合出的破坏性交互。
- **做法**：`settings_service/secret.rs::save` 先读盘，「内存为空而磁盘仍是非空 `enc:v1:` 密文」时原样回写密文并留痕。**不会误伤清空操作**：`PUT /api/settings` 对空值直接忽略（`api/settings.rs:300-305`），接口层面无法把已配置 Key 改为空。改密钥相关代码时保持该不变式，并跑 `secret.rs` 的 3 个保留测试。

### 经验 25 —— schema.rs 加列漏写 `ensure_*` 迁移只在老用户机器上炸（原 `MAINTENANCE.md` §10 条目 25）

### 经验 E20 —— Android JNI 桥接的两条硬约束（原 `archive/2026-09-16-consolidation/android-port-plan.md` §五之三）

- **现象**：Android Keystore 桥接（`keystore_android.rs` ↔ `KeystoreBridge.kt`）若违反两条约束必然踩坑。
- **根因**：① **类加载器**：在 `AttachCurrentThread` 附加的原生线程上 `FindClass` 走的是系统类加载器，找不到应用类；② **VM 指针**：Rust 没有 JavaVM，只能由 JVM 在 `System.loadLibrary` 时经 `JNI_OnLoad` 传入，且该函数定义在 **cdylib 根**（`src-tauri/src/lib.rs`），依赖库内部定义可能被链接器丢弃。
- **做法**：① 必须在 `JNI_OnLoad` 期间（此时类加载器可见应用类）`FindClass` 一次并缓存为 `GlobalRef`，后续线程复用；② `JNI_OnLoad` 放 cdylib 根，并核查 tao/wry/tauri 全栈 **无**其它 `JNI_OnLoad`（否则会符号冲突）；调用 Kotlin 只走两个字符串进出的静态方法，不在 Rust 里逐个拼 `javax.crypto` 的 JNI 调用。密文格式用 `[1 字节 IV 长度][IV][密文+标签]`，**存 IV 长度而非写死 12**，避免不同实现下 IV 长度变化导致解密失败；`secret_store` 三平台分支（Windows DPAPI / Android Keystore / 其它平台维持原拒绝语义）共用 `enc:v1:` 前缀，避免上层迁移逻辑分叉。

### 经验 E21 —— `Db::write()` 返回 `MutexGuard` 的作用域纪律（原 `MAINTENANCE.md` §7「维护注意」）

- **现象**：持写锁期间再取写锁会死锁。
- **根因**：`Db::write()` 返回 `MutexGuard<Connection>`，std::sync::Mutex 非重入。
- **做法**：**必须在其作用域结束后再调用其他取写锁方法**；只读查询用 `Db::read()`（连接池，无此约束）。数据兼容性亦在此节记录：表结构与原 Node 版完全一致，旧 `kedai.db` 可直接使用（已验证）；备份复制 `data/` 目录即可（SQLite WAL 模式建议先停服再拷，或同时拷 `-wal`/`-shm`）。

### 经验 2 —— std::sync::Mutex 不可重入（原 `MAINTENANCE.md` §10 条目 2）

- **现象**：`services` 层 DB 操作持锁期间再调用同类方法会死锁。
- **根因**：`std::sync::Mutex` 非重入。
- **做法**：目前代码已按「先释放锁再查」处理，新增代码须遵守；全项目锁中毒一律恢复（`.lock().unwrap_or_else(|e| e.into_inner())`），不 panic；**禁止持 std::sync::Mutex guard 跨 `.await`**（Clippy `await_holding_lock` 防护）。细则见本文条目 E21 与下方「DB 并发纪律」。

### 经验 17 —— 16GB 内存 + 11GB 页面文件下禁止全并行 debug 链接（原 `MAINTENANCE.md` §10 条目 17）

- **现象**：2026-09 实测踩坑。`cargo test`/`cargo build`（debug）全并行链接 `libkedai_server-*.rlib`（带 debuginfo 约 665MB）会触发 `os error 1455 页面文件太小`，rlib 被写坏后 **后续所有编译持续报 E0786「invalid metadata files」**，表现为莫名其妙的全量失败。
- **根因**：内存/页面文件被并行链接耗尽。
- **做法**：规避用 `.shakedown/krun.bat`（已封装 `vcvars64 + CARGO_BUILD_JOBS=4 + debuginfo=0`）；遇到 E0786 先删坏 rlib（`rm server-rs/target/debug/deps/libkedai_server-*.rlib`）再重建。**注意 release 构建（build.ps1）不受影响**（LTO + strip，产物小），但构建期间不要与前端 vitest / cargo test 并发跑，内存争用会让链接器崩（`0xc0000409`）。**另见条目 29**：`rustc` 自身崩溃（`STATUS_STACK_BUFFER_OVERRUN`）同样会伪装成「rlib 缺失」，那是另一诱因，处置也不同。

### 经验 29 —— 见到「依赖 rlib 缺失」先降并发，不要改依赖（原 `MAINTENANCE.md` §10 条目 29）

- **现象**：2026-09-15 实测，批次 0 入档。文案：`error: crate <name> required to be available in rlib format, but was not found in this form`，或 `error[E0463]: can't find crate for kedai_server`。
- **根因**：**真实原因不是代码或依赖问题**：默认并行度下 **rustc 进程自身崩溃**（退出码 `0xc0000409 STATUS_STACK_BUFFER_OVERRUN`），崩溃信息在日志末尾可见；进程被杀导致依赖产物缺失，才表现为「找不到 rlib」。
- **做法**：改用 `-j 2` 复跑（**实测一次通过、0 编译错误**），**不要改依赖**——照报错去动 `Cargo.toml` 只会越改越偏。`tools/check-all.ps1` 的 `cargo test --workspace` 步骤已带 `-j 2`（注释记录了本机并行链接的历史故障），但该规避 **只覆盖脚本内部**：直接调用裸 `cargo test` 仍会撞上，故 `AGENTS.md` 的验证命令也已补 `-j 2`。**与条目 17 相关，此为另一诱因**：条目 17 是 16GB 内存 / 11GB 页面文件下全并行链接的 **内存耗尽**（表现为 `os error 1455` / `E0786 invalid metadata files`），本条是 **rustc 自身栈溢出崩溃**；两者都表现为「rlib 异常」，但诱因与处置不同，勿混。

### 经验 30 —— `target\debug\deps\` 里只有 `.rmeta` 没有同名 `.rlib` 的孤立产物（原 `MAINTENANCE.md` §10 条目 30）

- **现象**：2026-09-15 实测 **183 个**。`cargo check`/`cargo clippy` 只产元数据不产 rlib，与 `cargo test`/`cargo build` 交替执行时便会残留——它正是上一条「找不到 rlib」的 **直接来源**。
- **根因**：两种 cargo 模式的产物集合不同，交替执行留下不成对的产物与指纹。
- **做法**：清掉孤立 `.rmeta` 及与之对应的 `.fingerprint\*-<hash>` 目录（**成对删除**：只删 `.rmeta` 会留下失配指纹，反而引出新怪象）。此类残留会随 `check`/`clippy` 与 `test` 交替执行而 **持续累积**，故每次撞上「找不到 rlib」先看这里，再按条目 29 降并发复跑。

### 经验 E22 —— DB 并发纪律（2026-08 改造）（原 `MAINTENANCE.md` §7「DB 并发纪律」）

- **现象**：api handler 直接做同步 DB 调用会卡住 tokio worker；`db_write` 闭包内再取写锁会自死锁。
- **根因**：两类句柄语义不同，且写连接全局唯一：`Db::read()` 返回只读连接池句柄（`PooledRead`，**SELECT 专用**，可并发多连接）；`Db::write()` 返回全局唯一写连接的 `MutexGuard`，一切写 SQL 与「读+写同事务」的混合场景走它。
- **做法**：**handler 必须过阻塞池**——api handler 禁止在 async 上下文直接执行同步 DB 调用，一律经 `AppState::db_call`（任意 services 同步方法）/`db_read`（只读闭包）/`db_write`（写闭包），三者内部均为 `spawn_blocking`。**`db_write` 非重入**：闭包执行期间已持有唯一写连接，**闭包内不得再调用会重新获取写锁的 services 写方法**（Mutex 非重入 → 自死锁）；需要走 services 写方法时用 `db_call`（连接由服务内部按需获取）。**失败出口**：阻塞任务 JoinError / 连接池错误 / 服务内 String 错误统一由 api 层 `db_err` 转 500 + `code: "DB"`；锁中毒一律恢复，不 panic。

### 经验 E23 —— 磁盘瘦身：可删的是构建缓存，`data/` 切勿删除（原 `MAINTENANCE.md` §9「空间清理与数据布局(磁盘瘦身)」）

- **现象**：项目主要占用来自 **构建缓存**；用户数据集中在 `data/`。
- **根因**：缓存目录可再生，用户数据不可再生。
- **做法**：可安全删除 `server-rs/target/`（数 GB~11GB）、`src-tauri/target/`（~2.3GB）、`node_modules/`（~112MB，删后须 `npm install`）、`sandbox/`（~65MB）、`dist/`（~28MB）、`data-backup-before-v3fix/`（~20MB，一次性旧备份）、`launcher/target/`（~10MB）、`logs/`（~1MB）；**`data/` 切勿删除**（`kedai.db`、`characters/`、`avatars/`、`settings.json`、`prompt_floors.json`、`agent_flows.json`、`AGENTS_RUNTIME.md`）；`web/dist/` 建议保留。清理命令（PowerShell，应用停止时执行）：
  ```powershell
  Remove-Item server-rs\target, src-tauri\target, launcher\target, node_modules, sandbox, dist, logs, data-backup-before-v3fix -Recurse -Force
  npm install   # 恢复依赖(如不删除 node_modules 可跳过)
  ```
  **实测记录（2026-08-12）**：删除上述全部目录回收约 **13.5GB**（server-rs/target 11.3G + src-tauri/target 2.3G + node_modules 112M + sandbox 65M + dist 28M + data-backup 20M + launcher/target 10M + logs 1.2M）。`data/`（角色卡、数据库、设置）与 `web/dist` 未动，应用数据完整。**注意**：删除 `server-rs/target` 后，首次 `cargo build/test` 需全量重编（集成测试编译约 2~5 分钟量级）。

### 经验 E24 —— Win 构建与 Android 构建必须串行（原 `archive/2026-09-16-consolidation/残余任务与后续计划-2026-09-13.md` §八 5）

- **现象**：`taskkill` / gradle / cargo 并发重活会互相踩。
- **根因**：本机 16GB 内存，并发链接会崩（见条目 17）。
- **做法**：Win 构建与 Android 构建 **串行**执行。

### 经验 E25 —— `java`/`cargo` 残留进程会耗尽内存（原 `archive/2026-09-16-consolidation/android-port-plan.md` §五之二）

- **现象**：15.2GB 物理内存 + 16.7GB 页面文件在「模拟器 + gradle daemon + 多路 rustc」并发下被打满，导致 rustc 以 `STATUS_STACK_BUFFER_OVERRUN` 崩溃并写出损坏的 `.rmeta`（表现为 `found invalid metadata files for crate ...`）。

### 经验 E26 —— 后台命令的 exit code 不可轻信（原 `archive/2026-09-16-consolidation/残余任务与后续计划-2026-09-13.md` §八 4）

### 经验 32 —— 测试临时数据目录从不清理，会把 %TEMP% 撑爆（原 `MAINTENANCE.md` §10 条目 32）

- **现象**：2026-09-15 实测并修复（测试基建批次 R5）。测试套件到处 `std::env::temp_dir().join(format!("kedai-..."))` 建数据目录（DB/角色文件 / settings.json 等），但 **从不删除**；即使少数用例写了 `remove_dir_all`，也在 `unwrap()` 断言之后，断言失败或 panic 时照样残留。
- **根因**：缺少统一的临时目录守卫，清理时机依赖断言成功。**实测数字**：清理前 `%TEMP%` 累计 **14015 个**`kedai-*` 目录 / **11.22 GB**（最早 09-11，最新 09-15），前缀十几种：`kedai-tool-test-*`（2418）、`kedai-memory-*`（1804）、`kedai-contract-history-*`（1148）、`kedai-session-*`（984）等；单跑一次全量 `cargo test` 就新增 **105 个目录 / 17 种前缀**。这是压满 C 盘的主力之一。
- **做法（新增测试必须遵守）**：
 - 一律用 `server-rs/src/utils/test_support.rs` 的 `TempDataDir::new("<tag>")`（目录名 `kedai-<tag>-<uuid-v4>`，作用域结束 best-effort 递归删除，失败静默忽略且绝不 panic）；**不要再裸写 `std::env::temp_dir().join(...)` 建目录**。模块门控 `cfg(any(test, feature = "test-support"))`，集成测试经 `Cargo.toml` 的自引用 dev-dependency（`kedai-server = { path = ".", features = ["test-support"] }`）打开。
 - **守卫的析构顺序是硬约束**（2026-09-15 rustc 1.97 实测，写反了就是「句柄还开着 → 删除失败 → 静默残留」，不报错但没修好）：局部变量按声明逆序析构（守卫声明在 Db/服务 **之前**）；解构绑定按绑定逆序析构（故 `let (guard, svc) = service();`，**不是**`let (svc, guard)`）；结构体字段按声明顺序析构（守卫必须是**最后一个字段**）；整个元组不解构时按字段顺序。
 - 禁止临时值形态 `Db::open(&TempDataDir::new("x").path().join("kedai.db"), ..)`——语句末守卫即析构，库还开着就删目录。必须先 `let dir = TempDataDir::new("x");`。
 - **不要**给 `lib.rs::build_test_app` 的目录套守卫：它是 `OnceLock` 进程级单例，生命周期等于测试进程，套上会在第一个用例结束就删掉后续所有用例要用的库。个别「按需构造路径」的读取型代码（`tests/undo.rs`、`tests/agent_trace.rs` 等）同理保持现状。
 - 少量确实需要「Drop 后仍检查目录」的场景用逃逸阀 `TempDataDir::keep() -> PathBuf`（极少用）。
- **本批次后的实测残留**：该残留登记见 `遗留.md`。（原文此处附「迁移前 105 个目录 / 17 种前缀 → 迁移后约 30 个」及 `kedai-tool-test-*` 3 个已知有界残留的明细，属「遗留」而非「经验」，由遗留类负责登记，本文按约定截断，仅保留这一句指引。）

### 经验 E27 —— 门禁失败聚合的「自我遮蔽」：两个失败桶必须都打印再退出（原 `MAINTENANCE.md` §0「修复纪律(2026-09-14 教训)」）

- **现象**：规则 I 的前端分支曾误写入后端失败桶，而汇总在后端违规时立即 `exit(1)`，导致 **前端规则 J 的结论永不打印**（护栏静默失效，且当时 26 项未登记使构建被阻断）。
- **根因**：失败聚合逻辑先退出、后打印，一个桶的失败遮蔽了另一个桶的全部结论。
- **做法**：已改为两个失败桶都打印后再统一退出。修改任何门禁脚本的失败聚合逻辑时，**必须验证两侧报告都能输出**，并确认退出码仍非 0。

### 经验 E28 —— 每批次执行纪律：先写失败测试 + 变异测试、ratchet 只降不升、冻结点清单（原 `archive/2026-09-16-consolidation/工程修复计划-2026-09-15.md` §1）

- **现象**：批次化工程中容易混批、顺手改、放宽基线。
- **根因**：本仓已有「批次化 + 变更说明 + 核对表」的成熟体例，混批会让回滚粒度失效。
- **做法（全程适用）**：
 1. **每批次独立可交付、独立可回滚**；不跨批次顺手改别的东西（`AGENTS.md` 禁用项）。
 2. **先写失败测试**（`AGENTS.md` 约定）；新测试须经 **变异测试**确认能捕获目标缺陷，避免「永远通过」的装饰性断言。
 3. **ratchet 只降不升**：改动 `tools/check-arch.mjs` 基线必须同步下调并记录前后值。
 4. **数字同步**：测试数量以 `MAINTENANCE.md` 为唯一真值源，每次新增测试后跑 `node tools/count-tests.mjs --check` 确认不漂移。
 5. **`-j 2` 是必需参数**（默认并行度下 rustc 可能崩溃，报错伪装成「依赖 rlib 缺失」）。
 6. Git 提交按 `AGENTS.md` 「Git 提交纪律」执行；需 exe 版时另跑 `.\build.ps1`。
 7. **不可动的冻结点**：`models/db/schema.rs` 的 `CREATE_TABLES` 静态文本（须与 `ddl.rs` 在 `normalize_sql` 后一致）；`SseEvent`/`TaskEventKind` 线格式值（`check-contract.mjs` 守卫）；EJS 能力面（规则 H 冻结，只降不升）；` / api/health` 的 `ok` 语义（桌面壳单实例判定依赖它）；SSE 重连算法（只加可观测信号，不改策略）。

### 经验 E29 —— 「测试全绿」这次给出的信号是假的：mock 与后端实现不一致（原 `archive/2026-09-16-consolidation/工程实测报告-2026-09-15.md` §3.2）

- **现象**：`/api/diagnostics/cache` 三缺陷叠加，优化面板的缓存健康区在当时 **必然打不开**，而三个环节各自「看起来没问题」：① **后端集成测试**永远带 `session_id`（`tests/api_integration.rs` 的两处调用 `?session_id={sid}`/`?session_id={sid}&window=1`），无参分支**从未被执行**；② **前端单测**用 `status: 500` 模拟失败路径，而后端该路径**实际返回 200**——mock 与实现不一致，恰好绕开了缺陷；③ **前端组件测试**注入的是格式正确的样例数据，不经过真实响应形状。
- **根因**：**根因不是某个测试写错**，而是缺少「mock 契约与后端实现对齐」这一层护栏：测试只证明「已写的断言通过」，不证明「未执行的分支正确」。
- **做法**：新增后端负路径测试锁定「200 + 结构完整 + 无 `error` 字段」；前端加 `assertDiagnostics` 形状闸门（载荷缺 `totals`/`entries`/`watermark` 即抛错）；并用 **变异测试**确认新测试有效（临时把 `SQL_ALL_SESSIONS` 改回 `LIMIT ?2` 复现原缺陷，新测试 FAILED、既有测试依然 ok，两侧信息都有价值）——正好印证「既有测试存在覆盖盲区」的判断。

### 经验 E30 —— 测试体系盲区的三条护栏（原 `archive/2026-09-16-consolidation/工程实测报告-2026-09-15.md` §7）

- **现象**：前端单测 mock 的 HTTP 状态码可以与后端实现 **不一致**，而没有任何机制发现它（案例：`web/src/api/diagnostics.test.ts` 原用 `status: 500` 模拟「后端统计失败」，但后端该路径当时实际返回 **200**）。
- **根因**：前后端测试各自独立，缺一层「契约对齐」的机制性护栏。
- **做法**（三选一或组合）：① **契约化 mock**：前端 mock 的状态码/错误体形状从单一位置声明，并在注释中标注对应的后端源码位置（轻量、无新增依赖）；② **新增后端负路径测试**：凡 handler 有错误分支，集成测试必须至少覆盖一次并断言真实状态码（本例即缺此覆盖）；③ **前端形状闸门**：凡 `request<T>()` 的返回被直接解构的 API 封装，加运行时形状校验（`assertDiagnostics` 即首例）。其中 **② 收益最大且不需新机制**：它把「后端错误分支是否被真实执行过」变成可检查的事实。

### 经验 E31 —— 自己写的门禁会误报，要给「误报修正」留时间（原 `archive/2026-09-16-consolidation/残余任务与后续计划-2026-09-13.md` §八 3）

- **现象**：`check-lock-sync` 在发版时报 FAIL（两锁自身版本本就不同步）。
- **根因**：新门禁上线时未把「本仓自身包」这类正常中间态排除。
- **做法**：`check-lock-sync` 需排除本仓自身包（见条目 23⑤）；新门禁上线后要预留「误报修正」时间，别让门禁成为构建的唯一阻塞点却无法调整。

### 经验 E32 —— 门禁纪律：CI 是纸面，实际生效的闸门只有 build.ps1 与 pre-push（原 `MAINTENANCE.md` §0「门禁纪律」）

- **现象**：`.github/workflows/ci.yml` 2026-09-13 落盘，但仓库 **始终未配置 git 远端**（`git remote -v` 为空），故从未触发。
- **根因**：`tools/check-all.ps1` 是唯一的本地 CI 入口，现已接三处触发——① `build.ps1` 在构建前跑 `check-all -Quick`，失败即中止构建（`-SkipChecks` 仅限本地应急，**交付/试用前必须补跑一次完整 `check-all`**）；② `tools/hooks/pre-push` 在推送前跑同一检查（装一次：`npm run hooks:install`；紧急可 `git push --no-verify`，同样须事后补跑）；③ CI 工作流（纸面，从未运行）。
- **做法**：**不要依赖 CI 兜底**——当前实际生效的闸门只有前两条；变更 `tools/check-*.mjs` 的检查规则时，同步更新门禁文档与检查项清单。配置远端并推送后 CI 会自动生效，届时本节应更新为「三处触发均实测生效」。

### 经验 E33 —— 依赖供应链三把闸的默认档位（原 `MAINTENANCE.md` §0「依赖供应链纪律」）

- **现象**：依赖漂移与漏洞需要机器可判的闸门。
- **根因**：双 Cargo.lock 漂移、advisory 漏洞、npm 漏洞各有不同的判定口径。
- **做法**：三把闸已进 `check-all`——① `deps: check-lock-sync`（双 Cargo.lock 漂移检查，**0 漂移为基线**，新增即 FAIL，例外登记 `tools/lock-sync-baseline.json`）；② `cargo audit` 默认 **硬门禁**（server-rs 锁历史 0 洞；仅 advisory DB 拉取失败时降级 WARN，`-LooseAudit` 可临时降档）；③ `npm audit --omit=dev` 警告档（历史 2 洞——sanitize-html 存储型 XSS / nanoid——已修复）。

- **根因**：数字手抄 + 多文档各写一份 = 必然漂移；文档滞后于代码而无人回填。
- **做法**：测试数量以 `MAINTENANCE.md` 为 **唯一真值源**，由 `tools/count-tests.mjs` 自动统计，用 `npm run count:tests` 查看当前值、`npm run check:tests` 校验漂移；**不手抄测试数字**；文档改动「改到谁更新谁」，并在索引（`docs/README.md`）中登记新增规则/文件。（本文遵循同一纪律：凡数字类事实以 `MAINTENANCE.md` 为准。）

### 经验 E35 —— 架构叙事会与实现脱节：偏差必须登记（原 `archive/2026-09-16-consolidation/ARCHITECTURE-3H.md` §7）

- **根因**：架构叙事 **停留在文档层**，代码里仍存在环依赖、重复实现与死抽象；核查依赖 grep 交叉验证 + 全量测试 + 依赖图分析，而不是读文档。

### 经验 E36 —— 计划文档与代码现状不符：4 处实测修正（原 `archive/2026-09-16-consolidation/工程韧性修复-变更说明.md` §4）

## 八、协作与提交

### 经验 E37 —— 与并行写者共处：提交前必须先看工作区是不是自己的（原 `archive/2026-09-16-consolidation/截断与Agent工具面修复计划-2026-09-16.md` §0.4）

- **现象**：本轮实施期间有 **另一个会话在同一分支并行写同一批文件**（R5 测试基建）。
- **根因**：并发会话共享同一工作区，文件边界与提交边界不一致。
- **做法**：① 动手前 `git status` 是 clean，不代表中途还是 clean；**提交前必须重新核对**；② 交织文件（同一文件的 hunk 分属两个批次）无法用 `git add <path>` 干净剥离，只能按「文件归属一个主题」合并提交；③ **依赖倒挂**：我的新测试用了并行批次的 `dummy_for_test()` 新签名，导致「单独提交我的文件」会编译不过——**提交粒度受编译依赖约束，不只是文件边界**。

**案例（2026-09-16 文档整合，违例形态与上面两条不同）**：

- **现象**：六类文档整合期间，另一会话在同一工作区修 IFW-3（`SettingsHub.vue` 的 `ROLEPLAY_ONLY` 误含 `'flow'`）。我用 `git add server-rs/ web/ tools/ AGENTS.md README.md` **按目录整片暂存**回填文档路径引用，把该修复的代码（`SettingsHub.vue` +3 行）与回归测试（`SettingsHub.test.ts` +30 行）一并收走；另有一处测试计数 `834 → 836` 被收进 MAINTENANCE 瘦身提交。两个提交正文均宣称「**纯注释与说明文字改动**」/「该行逐字保留」——**对这几个文件不成立，提交信息失实**。
- **根因**：路径回填天然只改注释，于是我用 `git add <目录>` 图省事，跳过了「逐个文件确认归属」；`AGENTS.md` 与 E40 都写着「不要一把 `git add -A` 了事」，**按目录整片 add 是同一错误的变体**（`-A` 是收全仓，`server-rs/ web/` 是收大半个仓，都越过了文件级核对）。
- **做法**：
  - **按目录整片 `git add <dir>` 之前，先 `git status --short <dir>` 看该目录下每个文件是不是自己的**。若本批只应改注释，而 `<dir>` 下出现了 `.vue`/`.test.ts` 这类非注释文件（回填只碰注释，故出现即异常），立刻 `git add <file>` 逐个指定。
  - **提交后可用一条命令反查是否混入**：`git show <commit> -- <file> | grep -E '^[+-]' | grep -v '^[+-][+-]' | grep -vc '<本批唯一意图的关键字>'` —— 若某文件出现非本意行，即说明被收走。本例正是用这条命令精确定位到只有 2 个文件混入（其余 55 个确为纯路径替换）。
  - **已混入的处置：优先「补记录归属」，不要改写历史**。本例由被影响方追加提交 `56d18af`，在 `功能-变更史.md` 登记「本修复的实际提交归属、勿按提交标题找」，并明确指出原提交正文措辞不实。这比 amend 更稳：一旦混入提交已被后续提交引用为父（本例 `56d18af` 之于 `7ab983c`），amend 会连带作废那些说明本身。

### 经验 E38 —— 顺带修掉的既有缺陷要写进提交信息（原 `archive/2026-09-16-consolidation/截断与Agent工具面修复计划-2026-09-16.md` §0.5）

- **现象**：R5 批次把两个权限测试改用 `TempDataDir` 后，把守卫自动创建的目录当文件写，机制被破坏（`Os error 5 拒绝访问`）。
- **根因**：跨批次改动撞上了别人的在制品。
- **做法**：改成在其内一层放「文件」以保留原机制；这类「修别人的在制品」 **必须在提交信息里说清**，否则后续排查会把作者记错。

### 经验 E39 —— 「四处同源」的常量必须一起改（原 `archive/2026-09-16-consolidation/截断与Agent工具面修复计划-2026-09-16.md` §0.3）

- **现象**：截断自愈的预算决策收敛在 `utils/retry.rs`（2026-09-13 批次 4.1 四路合一），但 **封顶常量仍分散在四处**。若只改校验上限，会出现「设置页允许 131072、重试封顶仍 65536」这类自相矛盾——`doubled_heal_budget` 会因 `min(current*2, cap) <= current` 恒判「无增长」。
- **根因**：同一语义的常量散落在多条路径（env / PUT / generate-raw / 两处重试封顶）。
- **做法**：改这类跨路径常量时，用 `grep` 把「同一语义的所有常量与注释」一次列全，逐个确认。

### 经验 E40 —— Git 提交纪律：完成并验证后按体例提交（原 `AGENTS.md` 「Git 提交纪律」）

- **现象**：旧纪律「一律不提交」导致改动长期滞留工作区，无法用 `git log` 追溯「哪次改动为哪批需求服务」，回滚失去粒度（2026-09-15 修订）。
- **根因**：提交边界即回滚粒度；不提交就没有这种粒度。
- **做法**：
 - **完成一批改动并验证通过后，按仓库体例提交。**
 - **提交信息体例**：Conventional Commits 前缀 + 中文 scope 与描述，沿用既有 commit 风格（例：`refactor(架构治理): 三结合彻底落地——…`、`fix(可观测性): …`）。正文写清 **三件事**：**改了什么 / 为何这么改 / 验证证据（实际跑过的命令与结果）**。
 - **粒度**：一个逻辑批次一个提交；互不相关的改动不混进同一提交；工作区同时存在多条线时，按主题分多次提交（必要时 `git add <path>` 逐个指定），不要一把 `git add -A` 了事。
 - **不提交**：构建产物与其 sidecar（`dist/`、`target/`、`Kedai.exe`、`*.lnk` 等，`.gitignore` 已覆盖）、用户数据（`data/`）、密钥（`.env`）、开发 agent 的会话目录（`.zcode/`）。
 - **提交前的最低验证**：改了后端跑 `cargo test --manifest-path server-rs/Cargo.toml -j 2`；改了前端跑 `npm test -w web`；只改文档可跳过测试，但仍要跑 `node tools/check-arch.mjs` 与 `node tools/count-tests.mjs --check` 确认门禁不漂移。
 - **分支**：主干 `main` + 平台分支 `kedai-Win`/`kedai-Android`（模型见 `archive/2026-09-16-consolidation/平台分支说明.md`）。仓库当前 **未配置远端**；有远端后推送前先确认当前分支，不要在平台分支上提交共享代码。
 - **不改写历史**：不 `rebase`/`amend` 已推送的提交；`docs/archive/` 下的历史文档只读不改。

### 经验 E41 —— 实现约定：先写失败测试、不顺手实现未要求的批次（原 `AGENTS.md` 「实现约定」）

- **现象**：范围蔓延与「没有失败测试的最小实现」会同时污染回滚粒度与回归信心。
- **根因**：未要求的批次一旦顺手做掉，就与当前批次耦合，回滚时无法单独剥离。
- **做法**：面向用户的提示、错误和代码注释使用简体中文；修改核心行为 **先写失败测试，再做最小实现**；不泄露聊天正文、API Key 或本地真实数据；**不顺手实现未要求的安全 / API 批次**。

### 经验 E42 —— 判断编译 / lint 是否通过，不得经由管道取退出码（2026-09-16 踩坑）

- **现象**：自测时执行 `cargo clippy --all-targets -- -D warnings 2>&1 | tail -25`，看到 `Finished` 与随后的
  `echo $?` 为 0，据此判定 clippy 通过并提交；随后跑完整 `tools/check-all.ps1` 时 clippy **FAIL(exit=101)**，
  门禁链在第二阶段即被截断（`unnecessary_sort_by` 在 `-D warnings` 下是硬错误）。两次结论相反。
- **根因**：**`$?` / `%errorlevel%` 取到的是管道最后一段（`tail`）的退出码，不是被检命令的退出码**。
  `tail` 正常读完输入就返回 0，于是「编译失败」被伪装成「通过」。同类陷阱还有 `grep`（无匹配返回 1）、
  `tee`、`Select-Object` 等一切右端命令——只要命令被管道接了尾，退出码就不是被检者的。
  次生伤害更值得记：我因此**误判了两次**（先漏掉 clippy 错误，又把 `check-all` 的失败当成「与本批无关」），
  直到它在门禁里以阻断态复现才回头核查。
- **做法**：
  1. 需要退出码时**不要接管道**——在 `.bat` / PowerShell 里直接跑命令，紧跟一行取码：
     `cargo clippy --all-targets -- -D warnings` 后 `echo CLIPPY_EXIT=%errorlevel%`（`cmd` 下 `%errorlevel%`
     须在同一批处理上下文里立即取）。Windows 上写成一次性 `.bat` 可避开 Git Bash 的引号与路径转换干扰
     （与 `AGENTS.md`「裸 shell 无 cargo，须先 vcvars64」同属该环境备忘族）。
  2. 既要看输出**又**要退出码时，改用「先落文件再筛」：`cmd > out.txt 2>&1` 取码，再 `grep out.txt`。
  3. **以门禁自身的结论为准**：`tools/check-all.ps1` 的分阶段表（`OK`/`FAIL` + exit code）是权威——
     它按阶段失败即停，不会像管道那样掩盖退出码；本地自测脚本要与它同口径，否则「自测通过」不成立。
  4. 补充判据：`cargo build` / `clippy` 输出里出现 `Finished` **不等于**成功，失败时也可能已打印大量
     `Compiling` 行；只有 `error:` / `error[...]` 与外层退出码能定性。
